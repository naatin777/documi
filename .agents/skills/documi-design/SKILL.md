# Documi 上流設計・調査・仕様確定スキル (`documi-design`)

AI がコードを書く前にやりがちな 4 大事故（**車輪の再発明・古い API/Actions 記法・狭い 2 択の ADR・暗黙の前提を勝手な仮定で埋める**）を構造的に防ぎ、人間と合意した仕様・設計・ADR を確定させるための手順です。

## 1. 既存資産と制約の棚卸し（車輪の再発明を防ぐ）

コードを 1 行も書く前に、必ずリポジトリ内の既存資産と前提制約を確認する。

1. `documi map` — Goal・`goalConstraints`・`systemDesigns`・`systemConstraints`（未リリース方針等）・`domainInvariants`・`decisions`・`terms`（`antiTerms` 含む）を把握する。
2. `documi search "<今回のテーマ>" --context` — 関連仕様・既存設計・`<SourceRef>` を一括取得する。
3. 対象領域の `design` にある `<SourceRef mode="exports">` や既存ユーティリティを確認し、**社内に既にある関数・型・UI コンポーネント・エラー型を再発明しない**。

## 2. 最新バージョンと一次情報の確認（古い書き方・API 誤用を防ぐ）

学習データの古い記憶（Knowledge Cutoff）に頼らず、必ず実物と一次情報で裏を取る。

1. **実バージョンの確認**: `package.json`・lockfile・`.github/workflows/*.yml`・Dockerfile 等の実際のバージョンを確認する。
2. **ライブラリ API の裏取り**: 新しいライブラリやメジャーバージョン（例: Tailwind v4 / React 19 / Base UI / Hono / Zod 等）は、推測で書かず **`node_modules/` の実際の `.d.ts` 型定義** または **公式ドキュメントの Web 検索** で現行 API を確認する。
3. **GitHub Actions / 外部ツールの裏取り**: ワークフローや外部サービス設定を書くときは、古いメジャーバージョン（例: 旧 `actions/checkout@v3` 等）を惰性で書かず、最新の推奨アクション・バージョンを調べてから記述する。

## 3. 外部パターンのリサーチ（視野の狭い ADR を防ぐ）

構造判断・技術選定・新機能の設計で ADR（`<Decision>`）を書く前に、必ず外の知見を当てる。

1. **Web 検索で先行事例・業界標準・定番ライブラリを調査**し、頭の中の狭い 2 択で結論を急がない。
2. 最低 2〜3 案を比較したうえで、`<Decision id="dec.xxx" summary="...">` に `<Context>`・`<Chosen>`・`<Rejected option="...">`・`<Tradeoff>` を残す。
3. プロジェクト全体に関わる重い判断は独立 `docs/decisions/YYYY-MM-DD-<slug>.mdx`、機能固有の局所判断は該当 `design` / `spec` 内のインライン `<Decision>`（マイクロ ADR）に書く。

## 4. 暗黙の前提チェックリスト（曖昧なまま作らない）

人間にとって「当たり前すぎて言わなかった前提」を炙り出すため、以下の 7 軸で仕様の抜け漏れを点検し、**抜けていて影響が大きい項目だけ**を短い選択式で人間に確認する。

- **権限・セキュリティ**: 誰が実行できるか？非ローカル／未認証／ルート外パスはどう拒否するか？
- **空・異常・境界値**: 0 件・最大件数・不正入力・タイムアウト・ネットワーク断のときどう振る舞うか？
- **同時実行・冪等性**: 2 回連続実行・並列実行・途中失敗からの再実行で壊れないか？
- **データ寿命・削除・互換性**: 永続データの置き場所、削除時の挙動、既存データや設定への影響は？
- **既存機能・他マウントへの影響**: `documi impact <id>` で下流への波及を確認したか？
- **語彙の一貫性**: `domain` の `<TermDef>` と `antiTerms` に反する命名をしていないか？
- **やらないこと（Non-Goals）**: 今回あえて対象外にする範囲はどこか？

### 質問 vs とりあえず仮実装の切り分け（後戻りコスト基準）
- **重い曖昧さ（後戻りコスト高）** — データ構造・外部 API/CLI 契約・権限/セキュリティ・アーキテクチャ境界・Non-Goals → **実装前に必ず人間に質問して合意する**。
- **軽い曖昧さ（後戻りコスト低）** — デフォルト値・UI の細かい配置・表示文言・補助オプション等 → **合理的な仮案で「とりあえず実装」してよい**。ただし黙って確定仕様に混ぜず、必ず **`<Note intent="idea" title="仮置き: ...">`** または **`<Spec intent="idea">`** として明示し、PR 本文のレビュー観点にも記載する。
- `intent="idea"` ブロックは Web UI の Overview（「未確定の仮案・仮置き」）および `documi query --intent idea` に自動集約されるため、後から実物を見て確定・破棄できる。

### 過去の地雷・障害回避の保全（チェスタートンの柵）
- リファクタや既存設計の見直し時に、一見ムダ・遠回りに見える防御コードやワークアラウンドを見つけても、**理由が分からないまま削除しない**。まず `git log -S` / `git blame` と `documi search --context` で過去の経緯を確認する。
- バグ修正や地雷回避を実装したら、必ず **(1) コード直前に 1 行の Why-not コメント、(2) Red → Green の再現テスト、(3) 構造的な地雷なら該当 `design`/`spec` にインライン `<Decision>` ＋ `<Test>`** の 3 点セットを残す。

## 5. 入出力の具体例 ＋ `<SourceRef>` で仕様を確定する

仕様の解釈ブレをなくすため、実装に入る前に以下の 3 点セットを揃える。

1. **振る舞い (`<Spec>`)**: EARS 構文で観測可能な振る舞いと異常系を記述する。
2. **具体的な入力 → 出力 (`<Test verifies="..." level="unit|integration|e2e|contract|manual">`)**: 正常系・境界値・エラー系を宣言的な Given / When / Then で仕様のすぐ下に同居させる。
3. **実コード境界 (`<SourceRef>`)**: 公開型・関数シグネチャは手書きコピペせず、`<SourceRef file="..." symbol="..." />` または `mode="exports"` で実コードへ AST 接続する。
