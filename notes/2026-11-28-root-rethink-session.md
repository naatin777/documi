## 1. Root Goal の再検討（ほぼ完了）

- Goal の芯は確定済みと判断: **「目標がブレないこと」「AI Coding でイライラしないこと」**。ここはもう開かない。開くのは手段（means）だけ。
- 現行タイトル「人間が仕様と実装を把握し続けられる」は手段を目的に埋め込んでいる疑い。
- ユーザー回答（選択式）: **把握自体は目的の一部**（B）。把握の外でシステムが育つのは気持ち悪い。
- ただし把握の形: **常時全件把握は不要。必要時に素早く辿り着ければ実質把握と同等**（A 解釈）。
- **新しい最关键要件: 「一回は理解した」**。意味あるものごとに、人間が一度だけ本物の理解を通していること。一度通っていれば、あとは辿り着ければよい。
- 理解が最も安いのは**ものが生まれた瞬間**（会話の流れの中、1個ずつ）。後でのバッチレビューが最も高い。
- 承認の再定義仮説: 正しさの検証ではなく **「一回は理解した」の刻印**。
- システム規模は**大きいものがほしい**。総量上限の方向は却下。ただし理解イベントをすっ飛ばした増殖はしない。
- 理解を通っていないものは隠れず見えること（シラン機能問題）。

## 2. イライラ源泉リスト（6件）

1. **思った通りの実装をしない** — 意図と実装のズレ
2. **頭の中で完結してることを AI が知らない** — 暗黙前提。伝わっていると思ってしまう（※ 元の Root Goal 分析と一致）
3. **把握の外でシステムが育つ** — 理解を通っていない増殖（新規発見）
4. **同じズレが再発する** — チャットで直しても残らない（※ 元の分析と一致）
5. **それっぽい出力の検証コスト** — 合ってそうに見えるからスルーできず確認コストだけ重い（新規発見）
6. **AI 臭いノイズ・儀式的出力** — 情報を持たない儀式テキスト。例: CI で明らかなのに PR に「test完了」と書く（新規発見）

## 3. 本物の Target Actor 心理プロフィール

現行 Root Goal の「把握し判断する丁寧な開発者」はフィクション。本物:

- **完璧主義**: 全部ちゃんと揃ってないと納得いかない。欠点ではなく設計制約。対処は**完璧の範囲を小さく区切る**こと（到達可能な完璧）。
- **リセット願望**: AI coding 以前から存在。サイクル: 作る（楽しい）→ 動く（探索終了・退屈）→ 保守（楽しくない）→ 完璧主義が蓄積した汚れを許容できない → リセット。AI はこのサイクルを**加速かつ無糖化**した（AI が探索・生成の楽しい部分を食べ、人間に残るのはレビュー・検証・保守）。このサイクルで死ぬ仕組みは何を作っても同じ運命。
- **AI 臭さへの敏感さ**: 美的な好き嫌いではなく、正確に機能するノイズ検知器。
- **レビューしない・書かない・複数の AI ツールを使う・差分をざっと見て merge する**。これは怠慢ではなく人間の正常な仕様。システムはこれを前提に設計する。
- **無意識の企業的理想像**: 昔から頭にあり、消えない。対処は抑え込みではなく**境界のある仕事を与える**こと。完璧主義の担当区画 = 小さい公開面（README・見せる docs）。担当外 = 明示的に未完成が許可された領域。境界は目に見える形で。

## 4. 企業比較の分析

- 「企業の OSS は全部ちゃんと運用できてる」は**見た目**。生存者バイアス + 磨かれた公開面と汚い内部 + 原動力は組織の強制力（給料を払われた注意力、権限構造）。

- **逆転: 組織の強制力なしで品質を保てることが Documi の存在価値そのもの**。ユーザーの心理 = ターゲット市場。犬食いでつまずくのは正しいテストが機能している証拠。
- 正しい品質基準: 「個人が規律なしで続けられるか」。
- 盗んでよいもの: 軽量な CI ゲート、完璧範囲の限定、儀式を減らすこと。盗んではいけないもの: 「全部ちゃんとやる」という見た目の基準。

# Part 2: リリース運用・モチベーション・scope guard 方向の対話

> **これは何か**: 同日に続けて行われた対話の未加工キャプチャ。まだ仕様決定ではない。ただし Part 1 よりかなり具体的なプロダクト方向が見え始めている。蒸発させないために即時記録したもの。

## 1. 「ちゃんとした OSS」の正体の訂正

ユーザーが企業・OSS に感じていた「ちゃんとしている」は、全部を企業水準で運用することではなく、具体的には:

- リリースが区切られている
- 何がどう変更されたか追える
- PR のフォーマットが読める
- commit が読める

という **公開面の説明可能性** だった。

これは個人でも再現しやすく、完璧主義の担当区画にちょうどよい。中身全体を完璧にする必要はなく、公開面だけを小さく完璧にする。

現状の repo にはすでに器がかなりある:

- CI workflow がある
- tag `v*.*.*` で GitHub Release を作る release workflow がある
- PR template がある
- commit log はだいたい `feat:` / `fix:` / `docs:` / `chore:` になっている
- ただし tag はまだ 0 個
- `package.json` は `private: true` で npm 公開は未想定

つまり「ちゃんとした器はあるのに、最初のリリース運用が始まっていない」状態。

## 2. リリース方針の仮説

- **nightly は要らない**。意味のない日も出ると儀式化・ノイズ化する。外部テスターが毎日試す段階でもない。
- リリースは固定頻度ではなく、**意味あるまとまりごと**に切る。
- `CHANGELOG.md` は今は二重管理になるので作らない。GitHub Release を正準にする。
- PR title を正準化し、squash merge すれば generated notes で十分追える。人間は Highlights を 1〜3 行書くだけ。
- リリース条件は「完成度」ではなく **状態を正直に説明できること**。

alpha を積み上げる方向はあり。未完成でも、未完成であることを明示して出す。

- `v0.0.1-alpha` より `v0.1.0-alpha.0` がよいのではないか（現行 package version が `0.1.0` なため）
- 例: `v0.1.0-alpha.0` 初期スナップショット → `alpha.1` Root Goal / 人間モデル再設計 → `alpha.2` 最小ループ → `beta.0` README の手順が通る → `v0.1.0` 最小体験が end-to-end で通る
- alpha = 設計実験のスナップショット。仕様も CLI も変わり得る
- beta = README の最小導線は動くが粗い
- 0.1.0 = ひとつの意味あるユーザー体験が最初から最後まで通る

注意点: 現行 release workflow は `gh release create --generate-notes` だけで、`--prerelease` を付けていない。alpha tag が pre-release 扱いにならない可能性がある。

## 3. リリース前の積み上げ方

積み上げの単位は commit でも release でもなく **PR**。

```text
commit   = 作業ログ。多少汚くてもいい
PR       = 意味のある変更の単位。ここを一番綺麗にする
release  = 後から付ける区切り。進捗の単位ではない
```

リリース前の開発ループ仮説:

1. 1 PR で変えることを 1 つだけ決める
2. 先に「何ができたら完了か」を 1〜3 行書く
3. code / test / docs を同じ PR に入れる
4. CI が緑なら merge してよい
5. squash merge して、PR title を main の履歴に残す

重要ルール:

- 「docs はあとで」を禁止。影響がないなら「影響なし」と明記し、あるなら同じ PR に入れる
- PR title が 1 文で書けないなら、その PR は大きすぎる
- milestone は 1 個だけ。例えば `v0.1.0-alpha.0`。完了条件を小さく決め、完璧主義の対象をそこに閉じ込める
- issue は必須ではない。issue 債務を作らない

## 4. モチベーション管理の分析

ユーザー問い: 「こういうモチベみたいなものってみんなどう管理してるんだろう？」

結論: **みんなモチベーションを直接管理できていない**。多くは外部構造に乗っている。

- 会社: 給料・締切・同僚・責任という外部強制
- OSS メンテナ: ユーザー・issue・reputation・コミュニティ。burnout も多い
- 個人開発: 新奇性・衝動・小さい完成。飽きたら止めるのが普通

モチベーションは意志で維持するものではなく、だいたい次で決まる:

```text
見える進捗
+ 意味がある感覚
+ 小さく終わるスコープ
+ 誰か・何かからの反応
- 溜まった汚れ・借金
```

AI coding 特有の問題: AI に全部書かせると人間の役割がレビュー・検証・修正指示・差分確認になり、**検査官と債務管理者**化する。これはつまらない。モチベ維持には人間が「何を作るか」「どうあるべきか」「何が気持ち悪いか」「設計の芯」「公開面の品質」を握り続ける必要がある。

最重要原則:

> **モチベーションを維持しようとしない。切れても復帰できる状態を作る。**

個人開発は波があるのが普通。目標は「毎日やる」ではなく、**2週間空いても10分で状態と次にやることを思い出せる**こと。

alpha tag / milestone は公開のためだけではなく、区切り・達成感・無限に伸びない「途中」・自分の歩みの可視化という意味でも効く。

## 5. プロダクトの立ち位置探索

最初の問い: Documi の核は何か。選択肢は「思い出す装置」「ズレを防ぐ装置」「仕様の正典」「AI作業の監督」。

次に「どの瞬間に一番役に立ってほしいか」を選択式で確認。ユーザー回答:

> 全部ではあるんだけど、大本をたどると **B（作業中の逸脱検知）** かな？

整理:

```text
作業前のズレ防止  → 逸脱を減らす前処理
作業中の逸脱検知  → 大本。まだ修正できるうちにズレを見つける
作業後の理解      → 検知しきれなかったものの事後処理
再開時の把握      → 溜まった逸脱・途中状態の復旧
```

つまり全部必要だが、原因に一番近い介入点は **作業中**。

仮説としての Documi:

> **AI が人間の意図から外れ始めたことに、まだ修正可能なタイミングで気付けるようにするもの**

さらに分解すると:

```text
最小限の意図を引き出す
→ AI の作業が逸脱し始めたら検知する
→ 人間が短時間で判断・理解する
→ その修正知識を残す
→ 次回以降の再発を防ぐ
```

## 6. 逸脱検知後の反応

ユーザー回答のニュアンス:

> 全部その場で確認したいところだけど、今の時代的には D（程度に応じて変える）か A（危険なものだけ止める）かなあ？

ここで完璧主義と持続可能性が衝突している。理想は全部確認だが、全部確認したら続かない。

提案された原則:

> **最終形は D、初期形は A。**

理由: 今の AI に「程度に応じて」判断させると、リスク判定自体が AI 臭くて信用できない。最初は賢い判定ではなく、**機械的で説明可能なルールだけ止める**。

## 7. 停止条件

ユーザーは以下の全部を停止対象に選んだ:

- 指定外の範囲を触る
- 重要な契約を変える
- 依存や基盤を変える
- 破壊的操作をする

ただし解釈として重要なのは、常に止めることではなく:

> **事前に許可された範囲なら止めない。許可がないときだけ止める。**

理想:

```text
作業前に許可範囲を作る
→ 許可範囲内では自由にやらせる
→ 範囲外に出た瞬間だけ止める
```

ここからプロダクト像が大きく変わった:

> **Documi は AI coding の“作業許可範囲”を管理し、そこから外れた瞬間に人間へ判断を返すもの**

つまり、仕様管理システムというより **AI coding の permission system / scope guard**。

specs/docs は目的そのものではなく、なぜその範囲が許可されたか、過去にどんな逸脱があったか、どの修正を繰り返したくないかを覚える裏側になる。

## 8. 許可範囲の作り方

ユーザー回答:

> **AI が docs から自動推定して人間が承認？**

このハイブリッドでほぼ全ピースが繋がった。

見えてきたコアループ:

```text
曖昧な依頼
  ↓
AI が docs / code / 会話から影響範囲を推定
  ↓
「今回触る範囲」「触らない範囲」「危険な変更」を小さく提示
  ↓
人間が 1 回理解して承認 or 修正
  ↓
AI は許可範囲内で自由に作業
  ↓
範囲外に出たら止める or 確認
  ↓
人間の修正・判断を docs / memory に残す
```

ここで承認の意味が変わる:

- 旧: 「この仕様の正しさを人間が検証した」
- 新: **「この作業の意図と範囲を、人間が一回理解した」**

これは Part 1 の「一回は理解したい」と一致する。バッチレビューではなく、作業が生まれる瞬間に1回だけ理解する。

docs の立ち位置も変わる。docs は人間が常に読む正典ではなく、**AI が作業範囲・意図・過去の判断を推定するための記憶**。人間は docs 全部を読まず、AI が小さい承認カードだけを出す。

既存資産の意味づけも変わる:

- `<Spec>`: 正典ではなく意図推定の材料
- `<Decision>`: なぜその範囲を触っていい/いけないかの根拠
- `<SourceRef>`: 影響範囲推定の材料
- `documi check`: 債務取立てではなく逸脱・不整合・古さの検知
- review / approval: 仕様のバッチ承認ではなく作業許可の承認

プロダクトの一文候補:

> **AI に仕事を任せるとき、人間の意図と許可範囲を作り、そこから外れた瞬間に止めるもの**

## 9. 承認カードの初期案

人間が承認するカードに出す候補:

1. 今回の目的 / 完了条件
2. 触る予定の範囲
3. 触らない範囲
4. 重要契約・依存・基盤への影響
5. AI が不確かだと思っている点

ユーザーは **特に 1（目的 / 完了条件）** に強く反応した。

重要な関連原理:

> **完了条件の質が、人間のコード閲読量を決める。**

完了条件が具体的なら、コードを全部読まなくても結果を確かめられる。曖昧だと、何をされたか判断するためにコードを読むしかない。

## 10. docs 推定がズレる懸念とソースコード問題

ユーザー懸念:

> AI が docs から自動推定すると、だんだんズレてってる感じがしそう。やっぱり人間もソースコード見るべき？

この懸念は正しい。docs だけを正典にすると確実にズレる。

真実は 1 箇所にない:

```text
人間の意図      → 会話 / docs / Decision
実際の振る舞い  → source code / test / runtime
変更の履歴      → git / PR / release
```

Documi の仕事はどれか 1 つを正典にすることではなく、**この 3 つがズレたことを検知し、人間が判断できる形にすること**。

人間はソースコードを見るべきか:

- 全部は見るべきではない。それだと人間がレビュアーに戻り、続かない
- ただし重要な断面では見るべき
  - コアな抽象が初めて生まれたとき
  - 外部契約や公開 API が変わるとき
  - AI の説明と code が食い違うとき
  - 動作はするが設計思想に合うか分からないとき
  - テストでは表現しにくい構造の変更

原則:

> **人間は意味を判断し、機械は挙動を検証し、コードは証拠として見る。**

コードは最初から読むものではなく、疑わしいとき・重要なときに辿るもの。

承認カードは AI の説明を読む場所ではなく、**証拠への入り口**であるべき。AI が「大丈夫です」と言うだけの AI 臭い出力を防ぐため、根拠と不一致を出す。

ズレの修正タイミング:

> **その領域に触れたときだけ、その領域のズレを直す。**

触っていない古い部分は多少ズレていてもよい。眠っているズレは起きるまで放置。全体監査の債務を作らない。

## 11. 一気にやろうとする問題

ユーザー:

> 一気にやろうとしちゃうからどうしても AI の作業量が多くて

これは AI だけの問題ではなく、人間側も途中で追加する。悪いのは思いつくことではなく、**その拡大が無意識に同じ作業へ吸収されること**。

重要原則:

> **AI の作業単位は、AI がこなせる量ではなく、人間が一回で理解できる量に制限する。**

「一回は理解したい」が目的なら、作業の上限は生産性ではなく人間の理解 bandwidth で決める。

必要なのは分割ゲート:

```text
依頼を受ける
→ AI が docs/code から影響範囲を推定
→ 大きい場合は勝手に始めず分割案を出す
→ 人間は Now / Next / Later から Now だけ選ぶ
→ Now だけ許可範囲を作る
```

例:

```text
Now:   Signal を query で検索できるようにする
Next:  editor で Signal 属性を編集できるようにする
Later: CLI/MCP へ公開し docs を同期する
```

途中追加の扱い。人間が途中で思いつくのは自然なので禁止しないが、AI は明示すべき:

> 「editor 対応は現在の許可範囲外です。今回の作業に拡張しますか？ それとも次のタスクに分けますか？」

目的はスコープ拡大を禁止することではない:

> **無意識なスコープ拡大をなくすこと。**

拡大してもよい。ただし、その瞬間に人間が理解して選ぶ。

作業量の上限は行数だけでは分からない。1000 行の機械的変更は軽く、20 行の意味変更は重いことがある。見るべきもの:

- いくつの意味ある振る舞いが変わるか
- いくつの capability / layer にまたがるか
- 外部契約を変えるか
- docs / test / code の同期が必要か
- 人間が理解すべき新概念がいくつあるか

初期は賢すぎる判定をせず、荒いトリップワイヤでよい。例: 2つ以上の capability、複数境界、新概念2つ以上、完了条件が3つより多い、などで分割案を出す。

## 12. 人間と AI の共有キュー

ユーザー:

> 色々やりたいことが出てきて今教えないと忘れちゃうから全部書いちゃう。分割してキューとかで一個ずつ読み込むべき。TodoList 大事かも、人間と AI の。

これは重要。ただし必要なのは単純な TodoList ではなく **2層の箱**。

> **忘れないための箱**と、**今やる箱**は分ける。

問題は「書いたら全部やる対象になる」こと。思いつきを書くのは自然だが、AI から見ると全部タスクに見える。するとスコープが広がる。

必要な構造:

```text
Inbox
  思いついたものを全部入れる。実行義務なし。

Next
  近いうちにやるかもしれないもの。少ない。

Active
  今やっているもの。1個だけ。

Done
  完了したもの。証拠や PR へのリンク付き。

Parked / Dropped
  やらないと決めたもの。理由付き。
```

重要: **Inbox は Todo ではない**。忘れないための記憶であって、いつか必ずやる借金ではない。ここを分けないと 99 件レビュー債務と同じ構造が再発する。

AI 用チェックリストとも分ける:

- **AI の実行チェックリスト**: 今の作業を完了するための短命な手順
- **人間と AI の共有キュー**: プロジェクトの意図やアイデアを持ち越す永続的なもの

さらに Todo の種類を分ける:

```text
build:       実装するもの
decide:      人間が決めるもの
investigate: 調べるもの・理解するもの
```

これを区別しないと、AI は相談事項まで勝手に実装し始める。

理想の AI の反応例:

> 「今出た 5 件は Inbox に入れました。現在の Active は『Signal を query 対応する』のまま進めます。このうち『editor 対応』だけ関連が強いので Next 候補にします。」

Documi は汎用タスク管理ツールにはならない。目的はタスク管理そのものではなく:

- 思いつきを消さない
- でも勝手に実行させない
- Active を 1 個に保つ
- 人間が戻ったときに再開できる

かなり重要な一文:

> **書き出すことは解放であって、約束ではない。**

人間と AI の共有キューは Documi の中心機能候補。

## 2. Permission / guardrail の業界パターン

### 2.1 技術的 boundary と approval は分離されている

Codex が分かりやすい:

- sandbox mode: 何が技術的にできるか。どこに書けるか、network に出られるか
- approval policy: いつ人間に停止して確認するか

この 2 層は別物。Claude Code / Kiro も同じ方向。つまり「止めるかどうか」だけではなく、「そもそも到達できない範囲」を作る発想が標準化しつつある。

Documi への示唆:

- scope guard は「確認ダイアログ」だけで設計してはいけない
- technical boundary（触れる場所・実行できる操作）と semantic boundary（今回の意図・capability・契約）は分ける
- 既存ツールは technical boundary が中心。semantic boundary はまだ弱い。ここに Documi の独自性がありそう

### 2.2 deny / ask / allow + evaluate / classifier の方向

各ツールの共通パターン:

- deterministic な deny / ask / allow が基礎
- その上に classifier / analyzer / evaluate がある
- deny は最強で、classifier や bypass より優先されることが多い

例:

- Claude Code: hooks → deny rules → ask rules → allow rules。`default` / `acceptEdits` / `plan` / `auto` / `dontAsk` / `bypassPermissions`。deny は bypass でも効く。critical path 削除などは auto-approve しない領域がある
- Kiro: capability (`fs_read`, `fs_write`, `shell`, `web_fetch`, `mcp` 等) ごとに `deny` / `ask` / `allow` / `evaluate`。priority は `deny > ask > allow > evaluate`
- OpenHands: `AlwaysConfirm` / `NeverConfirm` / `ConfirmRisky`。`ConfirmRisky` は security analyzer 依存
- Codex: sandbox + approval policy + automatic approval reviewer

Documi への示唆:

- 「最終形 D、初期形 A」の仮説は業界方向と一致する
- ただし最初から AI に曖昧な risk judging をさせる必要はない。まず deterministic rule を優先すべきという裏付けになる
- evaluate / classifier は補助であって、hard boundary の代替ではない

### 2.3 plan mode / read-only mode が標準化しつつある

Kiro Plan mode はかなり今回の論点に近い:

- file reading / code intelligence / search / web search はできる
- file writing / command execution / MCP tools はできない
- structured questions → codebase exploration → implementation plan → 承認後 execution handoff

Claude Code にも plan mode があり、探索と変更を分ける。

Documi への示唆:

- 「実装は opt-in」「相談時は read-only」は業界標準方向と一致している
- ただし既存 plan mode は「計画してから実装する」ためのもので、相談 / decide / investigate / capture の分類までは十分ではない
- Documi は task type routing をより明確にできる可能性がある

### 2.4 hooks は検知・注入・ blocking の共通基盤

Claude / Kiro とも hooks があり、少なくとも以下ができる:

- PreToolUse / PermissionRequest / PostToolUse / PromptSubmit / FileSave 等のイベント
- shell command の stdout を agent context に入れる
- error / deny によって tool invocation や prompt submit を止める
- deterministic command と agent prompt action を使い分ける

Documi への示唆:

- 以前の仮説「検知はハード、解決はソフト、hook 出力は AI への伝達チャネル」はかなり業界実装と一致している
- repo / agent runtime 層に置くべきものは instructions だけではない。hooks / permission rules / sandbox が必要

## 3. Spec-driven development の業界パターン

### 3.1 Kiro Specs

基本は 3 ファイル / 3 フェーズ:

- requirements.md — user stories / acceptance criteria / EARS
- design.md — architecture / sequence diagrams / error handling / testing strategy
- tasks.md — discrete trackable tasks

Feature Spec は各フェーズで review する。Quick Spec は well-understood feature 向けに、前段で clarifying questions に答え、approval gates を外して一括生成する。

Kiro Plan mode は formal docs を作らない軽い計画モード。

示唆:

- フルワークフローと軽量ワークフローを分けるのは必須
- すべての作業に requirements/design/tasks は重すぎる
- quick / plan / full spec のようなサイズ別ルートは必要

### 3.2 GitHub Spec Kit

基本フロー:

```text
constitution
→ specify
→ clarify
→ plan
→ checklist
→ tasks
→ analyze
→ implement
→ converge
```

ただし小さい機能向けには短縮パスがある:

```text
specify → plan → tasks → implement → converge
```

重要な点:

- `clarify` は ambiguity を実装前に質問で潰す
- `checklist` は requirements quality の reviewer-owned checklist
- `analyze` は spec / plan / tasks の矛盾を read-only で確認する
- `implement` は unchecked checklist があると確認する
- `converge` は codebase と spec/plan/tasks の gap を見て、不足があれば tasks を追加する

既存プロジェクト導入ガイドでは:

- 既存システム全体を再仕様化しない
- bounded first change を選ぶ
- spec は「既存全体の retroactive spec」ではなく「今回変更するもの」を定義する

complex features では:

- 一度に全部 implement せず、task range / phase で止める
- sub-agent に分割する
- 大きすぎる場合は小さい spec に分解する

idea assessment extension では:

- intake → research → define → shape → decide
- verdict は `go` / `needs-clarification` / `kill`
- source code は変更しない
- stopping is a successful outcome
- assessment は standalone で、自動的に SDD / implementation へ進まない

示唆:

- Spec Kit 自身も、重いフローを全件適用しない方向へ動いている
- 「bounded change」「task range で止める」「assessment は implementation に自動接続しない」は Documi の方向とかなり一致
- 特に idea assessment は build / decide / investigate / capture の分離に近い

## 4. 批判・実践上の失敗

### 4.1 Thoughtworks / Birgitta Böckeler の観察

重要な批判:

- **one workflow does not fit all sizes**。小さい bug に重い workflow は sledgehammer。problem size/type に応じた複数 workflow が必要
- **reviewing markdown over reviewing code**。spec-kit は大量の markdown を生み、冗長でレビューがつらい。場合によってはコードレビューのほうがマシ
- **false sense of control**。大量の instruction があっても agent は無視したり、過剰に従いすぎたりする。small iterative steps が依然重要
- functional spec と technical spec の分離は難しい
- spec-anchored / spec-as-source は MDD（model-driven development）の失敗と類似の危険がある。柔軟性低下と LLM の非決定性の両方の欠点を持つ可能性
- spec-first の一般原則は有用だが、重い SDD ツールは Verschlimmbesserung（直そうとして悪化）になり得る

### 4.2 arXiv 2608.25202v5 の empirical findings

Abstract / findings から重要なもの:

- practitioners は specs が intent capture に有用だと感じている
- specs は agent work を more reliable にする報告が多い
- ただし planning / review cost は増える
- spec drafting with agent は intent clarification に役立つ
- SDD は token/time/cognitive load を implementation から planning に移す
- agents departed from specs during implementation（implementation drift）
- specs went stale as code changed（spec decay）
- evaluation effort grows with the system and outgrows human ability to review
- individual benefits may come from clarifying intent before delegation
- team benefits may depend on SDD becoming a shared process
- participants described spec-code checks mainly when changes are completed rather than over time

## 5. Documi への示唆

### 5.1 重い spec-driven development の clone は作らない

市場にはすでに重い SDD がある。しかも批判も強い。大量 markdown を生成して人間にレビューさせる方向は、ユーザーの心理とも一致しない。

Documi の差別化は「ちゃんとした spec を書くこと」ではなく:

- 人間が決められる状態を作る
- 小さい意図を引き出す
- 作業範囲を限定する
- 逸脱を検知する
- 判断を残す

にあるべき。

### 5.2 spec-first は有効。ただし spec-anchored/spec-as-source は慎重

外部調査でも spec-first の価値は確認できる。特に intent clarification は個人に効く。ただし、spec を永久的な正典として維持する方向は drift/decay/review overload が起きる。

Documi は specs を正典として崇めるのではなく、意図推定とズレ検知の材料にする方向が妥当。

### 5.3 デフォルトは read-only / no implementation

Kiro Plan mode や Spec Kit assessment と同様に、相談・調査・意思決定では source を変更しないのが自然。

Documi のデフォルトは:

> 実装は opt-in。曖昧なら実装しない。

これは外部パターンとも一致する。

### 5.4 hard rules と classifier は分ける

業界は deterministic permission rules + classifier/evaluate の hybrid に進んでいる。Documi も最初は deterministic な deny/ask/allow を優先し、AI による risk judging は advisory layer に限定するのがよさそう。

### 5.5 小さい bounded run は必須

Spec Kit ですら long implementation run の劣化を認め、task range / phase / sub-agent / smaller specs に分けることを推奨している。Documi の「人間が一回で理解できる量に制限する」は、model context 制約とは別の人間側理由を持つ stronger principle になり得る。

### 5.6 semantic scope guard が空白かもしれない

既存 permission system は filesystem / shell / network / MCP / command の制御が中心。一方で今回の痛みは:

- 相談を実装と誤分類する
- 無関係な capability に広げる
- docs/test sync を忘れる
- 暗黙前提を無視する
- 意図していない契約変更をする

といった semantic / workflow level の逸脱。ここは既存ツールが十分に解けていない領域に見える。

### 5.7 rejection feedback は重要

OpenHands は rejection 時に理由を渡して agent が safer approach を探せるようにしている。Documi でも、人間が止めた理由・修正した意図を単なるログではなく今後の制約として残す価値がある。

## 6. 現時点の仮結論

外部調査を踏まえると、Documi の方向はかなり支持される。ただし条件付き:

- spec-heavy な文書生成システムにしない
- workflow はサイズ別に分ける
- 初期は deterministic guardrails + read-only planning
- specs は正典ではなく memory/evidence
- semantic scope guard と intent classification に焦点を絞る

特に重要な外部裏付け:

1. **spec-first / intent clarification には価値がある**
2. **spec は drift/decay する**
3. **review overload は実際に起きている**
4. **plan/read-only mode は既に有効なパターン**
5. **deterministic permission + classifier/evaluate の hybrid が業界方向**
6. **assessment/decision を implementation から分離する事例がある**

## 16. human/AI 別形式ではなく single source + projection

ユーザー提案:

> `<AI only>` とか `<Human only>` とか作るべきかしら。人間が見て良い形式と AI が見て良い形式は違う。

この問題意識は正しい。AI に必要なものと人間に必要なものは違う。

- AI: 正確な制約、詳細な分岐、schema、edge case、過去の decision、禁止事項、冗長でも機械的に参照できる情報
- 人間: 何が変わるのか、何を決めればいいのか、どこが危ないのか、どこが不確かなのか、根拠はどこか

ただし `<Human only>` は危険。人間の頭にあるのに AI が知らない、という本来解決したい問題を悪化させる。`<AI only>` も、AI への指示が人間から完全に隠れると監査しにくい。

提案された修正:

```text
shared:
  人間にも AI にも見せる。意図・制約・契約・決定

human-primary:
  主に人間向け。説明・背景・例・読み方。AI も読める

agent-primary:
  主に AI 向け。詳細手順・機械的制約・冗長な文脈。人間も開ける
```

重要原則:

> **情報は1回だけ書く。見せ方は複数あっていい。**

人間用と AI 用を別ファイルにすると、その 2 つがズレる。spec drift を増やす。そうではなく、1 つの構造化された記憶から複数投影する:

```text
1つの構造化された記憶
  ├─ AI projection: 詳細・正確・機械向け
  └─ human projection: 要約・判断点・差分・証拠
```

Documi の MDX は単なる文章ではなく構造化ブロックなので、人間に MDX をそのまま読ませる必要はない。MDX は構造化された記憶・中間表現、UI は人間向けに投影された判断画面、AI は構造を直接読む、という分離ができる。

人間画面の初期表示候補:

- 今回の目的 / 完了条件
- 変わるもの
- 変わらないもの
- 危ないもの
- 不確かなもの
- 人間が決めるもの
- 証拠リンク

残りは畳むが潜れる。これなら人間は全部読まなくてよく、AI は全部読め、隠し事もない。

評価:

- `<AI only>` / `<Human only>` を単純導入: 危険
- `agent-primary` / `human-primary` / `shared`: かなり良い
- AI用・人間用を別ファイルに分ける: ズレるので弱い
- 1つの構造化ソースから複数投影する: かなり強い

差別化仮説:

> **spec-kit が大量 Markdown を人間に読ませるのに対して、Documi は同じ情報を人間と AI に違う形で投影する。**

## 17. antigravity 蒸発事件のシミュレーション結果

ユーザー記憶:

> たくさん調べてくれて、ちゃんと的確な答えを出してくれたような気がした。構造とか7分割とか。

内容を正確には覚えていない。この「覚えていない」こと自体が事件の核心。

復元:

```text
入力:
  構造や7分類についての相談

AI output:
  調査されていて、それっぽく、的確に見える大きな回答

その場の感覚:
  良さそう。納得できそう

結果:
  内容は残っていない
  採用したのかどうかも曖昧
  後から「そもそもこの形式でいいのか？」が残る
```

これは悪い回答だったというより、**回答が人間の理解イベントと永続状態に変換されなかった**事件。

Signal 事件との対称性:

- Signal 事件: AI が勝手に世界を変えた。実体は変わったのに、人間の理解と承認がなかった
- antigravity 事件: AI は良さそうな思考を出した。でも人間の理解と承認がないまま、永続状態にもならなかった

共通の根:

> **会話の出力と、人間の理解・意思決定・永続状態が接続されていない。**

片方は無許可に状態変更し、もう片方は有益な思考が蒸発する。

ユーザー回答（回答後の理想）:

> D以外全部。ただし一気に承認じゃなくて一個一個のほうが良かったかも。それこそちゃんとPRとかで分割して。

ここ重要。理想的には、大量回答のあとに:

- 採否を決める
- 小さい実験に落とす
- 有力仮説として保存する

の全部があり得るが、**一括承認はしない**。大きな提案を独立して判断できる粒に分解し、1個ずつ進める。

導かれた pipeline:

```text
大きな回答
→ 判断単位 / decision atoms に分解
→ Inbox / Next に入れる
→ Active を 1 個だけ選ぶ
→ 小さい実験または PR にする
→ 結果と判断を memory に残す
```

重要原則:

> **大きな提案はそのまま承認しない。まず独立して判断できる粒に砕く。**

7分類のような構造提案も、全部を一括採用するのではなく、独立した仮説や変更単位に分けて試すべきだった。AI の出力は evidence であって、自動的な仕様決定ではない。

## 18. 99件レビュー債務の root hypothesis と質問 UX

ユーザー回答（99件事件の失敗）:

> ちょっとずつやらなかったこと。レビューもやるのがめんどかった。ブラウザを自動で開くとか、AIが人間承認をちゃんと確認するとかもあり得るが、そういうやり方もありふれていて根本ではない気がする。

整理:

- cap / notification / auto-open / AI による承認確認は対症療法であって root fix ではない
- 「ちょっとずつやらなかった」は原因というより結果
- root hypothesis: **レビューが、今の作業と切り離されたバッチ検証だったこと**
- レビューが「未来の品質のための義務」だったため、宿題化した

重要な対比:

```text
悪い方:
  昨日生成された 20 件の仕様をレビューしてください

良い方:
  この作業を進めるには、A と B のどちらにするか決める必要があります
```

つまり、承認は品質管理の儀式ではなく、**AI が次へ進むために必要な作業分岐**であるべき。レビュー依頼ではなく、進行に必要な判断依頼に変換する。

cap / UI / notification の位置づけ:

- cap: 債務の無限増殖を止める保険。根本治療ではない
- auto-open / notification: トリガー。根本治療ではない
- review UI: 摩擦を下げる補助。根本治療ではない
- root fix: レビューを後回しの検証ではなく、作業中の判断に変える

追加された重要な UX 要件（ユーザー）:

> AI が質問してくる場合も文章だからめんどくさい部分があるとすぐにだめになる。もうちょっと視覚化とか、すぐに質問の質問できる環境じゃないと。今の AI の ask user って質問の質問できない。

これはかなり重要。問題は選択式か文章かだけではない。ユーザーが質問の意味・選択肢の差・根拠を理解できないとき、気軽に深掘りできないと回答コストが跳ね上がる。

導かれる要件:

- 質問は文章だけでなく、必要に応じて図・差分・比較表・具体例で見せる
- 選択式ファースト、自由記述は逃げ道
- 「質問の質問」を低コストでできること
  - 「選択肢の違いを見せて」
  - 「具体例を出して」
  - 「影響範囲を見せて」
  - 「なぜこの質問が必要なの？」
- 質問と回答はチャットに埋もれさせず、判断オブジェクトに紐付ける
- 判断オブジェクトは後から再開できる状態を持つ
- ユーザーに長文を書かせない。選択・編集・ワンクリック深掘りを優先する

これは human projection UI の核心要件でもある。単なる Markdown viewer ではなく、人間が判断できるインタラクティブな decision environment が必要。

## 19. トレードオフ提示と「おすすめ」依存の危険

ユーザー追加:

> ちゃんとトレードオフを見せてほしい。めんどくさい時はおすすめを選んでしまう。判断材料が少ないから「いいや」になってしまう。

これは judgment UX の中心問題。回答コストだけを下げると、人間は理解したのではなく AI の推奨を rubber-stamp するようになる。

問題構造:

```text
判断材料が少ない
→ 比較できない
→ 面倒になる
→ おすすめを選ぶ
→ 「一回は理解した」が成立しない
→ 後で違和感やズレが残る
```

重要原則候補:

> **おすすめは答えではなく、検証すべき仮説。**

トレードオフは ceremonial な pros/cons ではなく、その判断固有の比較軸で示す必要がある。例:

- 何を得るか
- 何を失うか / 何が重くなるか
- 間違っていたときの被害
- 後戻りしやすさ
- 不確かなこと
- なぜ他案ではないか

UI 示唆:

- recommendation を初期選択しない
- recommendation は中立的な比較の後に示す
- AI の confidence / uncertainty を分ける
- 低リスクで可逆なら推奨に乗ってもよい
- 高リスク・不可逆・広範囲なら、比較を開かないと選べないくらいの摩擦があってよい
- ただし全件に重い確認を要求するとまた死ぬので、リスク連動にする

設計上の緊張:

- 回答コストを下げすぎると rubber-stamp になる
- 情報を増やしすぎると読まれずに死ぬ
- だから初期表示は小さく、必要な比較軸だけを出し、深掘りは progressive disclosure にする

## 20. Design Maybe / 仮置き設計点の概念

ユーザー:

> decision が増殖してもいいとは思う。でも decision にも色んな種類がある。AIがある程度埋めて、あとからAIが個々の部分の設計を詰めていきましょうか、みたいな。設計の maybe みたいなものでメモして。重要そうなら即。

これは重要な中間層。全部を人間に聞くわけではなく、AI が低リスクな部分を仮に埋め、それを明示的に `maybe` として保持する。

重要原則:

> **悪いのは AI が埋めることではなく、埋めたことが見えないこと。**

黙って埋められた前提はズレの原因になる。しかし visible な仮置きなら、作業速度を保ちながら後で修正できる。

概念整理:

```text
decision:
  人間が選ばないと進まないもの。高影響・後戻りコスト大。

maybe / assumption:
  AI が暫定的に埋めた設計点。人間承認ではない。visible で reversible。
  後で影響が大きくなったり矛盾したら decision に昇格する。

question / unknown:
  AI が分からないもの。調査または人間入力が必要。

risk:
  異常系・落とし穴・後で痛くなるもの。

idea:
  まだ採用しない設計候補・思いつき。
```

maybe のライフサイクル候補:

```text
AI が低リスクな設計点を暫定で埋める
→ maybe として記録する
→ 実装や設計が進む
→ 関連領域に触れた / 影響が大きいと判明 / 矛盾が出た
→ decision に昇格して人間に聞く
→ 決定後は Decision または確定仕様に反映
```

昇格トリガー候補:

- 外部契約・データ構造・セキュリティ・永続化に影響する
- 新情報と矛盾した
- 人間が関連領域に触れた
- 実装がその境界に到達した
- confidence が低いのに impact が高い

既存の `intent="idea"` 仮置き概念に近い。ただし現行は静的な仮置きに留まり、運用・昇格・質問化・人間への提示が弱かった可能性がある。

これにより、「頻繁に拾いたい」要求と「全部その場で聞くと死ぬ」問題を分離できる:

> **頻繁なのは capture。人間への即問いは重要なものだけ。低リスクなものは maybe として visible に仮置きする。**

## 21. 仕様は実装の写しではなく、安定した意味だけを書く

ユーザー:

> 大きい単位は全部書くんじゃなくて SourceRef で参照したほうが良いのでは。細かいところは SourceRef で。

これは重要な方向。仕様が実装詳細を大量に複写すると、更新コストが増え、spec-heavy になり、結局誰も読まない。変わりやすい実装事実は `<SourceRef>` やテストへ寄せるべき。

ただし「全部 SourceRef」には危険がある。SourceRef は実装位置や型・ export などの事実には強いが、以下を直接は表せない:

- なぜそうするのか
- 何を変えてはいけないのか
- 実装が変わっても維持すべき振る舞い
- 外部契約としての意味
- トレードオフ・却下案
- 複数関数やモジュールをまたぐ振る舞い
- コードが正しく実装しているかどうか以前の、意図の正しさ

暫定原則:

> **変わらない意味は書く。変わりやすい事実は参照する。**

書くべきもの:

- intent / goal
- 外部から見える振る舞い
- 安定した契約
- 制約・Non-Goals
- 後戻りコストの高い decision
- 人間が判断すべき差分と影響

SourceRef / test に寄せるもの:

- 型・関数シグネチャ・ export
- 実装入口・責務境界
- 細かい分岐や実装都合
- 具体入出力・異常系の再現
- 現在のコード事実

つまり仕様は実装の鏡ではない。実装が変わっても残る意味を最小限書き、現在の正確さは SourceRef と test で検証可能にする。人間向け UI は SourceRef から必要部分を投影し、生コードを読ませすぎないようにする。

## 22. SourceRef はリンクではなく authority delegation になりうる

ユーザー:

> 実装を全部仕様にしない。内部実装まで全部仕様化すると重い。そこは SourceRef で、もうソースコードが仕様みたいにすれば良いのでは。

既存 docs にも近い原則がある。`authoring-guide` は公開境界シンボルを手書きコピペせず `<SourceRef mode="exports">` 等で AST 紐づけし、非公開ヘルパーや関数内部の `if`/`for` 手順は書かずコードとテストに任せるとしている。また `source-ref-outside-design` ヒントは、ソース参照を `design` に閉じ、spec/contract は振る舞いと test に結合する方向を示している。

ここでの新しい強い解釈:

> **`<SourceRef>` は単なる参照リンクではなく、「この詳細の正典はコードである」という authority delegation にできる。**

つまり内部実装の詳細については、コード自体を詳細仕様として扱う。docs はその複写ではなく、どのコードが正典かを示す。

権威の分担候補:

```text
spec / contract:
  外部から見える振る舞い、維持すべき意味、拒否条件、優先順位

design:
  モジュール境界、データフロー、副作用分離、現在の構造地図

code:
  内部実装詳細の正典。非公開ヘルパー、分岐、一時的な手順

test:
  具体入出力、異常系、観測可能な振る舞いの実行可能な証拠

decision:
  なぜそうしたか、却下案、トレードオフ、地雷回避理由
```

ただしコードを正典にできる条件がある:

- 安定した `symbol` / `exports` で参照できる（行番号依存にしない）
- 名前・型・構造がある程度読める
- 振る舞いがローカルに閉じている
- 非自明な不変条件・権限・順序・失敗意味は別途書く
- テストまたは具体例で観測可能性を補う
- UI が人間に生コード全体ではなく必要部分を投影できる

重要なのは、SourceRef に役割を持たせること。少なくとも:

```text
evidence:
  主張の裏付けとして参照する

authority:
  この詳細の正典は参照先コードである

example / test:
  実行可能な例や検証として参照する
```

この区別がないと、「参考リンク」なのか「ここが仕様」なのか分からず、AI も人間も扱いを間違える。

## 23. 共通言語は「入力は寛容、出力は正典」にする

ユーザー:

> コードはそのまま動くものだから判断がない。最大級の仕様。関数名やクラス名を docs でも使い回して共通言語にしたい。共通言語がいろんな表現で書かれているのがイライラする。

既存 docs には既に近い設計がある。`<TermDef>` は `symbols` でコードシンボルと対応し、`aliases` で検索同義語を持ち、`antiTerms` で禁止語を示す。authoring-guide には「1 概念 = 1 正準表記」「aliases は検索専用」「本文中は正準 ID の 1 表記で統一」と明記されている。

つまり問題は概念の欠如ではなく、**運用・生成時に正典表記へ正規化されないこと**にある。

強い原則候補:

> **入力は寛容に、出力は正確に。**

- 入力・検索・会話では aliases や揺れた表現を受け付ける
- 解釈時には正準 Term / code symbol に解決する
- AI が生成する docs・判断カード・質問・要約では正準表記だけを使う
- 禁止語や混同語は normative 文書で検出する
- UI は正準用語を表示しつつ、別名からも辿れるようにする

これは単なる表記統一ではない。人間と AI が同じ概念を指しているかを確認するための意味境界である。

コードは実行される最大級の現行仕様だが、意図・判断・禁止事項は持たない。共通言語は、そのコードの正確さと人間の意図を繋ぐ橋になる。関数名・クラス名・型名は特に強い正準語として扱い、docs 側が独自の別名を勝手に増やさないようにする。

## 24. SourceRef は全コード網羅ではなく、Test は意味カバレッジ

ユーザー:

> 全部のソースコードを参照する必要があるのか。Test との関連は。

暫定回答:

全ソースコードを `<SourceRef>` で参照する必要はない。それをすると参照グラフがノイズ化し、リファクタで壊れ、docs が実装の写しに逆戻りする。SourceRef は「仕様や設計が権威を委譲する場所」「人間や AI が辿る必要がある境界」に限定する。

重要なのはカバレッジ方向:

```text
弱い/危険な指標:
  全コードのうち何割が docs から参照されているか

強い指標:
  normative な Spec が、実装アンカーと Test アンカーを持っているか
```

つまりコード側を網羅するのではなく、意味ある仕様側から実装と検証へ辿れることを重視する。

役割分担:

```text
Spec:
  何が維持されるべきか。観測可能な振る舞い・拒否条件・外部契約。

SourceRef / @implements:
  それがどこで実装されているか。内部詳細の正典はどこか。

Test / @verifies / test("[spec.id]"):
  その振る舞いが実際に観測・検証されるか。
```

SourceRef は正しさの証明ではない。実装の場所と正典を示すだけ。Test は実装意図の説明ではないが、振る舞いの証拠になる。両者は代替関係ではなく補完関係。

テストも内部実装を全部網羅すべきではない。内部の一時変数や private helper の詳細まで固定すると、リファクタできない脆いテストになる。基本は外部から観測できる振る舞い・異常系・不変条件・過去の地雷を検証し、内部実装はその振る舞いを満たす範囲で自由に変えられるようにする。

原則候補:

> **コードは全部参照しない。仕様は全部たどれるようにする。実装詳細ではなく意味をカバーする。**

## 25. Test は仕様そのものではなく、保証の実行可能な投影

ユーザー:

> AI が意味のないテストを書く。本質は何を保証するか。Test を仕様にすることや TDD は賛否あるけどどうなのか。

暫定結論:

Test は仕様の全部ではない。しかし、よい Test は仕様が保証しようとしている意味の実行可能な投影である。

```text
Spec:
  何を保証するか。意味・外部振る舞い・拒否条件。

<Test> / test code:
  その保証が具体的な状況でどう観測されるか。

implementation:
  その保証を現在どう満たしているか。
```

Test は事例であり、全称ではない。通常のテストは有限の例を示すだけで、すべての入力・優先順位・Non-Goals・トレードオフ・なぜそうするかを表せない。したがって Test-only specification では不足する。一方で、Test がなければ仕様は観測可能性を持たず、AI 臭い文章になりやすい。

良い Test の条件:

- どの Spec / 保証を検証するかが分かる
- 実装ではなく外部から観測できる結果を見る
- リファクタしても壊れない
- 壊れたときに失う意味がある
- 削除したら重要な保証が失われる
- AI が実装後に自己正当化で書いたものではない

意味のない AI テストの症状:

- 実装をなぞるだけ
- mock の呼び出し回数や内部呼び出し順だけを見る
- not-null / snapshot だけで意味を見ていない
- どの Spec を verifies するか言えない
- 要件を壊しても落ちない
- 実装後に書かれ、一度も Red を観測していない

TDD の評価:

TDD は万能な儀式ではないが、AI coding では特に有効な部分がある。実装前に失敗する保証を作ることで、AI が「実装に合わせて後から都合の良いテストを書く」自己密封を防げる。ただし全細部に dogmatic な TDD を強制すると重い。Spec-level の振る舞い・バグ再現・外部契約では test-first を強め、探索的実装や内部リファクタでは characterization / test-after を許容する。

重要原則候補:

> **Test は仕様ではない。Test は保証の実行可能な投影である。  
> 何を保証するかが言えないテストはノイズである。**

## 26. 脱線検知: SourceRef/Test論は first wedge の対象外に戻す

その通り。SourceRef・Test・共通言語の話は重要だが、現時点で全体アーキテクチャを再設計し始めると scope explosion になる。これらは first wedge を支える制約として保持し、個別の大改造は後回しにする。

- 大きな回答は判断単位に分解する
- AI が埋めた前提は visible な maybe にする
- 全部その場で聞かない
- 正準語を使う
- 実装詳細を大量に spec へ複写しない
- SourceRef/Test は必要な証拠として必要なだけ使う

今回はやらない:

- SourceRef authority role の正式仕様化
- Test/BDD/TDD 戦略の全面改訂
- realization / coverage モデルの再設計
- semantic scope guard の enforcement

## 30. Review Card プロトタイプ初回 feedback: 面倒さ・見逃し・情報密度・AI推奨

ユーザー:

> UI において、めんどくささと見逃さないかを考えたほうが良い。めんどくささはクリック回数とか？情報量は少ない。AI 推奨ってやらないんじゃなかったっけ？

重要な論点:

1. めんどくささはクリック回数だけではない。スクロール・読解・画面遷移・記憶保持・注意切り替えもコスト。
2. しかしクリックを減らすため全部出すと、今度は見逃しやすくなる。単なる情報量最大化ではない。
3. 現状は情報量が少ないと感じられた。特に理由・具体例・証拠が薄い可能性がある。
4. AI 推奨の扱いについて、ユーザーは「やらない」認識だった可能性がある。過去の会話では、推奨を完全禁止ではなく「推奨が変わる条件」を必須にして rubber-stamp を防ぐ方向だったが、実際に画面で見ると違和感があるなら設計を再検討すべき。

原則候補:

> **クリック数は代理指標。本質は注意コストと見逃しリスクのトレードオフ。**

Review Card UX は「少ない情報で楽にする」だけでも「全部見せて漏れをなくす」だけでもダメで、判断に必要な情報を重要度順に露出し、判断に関係ない詳細だけを畳む必要がある。

## 31. AI推奨の代替としての選択肢ソートと情報密度不足

ユーザー:

> AI 推奨は、優先順に選択肢をソートとか？不足している情報は、わかりやすさ・具体例・比較軸・全部。

これは重要な方向転換。明示的な「AI 推奨」セクションをやめ、選択肢の並び順で優先度を示す可能性がある。ただし注意点:

> **並び順も推奨である。**

AI 推奨ラベルを消してソートだけにすると、推奨が消えるのではなく、暗黙の推奨になる。ソート基準を隠すと、かえって rubber-stamp を助長する。したがって並び順を使うなら、少なくとも以下が必要:

- 何を重視した順序かを明示する（例: 小さく試せる順 / リスクが低い順 / 影響が小さい順）
- AI の見立て順なら、その根拠を表示する
- 可能なら並び替え軸を人間が変えられるようにする
- 初期選択済みにしない

不足情報は「全部」。少なくとも以下を初期表示または近くに必要としている:

- わかりやすい説明
- 具体例
- 比較軸
- 影響範囲
- 証拠の要点

つまり現行プロトタイプは情報量が少なすぎる。ただし単純に長文化すると見逃しが増えるため、比較表・具体例・証拠要点を構造化して出す必要がある。

## 32. v2/v3 とバージョンを積むことへの違和感

ユーザー:

> 入れる。ただ AI がすぐに v2 とか v3 とか積むのはちょっと違和感がある。個人的に違和感というか。

これは重要な指摘。バージョン番号を積むことの問題:

- バージョンを上げること自体が進歩の演出になりやすい
- 前の版を捨てて新しい版に置き換えたような印象を与えるが、実際には理解の連続的な更新である
- v1/v2/v3 はマーケティング的なリリースのリズムを暗示し、何を検証したいかより「次の版を出した」ことが目的化しやすい
- 番号には情報がない。何が変わったかが分からない

代替案:

- バージョン番号ではなく、検証している仮説や変更内容で呼ぶ（例: 「比較表と明示ソートを試す版」）
- あるいは単に「プロトタイプの改善」と呼び、番号管理しない
- 番号が必要になるのは、外部にリリースして互換性の話をするときだけでよい

原則候補:

> **内部の試行錯誤にバージョン番号は要らない。何を試しているかで呼ぶ。**

これは Review Card プロトタイプの改善にも適用する。以後「v0.2」ではなく内容で呼ぶ。

## 34. 世代ラベルは既に禁止されていた: 調べない失敗の実例

ユーザー指摘:

> 実は結構重複してて v2 v3 っていうのは多分検索かけると出てくるんじゃないかな。これこそ調べないっていうのに当てはまる気がする。まあ別に番号つけてもいいけど、名前を変える？スコープを付ける？みたいなことしたほうが良いのかなあ。リリースのバージョンとごっちゃになるから。

調査結果 — **このプロジェクトには既に明示の方針があった**:

- `docs/domain/glossary.mdx` の Anti-Terms 表: 「`v1` / `v2` / `Phase X`（現行仕様内のラベル）」は避ける表現。「現行の振る舞いとして直接記述（経緯は `decision` へ）」が正しい使い分け。理由: 未リリース期間中に世代ラベルを残すと AI が古い挙動と現行挙動を取り違える。
- `sys.pre-release-policy` Constraint（`docs/designs/system-overview.mdx`）: 未リリース開発期間中は後方互換レイヤ（v1/v2 分岐・非推奨エイリアス・DB マイグレーション）を溜めず現行実装を直接書き換える。リリース準備は人間の明示指示なしに開始しない。

つまり AI は一般論（「バージョン番号はマーケティング的」）をでっち上げる前にリポジトリを調べるべきだった。これは:

1. 「調べない」失敗の実例
2. このセッション全体の核心問題（知識は存在するのに判断時に出てこない）の再現

ユーザー指摘のもう半分: 番号自体は禁止ではなく、**リリースバージョンと混ざらないよう名前やスコープで区別する**設計もあり得る。既存の良い例: `reviews.json` のスキーマ `version: 1` は対象フォーマットにスコープされている。ライブラリの `tailwind v4` は外部製品にスコープされている。問題なのはスコープのない世代ラベル（「プロジェクトの v2」「プロトタイプの v3」的な、何の世代か曖昧なもの）。

## 35. 試行の命名原則（合意済み）

業界調査（Figma の version history 運用・英国政府 design history・受託デザインのファイル命名・continuous deployment）から収斂した構造:

```text
微細な試行の連続体:
  → 自動のタイムスタンプ履歴（git / notes）。命名しない

意味のある節目だけ:
  → 内容・目的で名前を付ける（番号ではなく）

番号を付けるのは:
  → スコープがある場合（reviews.json のスキーマ v1）か外部リリースのみ
```

補助原則:

- **日付は意味を持たなくていい。順序キー。意味は内容名が持つ**（英国政府 design history の `2025-03-10-iterating-the-work-history-section` 形式が実例）
- 「何番目か」を覚える必要がある時点で命名に失敗している
- このプロジェクトでは git が自動履歴を担い、意味のある節目は `<Decision>` に残る。既存資産と一致する
- 既存 Anti-Term 方針（`v1`/`v2`/`Phase X` を現行仕様内に残さない）および `sys.pre-release-policy` と整合する

ユーザー合意済み。会話内では「比較表と明示ソート版」のように内容で呼ぶ運用を継続する。

## 36. 比較表版の feedback: 表の違和感・直感理解・wedge ジャーゴン

ユーザー:

> 推奨に引っ張られる感じは収まったかな、多分。表がちょっと違和感あるというかどうなんだろう。情報量というか、直感的にユーザーが理解できるようにアスキーアートとか mermaid とか導入したほうが良いのかなあ？wedge って単語もわからんし。

論点:

1. **明示ソートは機能した可能性**: 推奨に引っ張られる感じは収まった（「多分」なので引き続き観察）
2. **比較表に違和感**: まだ原因不明。候補: セルの文章を読み比べる作業が重い、差分が視覚的に浮かばない、表という形式自体が「比較されるもの」という固定的な関係を前提にしすぎている
3. **直感理解のための視覚化要求**: ASCII / mermaid という具体的な手段が出たが、解決したい問題は「読まなくても分かる」こと。視覚化が有効なのは構造（フロー・依存・位置関係）があるときで、平面な選択肢の比較を図にしても装飾になる危険がある
4. **wedge は AI が生んだジャーゴン**: 「入力は寛容に、出力は正確に」の共通言語原則を決めた直後に、AI 自身が説明なしのジャーゴンを出力しカードタイトルに混入させた。原則の即時違反であり、生成時チェックが必要な生きた証拠

## 37. 決定の強度は一様ではない: 確定・おまかせ・暫定

ユーザー:

> 決定にも「絶対にこれで決定」っていうのと「めんどくさいから一旦推奨」っていうのと「今のところはこれだけど…」っていうので色々あるんだよね。

これは重要な指摘。判断の結果は二値（決めた/決めてない）ではなく、コミットの強度が違う:

```text
確定:
  よく考えて決めた。覆すコストは高い

おまかせ:
  めんどくさいので推奨に乗った。考えていない

暫定:
  今のところはこれ。再検討されることを前提にしている
```

ここでの気づき:

1. **おまかせは失敗ではなく正当な判断モードである**。注意は有限なので、すべてに熟考はできない。問題なのはおまかせすることではなく、おまかせが確定と区別なく記録され、後から見えなくなること
2. 既存の Anti-Term（`ReviewStatus` と実装進捗を 1 軸に混ぜると事故る）と同じ構造: **強度の違う決定を 1 つの「選択済み」に混ぜると事故る**
3. Design Maybe との対称性: AI が仮に埋めたもの（maybe）と、人間が熟考せず乗ったもの（おまかせ）は、構造的にほぼ同じ状態。「再検討可能で、重要になったら昇格すべき弱いコミット」。違いは誰が発生させたかだけ
4. 強度ごとに求めるものが違うはず: 確定には比較材料の閲覧を要求し、おまかせは低摩擦だが「おまかせ」と表示し、暫定には再検討トリガーを付ける

## 38. 実装中の無自覚な仮決定: コンパイルエラーを通すための発明

ユーザー:

> 実装にも、勝手にやるのって、ここの仕様は決まってないけどコンパイルエラーを通すためにとりあえずやってる、みたいなもので多分なんやかんや起きてるんだと思う。

これは Design Maybe の最重要ユースケースかもしれない。実装中、AI は仕様が決まっていない箇所を「ビルドを通すため」に仮に埋める:

- 型を満たすためだけのデフォルト値
- エラーハンドリングの方針（握りつぶす/返す/投げる）
- バリデーション規則の発明
- 命名・配置・分割の暗黙の決定

これらは悪意なく発生し、テストも通り、diff にも紛れる。**「通る」ことと「決まっている」ことは別**なのに、通った瞬間に決定の偽装が完成する。

判断の強度モデル（確定・おまかせ・暫定）との接続:

- 実装中の仮決定は AI 側の「おまかせ」に相当し、maybe として捕捉されるべき
- 「あとで直すつもり」は暫定に相当するが、再検討トリガーがなければ永久化する
- 強度の記録があれば、後から「この実装のどこが仮置きか」を棚卸しできる

決定: 判断の強度（確定・おまかせ・暫定）をプロトタイプに実装する方向で合意。

- 強度は一覧チップ・詳細の強度バー・ヘッダ集計で視覚的に区別

## 40. ユーザーによるスケッチ: 説明的すぎる UI からシンプルなカードへ

ユーザーが手書きスケッチを提示:

- カードは縦に並ぶ（マスターディテールではなくフィード的）
- カード内は「Q: 〜 + 説明」のあと、選択肢が縦に積まれた箱
- 各箱は左に選択肢名・メリット・デメリット、右に影響・可逆性などの小さな要素
- カード下部に「暫定」「確定」ボタンのみ

ユーザーの評価: 現行 UI は「説明的すぎる」。情報量ではなく提示の構造が問題。セクション・バナー・サイドバー・注釈が重なり、説明書のようになっている。

重要な構造上の気づき:

- スケッチでは選択肢に「選ぶ」ボタンがなく、箱そのものを選ぶ形。選んだだけで強度を確定しなければ、それは自然に「おまかせ」になる。デフォルト強度モデルと一致する
- 「暫定」「確定」はカード単位のボタンで、強度は選択後の仕上げ動作になっている

## 41. スケッチ構造への作り替え（実装済み）

worktree コミットで実装:

- マスターディテール廃止、カード縦並びフィード
- 比較表廃止、選択肢はクリック可能な箱（メリット/デメリット/影響/可逆性）
- 箱を選ぶだけで「おまかせ」、確定/暫定はカード下部ボタンの明示操作
- 説明的セクション・バナー・サイドバーを削除、不確かさ/証拠は details 展開式
- ヘッダの強度集計は残した（おまかせ棚卸しの種）

ユーザーのスケッチとの対応: Q + 説明、選択肢箱の縦積み、暫定/確定ボタンの配置はほぼスケッチ通り。保留/分割は小さいボタンとして残した。

## 42. カードの中身と出すタイミングの問い直し

ユーザー:

> カードの中身をちゃんと議論かなあ？不確かなこと・根拠、と保留分割がわからん。あとそもそもカードを出すタイミングってなんだ？実装するために必要なのか全体の方針のためか、クイズか。

3つの未解決問題:

1. **カードの中身の正当性**: 各フィールド（不確かさ・証拠・具体例・比較軸…）が何のためにあるか、1つずつ検証されていない
2. **保留/分割の意味がない**: ボタンはあるが操作の実体が定義されていない。保留に再浮上条件がなければ stash と同じ蒸発問題になる。分割も実態（子カード生成？AIへの再構築要求？）が未定義
3. **カードを出すタイミングが未定義**: 実装中の判断点で割り込むのか、方針決めのバッチか、inboxに溜めて任意処理か、クイズ的セッションか。これは「捕捉は頻繁、中断は選択的」の原則と直結する設計の芯

## 43. 割り込みタイミングの研究調査: coarse boundary 原則

ユーザー方向性: 3つのタイミング（ブロッキング割り込み・自然な境界・クイズ的バッチ）は全部欲しい。分けてもよい。調査せよとの指示。

HCI の割り込み研究（Adamczyk & Bailey CHI'04、Iqbal & Bailey TOCHI'08、Human Factors 2021 等）の主要知見:

1. **粗いタスク境界（coarse breakpoint）での割り込みは、割り込みなしとほぼ同じコスト**しかない。細かい境界（fine breakpoint）での割り込みは復帰遅延・精神的負荷・エラーが有意に増える
2. **精神的負荷はサブタスク境界で一時的に低下する**（瞳孔計測で実証）。大きなチャンクの完了ほど解放が大きい
3. よって **defer-to-boundary ポリシー**が推奨される: 通知は境界まで遅延させるべき
4. 割り込みの回数自体はパフォーマンスに影響しなかったが、**後の割り込みほど注意を払われなくなる**（1回目 > 2回目 > 3回目）。割り込みは使うほど効かなくなる

AI コーディング実務の実例知見:

- Claude Code の permission mode（毎回確認 / acceptEdits / plan mode）、Cursor の auto-run、Codex の承認ポリシーは、すべて「ブロッキング割り込みの頻度」の問題に対する業界の試行錯誤
- 割り込みが多すぎると人間は YOLO モード（全許可）に逃げる。これは rubber-stamp の別形であり、割り込み設計の失敗が安全性を犠牲にする構造

航空・医療のアラート設計:

- warning（割り込む）/ caution / advisory（割り込まない）の階層化が標準。全部割り込むとアラート疲労で無視されるようになる

結論の方向性: タイミングは3レーンに分流する。

```text
レーン1 割り込み:
  作業が停止する or 不可逆な危険。即時。ただし可能なら人間の粗い境界を待つ。
  頻度は極小であるべき（使うほど効かなくなる）

レーン2 境界での提示:
  仮決定の棚卸し・非ブロッキングの確認。
  タスク完了・コミット前・セッション終わりにまとめて出す。研究が支持する形

レーン3 バッチセッション:
  方針・設計の判断群。人間が選んだ時間に2〜3件ずつ。
  documi-review のクイズ型が既存資産
```

レーンはカード種別ではなく配送タイミングの属性。重要になった maybe がレーン2からレーン1に昇格しうる。

## 44. 3レーンは綺麗に分割できるか: レーンの再定義

ユーザーの問い: 3レーンモデルはちゃんときれいに分割できるもの？

正直な答え: そのままでは分割できない。理由:

1. **ブロッキングかどうかは文脈依存**。同じ判断でも、AI が別経路で進めるなら非ブロッキング。判断そのものではなく「これから何をしようとしているか」に依存する
2. **重要度や緊急度は連続量**であって、3つの箱は近似にすぎない
3. **レーン2とレーン3の境界が曖昧**。どちらもバッチ処理に見える

しかし、レーンをカード内容ではなく「人間に要求する認知操作」で再定義すると分割できる:

```text
レーン1 停止:
  「仮決定すら許されない」もの。
  判定基準: AIが仮に埋めて進められるか？ YESならレーン1ではない。
  不可逆・危険・後戻りコストが高い分岐のみ。

レーン2 批准:
  弱いコミット（maybe・おまかせ）の確認。
  認知操作はトリアージ（承認/却下/保留）で、1件数秒。

レーン3 熟考:
  比較検討を要する本当の意思決定。
  認知操作は判断で、1件数分。
```

この再定義では:

- レーン1の判定は「重要か」ではなく「仮に埋められるか」に変換される。重要性より可逆性のほうが判定しやすい
- レーン2と3は認知モードで分かれる: 批准（済んだことの確認）と熟考（これから決める）

残る問題: 初回のレーン分類は間違いうる。必要なのは正確な初回分類ではなく:

- 誤分類の修正が安いこと（レーン2は境界ですぐ見るので偽陰性が回復される）
- 「こういうので割り込むな」というフィードバック経路
- 迷ったら割り込まない側に倒す（レーン1の誤用は信頼を削り、レーン2の誤用は境界で回復できる）

## 45. 判定誤りボタン: 1クリックの訂正経路

ユーザー:

> 質問を見てユーザーがこの判定が誤ってたりしたら、判定誤りみたいなボタン作っても良いかも。

これはレーンモデルの要件だった「修正が安い」を「修正が1クリック」に具体化する。検討点:

- **何の判定が誤りうるか**: レーン（割り込むべきだった/なかった）、重要度、種別、そして問いのフレーミング自体（「そもそもこの論点は違う」「判断不要」）
- **押した後に何が起きるか**: (a) このカードの修正（レーン移動等）、(b) 将来の分類の較正データ。プロトタイプでは (a) のみでもよいが、記録は残すべき
- **摩擦の設計**: 理由まで聞くと重い。1クリックで誤り信号だけ記録し、必要なら後で分類し直す形が軽い
- 一般化すると: **AI の出すものはすべて仮説であり、仮説には安い反証経路が必要**。並び順・重要度・レーン・そもそもの論点立て、すべてに同じ原則が効く

既存概念との接続: 承認ガードの unapprove や suspect フラグは「後から誤りを標記する」仕組みであり、同じ思想が既にある。

## 46. レーン命名の混乱と英語正準語化の方針

ユーザー:

> ちょっとゴチャゴチャしてきた。一旦ちゃんと考え直そう。レーンのそれぞれの名前もちょっと分かりづらい。専門用語もプログラムと合わせるために英語にしても良いかも。

混乱の原因分析:

- レーン番号（レーン1/2/3）・タイミングの言葉（割り込み/境界/バッチ）・認知操作の言葉（停止/批准/熟考）の3系統が重なっていた
- 「批准」は条約の批准で日常語ではなく分かりづらい
- 共通言語原則（入力は寛容、出力は正準）に従い、正準語はコードシンボルに対応できる英語にする方向が示された

検討すべき論点:

- レーン（配送タイミング）とアーティファクト種別（認知操作）は相関する。ならば「レーン」という抽象を捨て、種別がタイミングを内包する形に単純化できる可能性
- 既存用語との衝突チェックが必要: `check`（documi check）、`review`（Review Queue）は既に占有。`Decision` は決定済み記録で占有

## 47. 難しい言葉を使いすぎる問題と、ユーザーの平易な再定式化

ユーザー:

> 配送ってなんだ？わからんくなってきた。仮置きできるもの、今ここで決めないと後々大変だから仮置きできないもの、あとなんだ？以前仮置きしたものを再判断。ゴチャついた。結構あんた難しい言葉使うから。

重要な指摘:

1. AI が「配送」「レーン」「アーティファクト」などの造語を重ねて混乱を生んだ。wedge と同じ失敗の再発。難しい言葉を使う傾向はユーザーから繰り返し指摘されている
2. ユーザーの平易な再定式化のほうがモデルとして綺麗:
   - 仮置きできるもの
   - 今ここで決めないと後々大変だから仮置きできないもの
   - 以前仮置きしたものの再判断
3. この3つでモデルが完結している可能性が高い。「大きな方針判断」は独立した種別ではなく、文脈の中で「仮置きできないもの」になるか、人間が時間を選んで話すだけのもの

## 48. 2つだけでいい: 仮置きの可否は種類ではなく状態

ユーザー:

> 3ってちょっとおかしい。多分3の中にも「以前仮置きできたけど今の判断だと仮置きできない」っていうのと「まだ先延ばしできるもの」がある。2つだけでいいかなという感じ。

これは重要な単純化。ユーザーの指摘の構造:

- 「以前仮置きしたものの再判断」は種類ではない。再判断されるものは、結局この2つに分かれるだけ:
  - まだ先延ばしできるもの → 仮置きできるもののまま
  - 今は仮置きできないもの → 仮置きできないものに移動した
- つまり「再判断」は第3のカテゴリではなく、どちらの状態にいるかを確認し直す行為にすぎない

結論のモデル:

```text
状態は2つだけ:
  仮置きできる
  仮置きできない

これは固定の種類ではなく、状況で動く状態。
見直しとは、状態が動いていないかを確認し直す行為。
```

「仮置きできない」の判定には「今決めないと後々大変」（ブロッキング・後戻りコスト）が含まれる。

## 49. 2分割で試す決定

ユーザー:

> この2分割かな。それか全部仮置き可能にして重要な判断とかにする？まあその重要な判断も判定がむずいんだけどね。でも一旦この2分割でやってみて…って感じかな。

決定: **仮置きできる / 仮置きできない の2分割で試す。**

却下されなかった代替案（将来の再検討用）:

- 全部仮置き可能にして「重要な判断」フラグで分ける案。重要度判定が難しい点は2分割と同じだが、こちらは仮置きのデフォルト化が強い。一旦保留。

プロトタイプでの試し方: 既存の8カードを2分割で分類し、分類できるか・どこで迷うかを検証する。迷うケースは判定基準の粗さの証拠になる。

## 50. 仮置きは一回きりではなく何度も見直すもの

ユーザー:

> 仮置きできるものって、全てを仮置きするものだと思ってない？何度も見直すものだし。

これは2つの重要な修正:

1. **仮置きは一回の仮決定+一回の確認ではない**。仮置きしたものは仮置きのまま生き続け、状況が変わるたびに何度も見直される。見直しは単発の批准イベントではなく、継続的な再確認
2. **「仮置きできる」はカード単位の全体的な属性ではない**。1つの判断の中に、仮置きできる部分とできない部分が混在しうる。可否は原子化した小さな判断単位に適用されるべき

設計への影響:

- 見直しが「何度も」行われるなら、見直しのコストが致命的に重要。毎回全部読み直す形は破綻する。「前回の見直しから何が変わったか」だけを見せる必要がある（既存の stale 概念に接続）
- 仮置きは「一度決めて承認待ち」ではなく「仮のまま所有し続ける」モデルに近い

## 51. 仮置き「できる」と仮置き「する」は別

ユーザー:

> あくまで仮置き可能か可能じゃないかっていう問題で、仮置きしないといけないって問題じゃないから。

AI の誤り: 「ほとんどの判断は仮置きできるから、人間に聞く必要がない」と結論づけたが、これは「できる」から「すべき」への飛躍。

正しい構造:

```text
仮置きできる / できない:
  何が許されるかの話。可逆性とコストの判定

仮置きするか / 聞くか:
  何をするかの選択。別の判断
```

- 仮置き**できない**もの: 聞くしかない。選択肢がない
- 仮置き**できる**もの: 仮置きしてもいいし、聞いてもいい。ここに選択がある

「仮置きできるものでも聞く」ケースは普通にある。人間が自分で決めたい判断、方向に関わる判断、単に気になる判断。つまり仮置き可否は行動を決めるのではなく、行動の許可範囲を決める。

残る設計問い: 仮置きできるものについて、聞くか仮置きするかを何で決めるか。候補は人間の意思（決めたいかどうか）・重要度・割り込みコストとの比較。

## 52. 問いを仮置き可能に「する」という能動的な転換

ユーザー:

> 仮置きするかどうかは多分人間が決めるものだから。問題は、この問いが仮置き可能な問いにするか、仮置き不可能な問いにするか、じゃないの？

2つの修正:

1. **仮置きするか聞くかは人間が決めること**であって、システムが設計する問いではない。AI が「何で決めるか」と考える必要はない
2. 本当の設計問いは: **この問いを仮置き可能な問いにするか、仮置き不可能な問いのままにするか**。仮置き可否は受動的に判定する性質ではなく、能動的に設計できるもの

これは「プロトタイプは仮置きできない判断を仮置きできる実験に変換する技術」という気づきと一致する。例:

- 「何から作り始めるか」は仮置き不可能（方向を決める）
- 「固定データでカードUIを試すか」は仮置き可能（小さくて戻せる）
- 前者を後者に変形するのがプロトタイピング

つまり問いが仮置き不可能なときの選択肢:

1. その場で人間が決める
2. 仮置き可能な問いに変形する（小さくする・分割する・試す形にする）

この「変形」こそが「分割」ボタンの本当の意味かもしれない。分割は単にカードが大きいときの操作ではなく、仮置き不可能な問いを仮置き可能な問いに変換する行為。

## 50. 仮置き可否の具体例と変形可能性の検証

ユーザーの問い:

1. 必要なのは「必要になったら」でいいのでは（事前に全部分類しない）
2. 本当に変形できるものなのか（疑念）
3. 具体的にどんなものが仮置き可能/不可能か、案を挙げてほしい

検討した具体例:

仮置き可能（戻せる・試せる）:

- 命名・内部構造・実装詳細（リファクタで戻せる）
- UI の細部文言・レイアウト・デフォルト値
- 内部のエラーハンドリング方針
- ツール内の運用ルール（やめればいい）
- 試験的な仕組みの導入（このプロトタイプ自体）

仮置き不可能（戻せない・後では遅い）:

- 外部に公開する行為: リリース、公開 API の破壊的変更、送信済みメッセージ
- 不可逆な操作: 本番データの削除
- 他者が依存し始めた公開契約
- セキュリティ境界の設計（穴は後から埋められない）
- 時間を食う方向のコミット（使った時間は戻らない）

変形の可否（ユーザーの疑念への答え）:

ソフトウェアには不可逆を可逆に変える技術体系がある:

- 本番削除 → soft delete / バックアップ / staging でのリハーサル
- API 破壊的変更 → feature flag / 併存期間 / versioned endpoint
- 方向のコミット → 小さいプロトタイプ・spike
- 公開リリース → prerelease / limited beta

変形できないものもある:

- 送ったメッセージ、他者が依存し始めた API、使った時間（機会費用）
- 変形コストが判断コストを超える場合は変形しないほうがよい

つまり変形は万能ではないが、ソフトウェアでは驚くほど広く効く。「仮置き不可能」の多くは「まだ可逆化の工夫をしていない」にすぎない可能性。

## 51. 仮置きの目的の原風景: 焦点と付随の分離

ユーザー:

> 仮置きの目的ってそもそも何だったかって言うと、今決めたいのはここなんだけどコンパイル通すためにはここも決めなきゃいけない、でもここ決めるのはもうちょっとあとのほうが良いから一旦こうしておいて、で一旦こうしておくから確定ではない、みたいな状況で使う。

これは仮置きの目的の正しい接地:

```text
今決めたいのはここ（作業の焦点）
  でも進めるには、ここも何か決めなきゃいけない（付随する未決定）
  ここをちゃんと決めるのは、もうちょっとあとがいい
  → 一旦こうしておく
  → 一旦だから確定ではない
```

つまり仮置きは「決定の先送り」ではなく「**ちゃんと決めるべき時を、ちゃんとした時にするための仕組み**」。付随して必要になった決定を、焦点の作業を止めずに、しかし確定の偽装もさせずに、後の適切なタイミングに送るもの。

ここから導かれる要件:

1. **確定と区別できること**が本質要件。見えない仮置きは確定と区別がつかず、先送りがいつの間にか永久化する。これがコンパイルエラーを通すための仮実装の問題だった
2. 仮置きの単位は小さく具体的（デフォルト値・バリデーション・命名など、実装中に付随して必要になるもの）
3. 大きな判断は「今決めたいここ」の側であり、仮置きの対象は付随側

焦点と付随の分業:

- 焦点（今決めたいこと）: ちゃんと決める。必要なら人間と
- 付随（コンパイルを通すために必要なもの）: 仮置き。visible で確定ではない

## 52. 選択式UIの未決領域と強度モデルの衝突

ユーザー:

> そうだね、ちゃんとできた気がする。実装かなあ。まだ終わってないのが、どういう選択式にするか。多分 仮 or 不可っていうのはボタンをいっこ追加するだけなんだけど、それ以外がぜんぜん決まってない。

設計待ちの論点:

1. **強度モデルと仮置きモデルの衝突**: 暫定（provisional）は人間による仮置きであり、概念が重複している。おまかせも AI の仮置きを無批判に受け入れた状態で、やはり弱いコミット。確定/暫定/おまかせの3強度は、確定/仮置きの2状態に単純化できる可能性
2. **保留ボタンの存否**: 決めないカードは開いたまま残るだけで、「後で」は操作ではなく状態の不在。再浮上条件のない保留は蒸発装置だが、開いたまま残ること自体は自然な先送りとして機能する
3. 「AIにまかせる」の位置: 仮置き可能な問いで人間が選ばずAIに仮置きさせる操作は、選択肢を選ぶとは別の行為
4. 分割は仮置き不可能な問いの変形要求

## 53. 決定援助の中身: IPDAS 規格の調査

ユーザー指摘「これはちゃんと調べた？」に基づき調査。医療の patient decision aid（患者決定援助）には IPDAS という国際基準があり、何を含めるべきかがエビデンスベースで規格化されている。

IPDAS の必須項目（Qualifying criteria）:

1. 決定を明示する（explicitly state the decision）
2. 状況・背景を記述する
3. **「様子を見る/何もしない」選択肢を含め、すべての合理的な選択肢を挙げる**
4. 各選択肢の良い点（benefits）を記述する
5. 各選択肢の悪い点（harms）を記述する
6. **どの良い点・悪い点が本人にとって大事かを考えさせる**（values clarification）、または結果を経験することがどんなものかを記述する
7. 比較は side-by-side で、表現は even-handed（同じフォントサイズ・中立な言葉）
8. **何もしない場合の自然な成り行き（natural course）を記述する**
9. 結果の確率がある場合は positive/negative 両方のフレームで示す

我々の議論との対応:

- 「決めないとどうなるか（仮置き内容の提示）」は IPDAS の natural course と同じ。30年の規格で必須
- 「何もしない選択肢」を明示する — 仮置きを受け入れることは、まさに do-nothing 選択肢。カードに暗黙でなく明示すべき
- values clarification（本人の価値観の明確化を助ける）は我々のカードに欠けている。AI の価値観（並び順の根拠）はあるが、人間の価値観を引き出す仕組みがない
- even-handed な提示（同じ重さ・中立な表現）は推奨バイアス対策と一致
- 具体例は「結果を経験することがどんなものか」に対応し、必須項目に入っている

## 54. 「質問の意図を理解できません」ボタン

ユーザー案。判定誤りとは別のフィードバック経路。

「質問の意図」が分からない = なぜこれを聞かれているのか、何に影響するのかが分からない状態。質問文は読めても意図が不透明なことがある。これは「状況・なぜ今か」フィールドの失敗の検出器。

重要な含意: 仮置きの仕組みは「後で人間が見直せる」ことを前提にしている。**意図が分からない質問は、仮置きすら機能しない**——見直しのときに結局分からないままだから。つまり意図不明の質問は、仮置き不可能以前の問題として、カード自体が壊れている。

押されたら何が起きるべきか:
- AI が問いを立て直す/説明し直す機会になる
- それでも分からなければ、その問いは存在自体が誤りかもしれない（フレーミングの誤り、存在の誤りに繋がる）

フィードバック経路の整理（ここまでに出たもの）:
- 判定誤り: 仮置きできる/できないの分類が違う
- 意図がわからない: 問いの意味・動機が不透明
どちらも「押すだけで信号が記録される」軽い形が共通している。

## 55. 「質問が理解できない」と「意図がわからない」は別物 — 調査裏付けあり

アンケート方法論（survey methodology）に数十年の研究蓄積がある。質問理解は2層に分かれる:

1. **文字通りの意味（literal meaning）の理解** — 語彙の曖昧さ・構文の複雑さで失敗する。「質問が理解できない」はこちら
2. **語用論的な意味（pragmatic meaning）の理解** — 質問者の意図の推論。「何を報告すべきか」「どの範囲を聞いているのか」。「意図がわからない」はこちら

例: "What have you done today?" — 単語は全部分かるが、シャワーを報告すべきかどうかは質問者の意図を推論しないと分からない。

重要な非対称:
- literal の失敗は本人が自覚できる（読めないものは読めない）
- pragmatic の失敗は**無自覚に起きうる**。バターの例: マーガリンを含むと勝手に解釈して、自信満々に違う質問に答える。修正要求がない限り誰にも気づかれない

含意: ボタンは自覚した失敗しか捕まえない。無自覚の誤解は具体例との突き合わせで浮上させるしかない（例が自分の解釈と合わない → 何かがおかしいと気づく）。

Tourangeau の認知モデル: 質問応答は comprehension → retrieval → judgment → response の段階。comprehension は最初の段階で、ここが失敗すると後は全部無意味。通常の会話では repair（修正の要求）で解決するが、一方通行の仕組みではその経路を用意する必要がある。

## 57. ボタン集約の提案と contestability 調査

ユーザー案: フィードバックを集約して4ボタン構成にする:

```
理解不能 / 異議申し立て / 仮置き(optional) / 確定
```

- 理解不能 = 質問の理解失敗（literal/pragmatic 両方を含む）
- 異議申し立て = 理解はできたが分類・フレーミング・前提に納得いかない
- 仮置き(optional) = 仮置きできる問いでのみ有効。分類がボタンの有効性を決める
- 確定

調査（contestability — アルゴリズム決定への異議申し立て研究）:

- contestability の存在は**使われなくても**手続き的公平性の知覚を上げる（CHI 2023）。ボタンがあること自体が信頼の装置
- ユーザーが異議を申し立てたい対象は2つ: 決定者自体、または決定の根拠
- 効果的なレビューに必要なもの: 人間の関与・参加できること・タイムリーな結果
- 実例: Stack Overflow の close 理由 "needs details or clarity" は意味不明と意図不明を区別しない単一カテゴリ

理解不能を1ボタンにする論理的根拠: 理解できない人は**なぜ理解できないかを自己診断できない**。literal か pragmatic かの区別を要求すること自体が理解不能なタスク。原因の診断はシステム側が後でやればいい。

この4ボタンでカードへの応答は完全に閉じる:
- 理解不能 → カード破損状態、AIが説明し直す
- 異議 → 分類/フレーミングの見直しフラグ
- 仮置き → 仮置き状態へ（仮置き可能な場合のみ）
- 確定 → 確定状態へ
- 押さない → 開いたまま残る（自然な先送り）

## 58. プロセスの接地: カードはチャットの付属物

ユーザーの接地: 「そもそもどういうプロセスでこの質問が出てくるのか」。カードはチャット駆動の作業から発生し、フィードバックもチャットに戻る。異議を押したら chat に戻って AI が理由を聞く形でいい。

調査（conversational repair — 会話の破綻と修復の研究）:

- **least collaborative effort の理論**: 修復の負担は双方に分散すべき。ボタン（人間の最小労力）+ チャット（対話での修復）はこの理論に正確に沿う
- **協調的修復は一方任せより成績が良い**（保険会社チャットボットの野外実験）。修理を人間だけ/システムだけに任せると失敗ループになる
- **「言い換えて」のみの修復は失敗しやすい** — 同じ誤解を繰り返す。選択肢や解釈候補の提示（"X と Y のどっちですか"）のほうが有効
- 破綻の原因は分類器でリアルタイム自動分類できる実績がある（21,736 メッセージのクラスタ分析）— 押したボタン+コンテキストがあれば原因診断はシステム側で可能

プロセスの全体像:

```
チャットでAIと作業
  → AIが判断点にぶつかる/仮置きする
  → カードが発生（ブラウザ）
  → 人間がカードを見る
    → 確定/仮置き → 作業続行
    → 理解不能/異議 → チャットに戻って対話で修理
```

アーキテクチャ含意:

1. カードは出自（どの会話・作業から生まれたか）を持つ必要がある — フィードバックはそのコンテキストに戻る
2. ボタンはコンテキスト付きの再入場トークン: 「このカードの、この種類の問題」をチャットに引き継ぐ
3. カード UI にフォームや入力欄を作らない — チャットが既にある。これで前回の未決問い（任意の理由入力欄）は解消: 入力欄は要らない

## 59. 仮置きボタンの意味と出すタイミングの方針

ユーザーからの2点の修正:

1. **仮置きは選択肢を反映する** — 仮置きボタンを押す = 人間が選んだ選択肢を仮置きとして適用する。「判断が全部自動で仮置きになる」わけではない
2. **いつ出すか** — AI chat の質問と同じようにしていい。特別なタイミング機構は作らない

調査（AI コーディングツールの質問 UX）:

- Claude Code の AskUserQuestion はモーダルで文脈を隠す問題が報告されている — 質問に答えるのに必要な情報を質問 UI 自体が覆い隠す。カードが別画面（ブラウザ）であることはこの失敗を回避する
- Cursor Agent は回答を待ちながら作業を続行し、答えが来たら取り込む — 非同期質問。仮置きしながら進めるモデルと同じ構造
- サイド質問（/btw, /side）— 本流を中断しない並行チャネルとして両ツールに存在

## 60. 質問の出力形式: CLI/MCP、同期/非同期

ユーザーの設計問い: 質問をどういう形式で出すか（CLI? MCP?）、同期か非同期かタメとくか。

調査（MCP elicitation — 2025-11-25 spec）:

- MCP には `elicitation/create` がある: サーバー→クライアントへの質問要求。ツール実行を途中で止めてユーザーに聞ける
- 2モード: form（構造化データをクライアント内で収集。スキーマはフラットなオブジェクトのみ）と **url（ブラウザで外部URLを開いてやり取り）**
- url モードは「MCPクライアントを通さないやり取り」のためにある — カード UI がブラウザで開く構造と同じ
- 性質は同期的: ツール呼び出しが応答を待って止まる

設計の答え（仮置きモデルから導かれる）:

```
仮置きできない → 同期的: 作業が止まって聞く。elicitation 相当
仮置きできる   → 非同期: AIは仮置きで進める。カードはタメとく
                        人間は後で見て、必要なら方向を上書きする
```

タメとく場所には2種類たまる:
- 未回答のカード（AIの仮置きで進行中）
- 仮置き状態のカード（人間 or AIが置いたもの）

documi 内部の先例: documi-review のクイズが既に「人間専用の最終確認URL」パターンを使っている。URL 経由の人間インタラクションはプロジェクト内に実績がある。

## 61. 実装: 4ボタン・2状態モデル（コミット 840dc0e @ prototype/decision-cards）

合意済みモデルをプロトタイプに反映した。

- アクション: 意味がわからない / 納得いかない / 仮置き / 確定 の4ボタン
- 仮置き・確定は選択肢を選ぶまで無効。仮置きは fillable なカードでのみ有効（状態機械でもガード）
- 3強度（確定/おまかせ/暫定）を廃止し仮置き/確定に単純化。選択は入力、ボタンが仕上げ
- 意味がわからない → 破損状態（選択肢もボタンも無効化、トグルで解除）。納得いかない → 進行を妨げないフラグ
- 「何もしないとどうなるか」（AIの仮置き方向）を全カードに追加。fillable カードでは「AI は〈先頭選択肢〉で仮置きして進める」、non-fillable では「進められない」
- 保留・分割ボタンは削除。決めないカードは開いたまま残るのが自然な先送り

検証: bun run verify 全通過。ブラウザで仮置きできないカード（確定のみ有効）・できるカード（両方有効→仮置きで状態チップ出現）を確認。

偏差（要確認）: 「何もしない」を明示的な選択肢としては実装せず、Q部の情報表示にとどめた。選択肢化すると「AIの仮置きを確定として批准する」意味になり、状態機械と絡むため一段階分けた。次の反復候補。

## 62. 原則: 問を見て判断できることは書かない（アンカリング研究の裏付け）

ユーザー原則: 「問を見て判断できることはなるべく書かないでほしい」。カードの中身は未決定のまま実装していたため、ここで決め直す。

調査（automation bias / anchoring）:

- AI の評価を先に見せると、人間は自分の正しい独立判断を捨てて AI に乗る（病理医実験で 7% の automation bias、時間制約で悪化）
- 逆順（先に独立判断→後で AI 推奨）なら誤った助言への耐性が約2倍（OR 1.9）
- つまり**人間が自分で判断できる種類のことを AI が先に表示するのは、情報価値ゼロでバイアスだけある**最悪の組み合わせ

含意: kind・重要度チップなどのメタ分類はカードから消す。カードに書くのは人間が自力で生み出せないものだけ:

- AI の意図（何もしないとどうなるか）— 見えないもの
- 分析の労働（選択肢の得失・可逆性など）— やればできるが労働
- 状況（なぜ今か、どの作業から出たか）— AI の内部状態は見えない

証拠・不確かなこと一覧・並び順の根拠もカードから消す方向。検証と修理はチャットと納得いかないボタンの役目。

## 63. 実装: メタ情報排除（コミット @ prototype/decision-cards）

決定したカード中身に合わせて実装。kind・重要度・仮置き可否チップ、不確かさ一覧、並び順の根拠、証拠セクションをデータモデルごと削除。カードは問い・状況となぜ今か・何もしないとどうなるか・具体例・選択肢（名前+一言、得るもの/失うもの、影響/可逆性）と4ボタンのみ。ユーザーの最初のスケッチとほぼ同じ形に収束した。verify 全通過。

## 64. 影響・可逆性の扱い: dilution effect の研究

調査: 判断に効かない情報（non-diagnostic）は、効く情報（diagnostic）の効果を薄める「dilution effect」が確認されている。重要な追加点: 「これは関係ないから無視して」と指示しても効果は消えない。**物理的に取り除いたときだけ消える**（Kemmelmeier 2004）。

含意: 影響・可逆性を全選択肢に一律表示すると、差が出ないカードでは得失の効きを薄めるだけ。ラベルや注記では防げない。可逆性の実質的内容はコスト/利得なので得失に折り畳める。

## 65. Q部の再設計と状態駆動リッチ化

Q部の問題3つと解消:
1. タイトルと decision が重複していた — decision フィールドを廃止し、タイトルを完全な問いに統一
2. タイトルがトピック名で問いになっていないカードがあった — すべて問いの文に書き換え
3. whyNow が「〜ため」で終わる断片だった — 完全な文に修正

リッチ化の方向性: 「情報を足す」ではなく「状態と階層を見せる」。研究メモ: 詳細を見た人ほど複雑な場面で正確性が下がる事例あり。複雑さを増すリッチ化は逆効果。

入れたもの:
- defaultPath にアクセントの左ボーダー（最重要の1行なので）
- 選択肢にラジオ風インジケータ（選択可能であることのアフォーダンス）
- 確定/仮置き後は未選択の選択肢をフェード — 決まったカードは落ち着き、未決のカードが目立つ。状態による progressive disclosure

生成時のチェックリスト論: 可逆性などの軸は表示の型ではなく AI の生成工程の自問項目として残す（表示は得失に折り畳む）。

## カードの選択肢構造の決定（夕方続き）

### 2つの「何もしない」は別物
- A. 人間が何もしない（無アクション）→ カードは開いたまま。回答ではない
- B. 「何もしない」という回答（negative decision）→ カードは閉じる。それで終了
- B は特別な機構なしに選択肢の1つとして状態機械をそのまま通る
- 記録価値: negative decision は理由付きで残すと再検討の蒸発を防ぐ（調査済み）
- 警告: 明示的な不作為選択肢は専門家でも不作為を増やす（71% vs 53%の実験）

### negative 選択肢は「個別」で付ける（決定）
- 自動付与（定型文）は中身が空っぽになり filler 原則違反
- 個別は AI が省略できるリスクがあるが、テストで「各カードに negative が1つ・得失が空でない」を機械保証
- 選択実験研究: generic な "neither" は非推奨、具体的な status quo 表記が良い

### 書き込み選択肢（第Nの選択肢）は第一級の選択肢（決定）
- アンケート方法論の "other (please specify)" が結論: ラジオ+入力が一体の1選択肢
- AI の書き起こし・承認は不要。自分のアイデアに AI の許可を待たない
- 内容が不明なら既存のチャット修理経路で聞く
- メリット/デメリットは決定時には存在しない。記録の完全性は後から追記可能（配管の話）

### 書き込み選択肢のインタラクション（決定）
- フォーカス = 選択。入力欄に触れた時点でチェックが入る
- 行全体は <label> 要素。どこをクリックしても入力欄にフォーカス（JSなしのネイティブ挙動）
- 丸は飾り。ボタンでもチェックボックスでもない
- ガード: 書き込み選択が空だと確定/仮置きは無効

### Q部の形（決定）
- 「問（タイトル）+ 詳細（1つのつながった文章）」のみ
- ラベル・ボーダー・斜体・キャプションなし。項目の区別は「放っておくと」「たとえば」の文そのものが担う
- データ上は whyNow/defaultPath/example の3フィールドのまま（生成チェックリストとして意味がある）が、表示は連結した1段落

### カード構造の完結
```
AIの選択肢 × 3  +  やらない選択肢  +  自分で書いて選ぶ選択肢
```
