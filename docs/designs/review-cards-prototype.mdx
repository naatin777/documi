# Review Card プロトタイプ設計


## 設計方針

Review Card プロトタイプは、AI 生成を正式化する前に、人間がカード形式で判断しやすいかを検証する画面である。再設計会話から抽出した実際の判断を初期データとして表示し、視覚的な情報量と選択肢比較のしやすさを優先する。

- **初期データは fixture、操作状態はカードストアとする**: 初期カードは実際の設計判断から作った TypeScript 定数を種元としつつ、回答・フラグは `.documi/cards/` に永続化する。これにより、UX の検証とデータ生成の難しさを分離しながら、リロード後も操作状態を確認できるようにする。
- **カードはチャットの投影であり独立したアプリではない**: フィードバック（意味がわからない・納得いかない）の理由はチャットで対話的に修理する前提であり、カード UI には理由入力欄を作らない。プロトタイプではチャット接続がないため、これらは状態マーカーとしてのみ表現する。
- **人間が問を見て判断できることは書かない**: 種別・重要度・仮置き可否のチップ、不確かさ一覧、並び順の根拠、証拠はカードに表示しない。AI が先に評価を見せると人間の独立判断がアンカリングで歪むため、カードには人間が自力で生み出せないもの（AI の意図・分析の労働・状況）だけを書く。検証と修理はチャットと「納得いかない」ボタンの役目である。
- **カードの中身は決定援助の規格に沿う**: 問い・状況となぜ今か・何もしないとどうなるか（AI がどう仮置きして進めるか）・選択肢の得るもの/失うもの・具体例を含める。何もしない場合の成り行きの提示は、人間が「仮置きを受け入れるか自分で決めるか」を判断する土台である。
- **4ボタンで応答が閉じる**: 人間の反応は「意味がわからない」（破損状態。決定も仮置きもできない）・「納得いかない」（進行を妨げない異議フラグ）・「仮置き」（選んだ方向の仮適用。仮置きできるカードでのみ有効）・「確定」の4つで完結し、押さない場合は開いたまま残る（自然な先送り）。
- **選択は入力であり、ボタンが仕上げである**: 選択肢をクリックしても状態は変わらず、「仮置き」「確定」を押して初めてその強度で適用される。何も押さなければ AI の仮置き方向で進むため、仮置きボタンは「AI のデフォルトとは違う方向に仮に進めたい」ときの操作になる。
- **推奨セクションは置かず、デフォルトの行き先だけを示す**: 独立した AI 推奨セクションは置かない。AI の見立ては「何もしないとどうなるか」として開示され、それが並び順バイアスの開示を兼ねる。
- **操作状態と記録を分ける**: カードは `.documi/cards/` に保持する操作状態であり、長期記録ではない。確定したカードだけ「記録に残す」操作で `<Decision>` として `docs/decisions/` に蒸留でき、蒸留に成功したカードは一覧から消える。蒸留は判断応答ではなくライフサイクル完了操作なので、4つの判断ボタンには含めない。
- **既存 Review Queue と分離する**: 既存の承認ワークフローや `reviews.json` には接続せず、独立した `/cards` ルートで検証する。
