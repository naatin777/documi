# ドキュメント執筆ガイド（各 Type の役割と粒度）

Documi の 7 種類の Artifact Type について、**「どこに何を書いて、何を書かないか」** の基準と粒度を定めるガイド。
ドキュメントの責務や記述が曖昧なままだと、AI の実装がブレるだけでなく **AI コードレビューも無限に修正案を出し続けて収束しなくなる** ため、各 Type の境界を明確に保つことを目的とする。

<Note id="note.authoring-guide-wip" intent="informative">
  7 種類の Artifact Type（`goal`・`domain`・`spec`・`contract`・`design`［全体設計は `scope: system`］・`decision`・`guide`）および `<Decision>`（マイクロ ADR）・`<Test>`（仕様同居保証シナリオ）とコード・テスト・コミット・コメントの責務境界を定義済み。
</Note>

---

## 1. 全体像：Problem Space と Solution Space

すべてのドキュメントは **「客側の課題・ありたい姿（Problem Space）」** から **「システムの約束・内部実装（Solution Space）」** へ向かって解像度を落としていく。

| 層 / 日本の工程対応 | Type | 一言でいう役割 | 書くこと | 書かないこと |
|---|---|---|---|---|
| **Problem Space** *(企画・業務要件)* | **`goal`** | なぜ・誰のため | 対象アクター / JTBD（状況・動機・期待成果）、目指す状態、Non-Goals、不変制約 (`<Constraint>`) | 具体的な画面仕様・API・実装詳細 |
| **Problem Space** *(業務の共通言語)* | **`domain`** | 共通言語と概念モデル | 用語定義 (`<TermDef>`)、別名、実コードの型・シンボル対応、概念の関係・状態遷移 | 画面操作や細かい条件分岐 |
| **Solution: ユーザー目線の外側** *(システム要件・外部設計)* | **`spec`** | ユーザーから見た振る舞いと保証 | テスト可能な要件・体験・非機能・異常系 (`<Spec>`) ＋ 宣言的な保証シナリオ (`<Test verifies="..." level="...">`) | 内部クラス構造や技術選定の経緯 |
| **Solution: 開発者目線の外側** *(外部 I/F 設計)* | **`contract`** | 外部境界の厳密な約束 | REST API・MCP・CLI・ファイル形式の入出力スキーマとエラー規約 ＋ 契約テスト (`<Test level="contract">`) | UI の見た目や内部処理手順 |
| **Solution: 内側** *(全体構成〜内部設計)* | **`design`** | 全体地図〜特定機能の作り方（現行版） | 全体アーキテクチャ・テスト戦略（`scope: system` → `map` 常時投入）および機能別モジュール構成・データフロー・`<SourceRef>` | 過去の棄却案の長文比較、関数内の擬似コード |
| **判断ログ** *(設計経緯)* | **`decision`** | なぜそれを選んだか（重い ADR） | 全体に関わる重い判断の結論 (`<Decision summary="...">`)、決定日 (`date`)、代替案比較・トレードオフ（基本追記型）。※ 機能固有の局所判断は `design`/`spec` 内にインライン `<Decision>`（マイクロ ADR）で記述 | 現行の詳細な内部設計 |
| **解説** *(マニュアル)* | **`guide`** | 人間向けの手順・書き方 | セットアップ、日常運用、ショートカット、執筆ガイド（Informative） | 必須仕様や不変制約 |

## 2. `goal` の定義と書き方ルール（確定）

ISO/IEC/IEEE 29148（BRS / StRS）・Amazon Working Backwards（PR/FAQ）・Impact Mapping（Why / Who / How）・Basecamp Shape Up・KAOS（Goal Refinement Tree）を踏まえ、`goal` は **客側（Problem Space）の「芯」と「達成したい状態」** を書く場所とする。

### 2.1 新 Type (`vision`) は増やさず、最大 2 階層で構造化する

- **Root Goal（1 枚・`derives` なし）**: プロジェクト全体の対象アクター・全体課題・目指す状態・Non-Goals を担う。
- **Sub-Goal（3〜6 枚・`derives: [goals/<root>]`）**: 解決したい **顧客の課題・価値テーマ** ごとに分割する。
- 3 階層以上に深くしない（管理コストと形骸化を防ぐ）。

### 2.2 分割軸と粒度の 3 ルール

1. **分割の軸は「機能」ではなく「課題・目指す状態（Problem / Outcome）」**
   - ✕ 悪い例: `goals/graph.mdx`, `goals/pdf-export.mdx`（機能名 → `spec` / `design` の単位）
   - ○ 良い例: `goals/human-comprehension.mdx`, `goals/ai-reproducibility.mdx`（誰の何を解決しどう変えたいか）
2. **本数の目安は Root 1 枚 ＋ Sub-Goal 3〜6 枚**
   - 1 枚だけだと全 `<Spec>` が 1 点に集中してグラフや `--scope goal:...` バンドルが機能しない。10 枚を超えたら細かすぎる（`spec` へ下ろす）。
3. **`goal` と `spec` の境界線（KAOS 実現可能性基準）**
   - **自動テスト (`expect(...)`) に直接書けない「目指す状態・価値（Outcome）」** → **`goal`**
   - **「When 〜, the system shall 〜」とテストで合否判定できる「振る舞い（Output）」** → **`spec`**

### 2.3 `goal` の統一フォーマット（Root Goal / Sub-Goal 共通）

Root Goal と Sub-Goal で型を分けず、**同じ 6 要素のフォーマット** で統一する（5・6 は該当がある場合のみ記載）。「〜を目指すプラットフォーム」のような宣伝文・ポエムは避け、**誰のどんな困りごとがどう変わっていれば達成か** を簡潔に言い切る。

1. **誰の課題か（Target Actors / Who）**: 漠然と「ユーザー」と書かず役割を具体化
2. **いま何が困っているのか（Problem Statement）**: 解決策をこっそり混ぜずに生の困りごとを書く（Root では全体課題、Sub-Goal では個別課題）
3. **どうなってほしいか（Desired Outcome）**: 機能を作ったことではなく、人の行動・状態がどう変わっていれば成功かを書く（Root では Sub-Goal への分解リンクもここに束ねる）
4. **成功のサイン（Success Signals）**: 定性・定量で「うまくいっている状態」を言語化
5. **やらないこと（Non-Goals / No-Gos）** *(任意)*: その Goal スコープで意図的に対象外にする領域
6. **不変制約（`<Constraint>`）** *(任意)*: その Goal 配下の仕様・設計で破ってはならないガードレール（`get_project_map` がすべての `goal` 文書から自動収集する）

## 3. `spec`・`contract`・`design`（`scope: system` 含む）の線引きと書き方ルール（確定）

日本の SIer 文化（工程・契約の引き継ぎ軸の「基本設計/外部設計」「詳細設計/内部設計」）と、海外・国際標準（ISO 29148 / ISO 42010 / C4 Model / arc42 / Google Design Doc / RFC / API Contract）の良さを取り込み、**「擬似コード化（書きすぎ）」と「曖昧すぎて AI レビューが発散する（書かなすぎ）」の両方を避ける** ために、この 3 Type（＋全体設計 `scope: system`）を明確に分離する。

### 3.1 日本の工程区分からの翻訳マップ

| 日本の区分 | 分解先（Documi Type） | 考え方 |
|---|---|---|
| 基本設計・外部設計：ユーザーから見た動き・体験・異常系 | **`spec`** | テストで合否判定できる観測可能な振る舞い（What）＋同居 `<Test>` |
| 基本設計・外部設計：外部 I/F の入出力・エラー規約 | **`contract`** | API / MCP / CLI / 共有ファイル形式の厳密な契約＋契約 `<Test>` |
| 基本設計・方式設計：システム全体構成・横断方針・テスト戦略 | **`design` (`scope: system`)** | HLD / C4 Level 1–2 相当の全体地図・依存境界・テスト戦略（`get_project_map` 常時投入） |
| 詳細設計・内部設計：機能単位の構造・データフロー・状態 | **`design`** | C4 Level 3 相当の現行設計図 ＋ `<SourceRef>` で実コード接続 ＋ 局所判断はインライン `<Decision>` |
| 詳細設計・RFC：全体に関わる代替案比較・なぜそれを選んだかの経緯 | **`decision`** | 追記型の ADR ログ ＋ `<Decision>` 結論 |
| 詳細設計：関数内の `if`/`for`・変数名・細部ロジック | **書かない** | C4 Level 4 はコード・型・テストが正。擬似コードは陳腐化と AI 劣化を招く |

### 3.2 各 Type の責務と AI レビューでの位置づけ

1. **`spec`（外側の振る舞い・要件＋同居 `<Test>`）**
   - **書くこと**: ユーザー・外部から観測できる振る舞い、画面体験、非機能要件、**異常系・境界条件**（EARS 構文の `<Spec>`）および同居する保証シナリオ（`<Test verifies="..." level="...">`）。
   - **書かないこと**: 内部クラス構造、アルゴリズム手順、詳細な JSON ペイロード定義（それは `contract`）。
   - **AI レビューでの扱い**: **厳密な判定基準（正）**。仕様逸脱・異常系漏れは要修正。
2. **`contract`（外部境界の厳密な契約）**
   - **書くこと**: REST API・MCP ツール・CLI コマンド・外部共有ファイル形式の **正確な入出力スキーマ、引数、ステータスコード、エラー規約、事前/事後条件、副作用、冪等性** と契約テスト（`<Test level="contract">`）。
   - **書かないこと**: UI の見た目や内部処理手順。
   - **AI レビューでの扱い**: **厳密な判定基準（正）**。型・スキーマ・エラーコード・副作用の不一致は要修正。
3. **`design`（`scope: system`：システム全体の地図・横断ルール・テスト戦略）**
   - **書くこと**: システム全体のレイヤー構成、モジュール間の依存方向ルール、横断的関心事（パス解決・セキュリティ・エラー方針・純粋領域と副作用領域の分離・テスト戦略と品質ゲート）、技術スタック全体像。基本 1〜2 枚に収めて `get_project_map` へ常時投入。
   - **書かないこと**: 個別機能の細かいデータフローやコンポーネント内部設計。
   - **AI レビューでの扱い**: **厳密な判定基準（正）**。レイヤー違反・依存方向違反・横断ルール違反は要修正。
4. **`design`（機能別の現行内部設計）**
   - **書くこと**: 機能領域ごとのモジュール分割、データフロー、状態遷移、キャッシュ/同期、内部 DB 物理設計、純粋計算と副作用の境界 ＋ 実コードへの **`<SourceRef>`**（`satisfies` で `spec` に接続）。機能固有の局所判断や地雷回避理由はインライン `<Decision>`（マイクロ ADR）として同居させる。**常に最新の現行版へ上書き更新**。
   - **書かないこと**: 関数内部の擬似コード（`if`/`for` の日本語訳）、全体に関わる重い代替案比較（それは独立 `decision`）。
   - **AI レビューでの扱い**: **構造ガイド**。`spec`・`contract`・`design (scope: system)` を満たす範囲での好みの細部リファクタを無限指摘しない。大きな構造変更時は `design` も同期更新する。

### 3.3 契約による設計（DbC）と純粋関数／副作用の置き場所

手続き的な擬似コードの代わりに **事前条件・事後条件・不変条件・副作用の範囲** を宣言的に書くことで、実装の自由度を保ちつつ AI レビューを収束させる。

| 観点 | 主な記述先 | 記述内容の例 |
|---|---|---|
| **システム全体の技術・運用不変制約** | `design` (`scope: system`, `<Constraint>`) | 任意 JS 実行禁止、`src/core/` フレームワーク非依存、パストラバーサル拒否、未リリース方針（`get_project_map` が `systemConstraints` として常時収集） |
| **ドメインの不変条件** | `domain` (`<Constraint>`) | Doc ID は POSIX 相対パス、承認状態と実現状態は独立した 2 軸 |
| **外部境界の事前・事後条件・副作用** | `spec`（振る舞い）/ `contract`（厳密 I/F） | 入力制約と違反時エラー、出力保証、どの永続状態だけを書き換えるか、冪等性 |
| **純粋領域 vs 副作用領域の方針** | `design` (`scope: system`) | Functional Core（純粋計算）と Imperative Shell（FS/DB/HTTP 副作用）の境界ルール |
| **個別モジュールの純粋性・副作用** | `design` | どのモジュールが純粋関数で、どこが外部 I/O・キャッシュ・SSE 配信を行うか |

### 3.4 迷いやすい 3 大要素（UI 画面設計・DB スキーマ・API スキーマ）の配置

| 要素 | 置き場所 | 切り分け基準 |
|---|---|---|
| **API スキーマ** *(REST / MCP / CLI / イベント)* | **`contract`** | 外部との契約そのもの。型・エラーコード・事前/事後条件・副作用まで厳密に書く |
| **DB スキーマ / 永続データ** | 概念・関係・不変条件 → **`domain`** / 外部共有形式（`reviews.json` 等）→ **`contract`** / アプリ内部専用の物理テーブル・インデックス → **`design`** | 外から読まれる形式は壊すと外部が壊れるため `contract`、内部専用の物理設計・正規化は `How` なので `design` |
| **UI 画面設計** | 画面一覧・遷移・操作への振る舞い・空/エラー/ローディング状態・ショートカット → **`spec`** / レイアウト構造・コンポーネント分割・状態管理・Code Splitting → **`design`** | テスト可能なユーザー体験の約束は `spec`、フロントエンドの組み立て方は `design` |

### 3.5 人間向け図解と AI コンテキスト制御（今後の構想）

人間が深く理解するための図解（Mermaid・ワイヤーフレーム・比較表等）を充実させつつ、AI のコンテキスト圧迫やノイズ化を防ぐため、MDX の安全な宣言的コンポーネントと AI 除外制御を組み合わせる方向で拡張する。

<Note id="note.human-only-tag" intent="idea">
  人間向けの大きなレイアウト図・ワイヤーフレーム・比喩的な解説などを囲む宣言的タグ（例: `<HumanOnly summary="画面レイアウトの概念図">`）の導入を検討中。Web UI や HTML/PDF Export では人間向けにリッチに描画し、MCP レスポンスでは既定で 1 行サマリへ圧縮・除外する（小さい状態遷移図や ER 図など AI にも有益な Mermaid はそのまま残せるオプトイン方式）。あわせて `<DecisionTable>`（条件×結果の真理値表）等の宣言的ビジュアルコンポーネント拡張も候補とする。
</Note>

## 4. `domain` の定義と書き方ルール（確定）

DDD（Domain-Driven Design）のユビキタス言語・概念モデル・ドメイン不変条件・Bounded Context を踏まえ、`domain` は **技術スタックや UI が変わっても揺るがない「共通語彙・概念・状態・不変条件」の地図** を書く場所とする（AI コンテキストへ常時投入される）。

### 4.1 `domain` 判定の 2 つの境界テスト

1. **紙とペンテスト（Pen-and-Paper Test）**: システムを使わず紙とペンだけで業務を回しても成り立つ概念・言葉・ルールなら `domain`。
2. **技術差し替えテスト**: DB（PostgreSQL → MongoDB）や UI（Web → CLI）を差し替えたときに書き換えが必要になる内容（物理テーブル名、`VARCHAR(255)`、`created_at`、JSON ペイロード、画面ボタン名）が混ざっていたら、それは `domain` からの漏れ（`contract` または `design` へ移す）。
   - ※ Documi では `<TermDef symbols="src/...#Symbol">` を使うことで、**本文の概念説明は技術非依存に保ちつつ、`symbols` 属性だけで実コードの型へ安全に橋渡しする**。

### 4.2 `domain` に書くべき 5 要素

1. **ユビキタス言語（`<TermDef>` ＋ `symbols`）— 1 概念 ＝ 1 正準表記**: 名詞だけでなく重要な動詞の意味（例：「承認する」「検証済みになる」）も定義し、コードシンボルと対応づける。**同じ概念を日本語と英語でバラバラに表記すると人間にも AI にも混ざるため、本文中は正準 ID（`<TermDef id="...">`）の 1 表記で統一する**。`aliases` は `documi search` の検索同義語ヒット専用とし、Web UI の自動リンク対象には含めない（日常語への誤爆と表記ブレを防ぐため）。
2. **禁止語・混同注意（Anti-Terms）**: AI や人間が混ぜやすい類義語・使ってはいけない言葉（例：`delete` と `cancel` の違い、曖昧な単一 `status` の禁止）を明示し、命名ブレとレビュー発散を防ぐ。
3. **概念モデルと関係（Conceptual Model）**: 物理 DB スキーマではなく、概念同士の意味的な関係・多重度・一貫性の単位（集約）。
4. **ライフサイクル・状態遷移（State Machines）**: 取り得る状態と許可される遷移／禁止される遷移（Mermaid `stateDiagram-v2` で 1 枚に表すと人間にも AI にも効く）。
5. **ドメイン不変条件（Always-Valid Invariants）**: 単なる入力形式バリデーション（→ `contract` / `spec`）ではなく、「破ったら不正な状態が生まれてしまう本質ルール」を明記する。

### 4.3 ファイル分割と AI レビューでの位置づけ

- **小〜中規模**: `domain/glossary.mdx`（用語集＋禁止語）＋ 必要なら `domain/domain-model.mdx`（概念関係・状態遷移・不変条件）の **1〜3 枚**。
- **大規模**: 同じ単語が領域ごとに違う意味を持ち始めたら、Bounded Context 単位で `domain/<context>.mdx` へ分割し、「この語彙が有効な範囲」を明示する。
- **AI レビューでの扱い**: **厳密な判定基準（正）**。用語・命名の揺れ、禁止語の使用、不正な状態遷移、ドメイン不変条件の違反は要修正。

## 5. `decision`（ADR）の定義と書き方ルール（確定）

MADR 4.0・Y-Statement などの ADR 標準および AI 時代の運用知見を踏まえ、`decision` は **「なぜそれを選び、何を捨てたか（Big Why & Why not）」を 1 決定 1 ファイルで残す追記型の判断ログ** とする。

### 5.1 書くべき判断（ASR）vs 書かない判断（ADR Fatigue 回避）

| 書くべき判断（1 ファイル＝1 決定） | 書かない判断 |
|---|---|
| 後戻りが高い構造判断（DB・フレームワーク・通信方式・認証・主要 UI 構造など） | 変数名・ローカル関数分割・小さな util 選定など後戻りが安い実装細部（→ PR / コードコメント） |
| 複数の有力な選択肢とトレードオフがあり、将来「なぜ別案にしないの？」と蒸し返されやすい判断 | 選択肢が事実上 1 つしかない当たり前の実装作業 |
| 横断的関心事のルール化（セキュリティ・エラー方針・依存境界） | 機能要件そのもの（→ `spec`） |
| 意図的な割り切り・技術的負債の受け入れ（将来の見直し条件つき） | 日常手順・セットアップ（→ `guide`） |

### 5.2 記述ルールと `design` との棲み分け

- **`design` との違い**: `design` は「今どう組まれているか（How）」の現行版（上書き更新）、`decision` は「なぜそれを選び何を捨てたか（Why）」の履歴（追記型）。1 つの `design` から重要な判断だけ 0〜数本の `decision` を切り出す。
- **メタデータ・命名**: frontmatter に **`date: YYYY-MM-DD`**（MADR 4.0 準拠・降順ソート）を付与し、ファイル名は **`decisions/YYYY-MM-<slug>.mdx`** を推奨する（並列 AI 作業での連番衝突を回避し、目次一覧は Web UI / MCP が自動生成する）。
- **構成（規模に応じて Minimal / Full を使い分け）**:
  1. **`<Decision id="dec.xxx">`（必須・2〜4 行）**: Y-Statement 調で「文脈・採用案・棄却案・狙い・受け入れるトレードオフ」を凝縮する。`get_project_map` で AI へ常時投入されるため、最小トークンで既決事項の蒸し返し（Re-litigation）を防げる。
  2. **背景・判断軸（Context / Drivers）**: 直面していた制約や課題。
  3. **検討した選択肢と棄却理由（Options Considered）**: 特に **捨てた案と理由** を明記する。
  4. **影響・将来の見直し条件（Consequences）**: 受け入れるマイナス面と再検討トリガ。
- **更新ルールと AI レビューでの扱い**:
  - 確定後は基本 **追記型（不変）** とし、方針を覆すときは新 ADR に `supersedes: [decisions/<old>]` を付けて記録する（検討中ドラフト段階の加筆は可）。
  - AI レビューでは **`<Decision>` を判定基準（正）** とし、既決の棄却案を蒸し返さない。ただし要件や前提が大きく崩れた場合は「`supersedes` の検討」として提案してよい（古い ADR への盲目的な過適合を防ぐ）。

## 6. 検証戦略と仕様同居 `<Test>` の書き方ルール（確定）

ISO/IEC/IEEE 29119 と **証拠主義（Prove It Works）** および **Living Documentation / BDD** の原則を踏まえ、独立した `verification` Type は設けず、**全体テスト戦略は `design` (`scope: system`) に置き、機能ごとの保証シナリオは `<Spec>` と同じ `spec` / `contract` ファイル内に `<Test id="..." verifies="<spec.id>" level="...">` として同居** させる。

### 6.1 構造と責務分担

- **全体テスト戦略（例: `designs/testing-strategy.mdx`, `scope: system`）**: テストピラミッド・証拠主義（Red → Green / 実測）・品質ゲート（CI コマンド群）・全体 Out of Scope を書く（`get_project_map` で AI へ常時投入）。
- **仕様同居 `<Test>`（`specs/*.mdx` / `contracts/*.mdx` 内）**: 各 `<Spec>` に対して「絶対に壊れてはいけない振る舞い・境界値・異常系・過去バグのリグレッション条件」を **宣言的な保証シナリオ** として同居させる（`level` は `unit | integration | e2e | contract | manual`）。
- **ユニットテスト 1 件ごとのドキュメント化はしない**: 個別関数の細かいアサーションまで手書きコピーするとテストコードとの二重管理・ドリフトを招く。詳細検証と合否証明は `tests/*.test.ts` の `test('[<spec.id>] ...')` ＋ JUnit XML（`Realization`）に任せる。

### 6.2 書くこと vs テストコードに任せること

- **書くこと**:
  1. **宣言的な保証シナリオ（`<Test verifies="...">`）**: クリック手順など Imperative な操作列ではなく、前提・事象・保証される結果を宣言的に書く。
  2. **テスト戦略と層の役割分担（`designs/testing-strategy.mdx`）**: Unit / Integration / E2E / 静的検査の使い分け。過剰モックや定数を写しただけの形骸テスト（Slop Test）を禁止する方針。
  3. **証拠の基準（Prove It Works）**: 「ビルド通過だけ」や AI の自己申告を完了と認めないルール。バグ修正時は修正前の失敗再現（Red → Green）を確認する。
  4. **意図的な対象外（Out of Scope）**: AI レビューが際限なく過剰テストを要求するのを防ぐ境界線。
- **書かないこと**:
  - ユニットテスト 1 件ごとの手順書・クリック手順・テストデータ羅列・アサーション全文（→ テストコードへ）
  - 手動の合否チェック表（→ `test('[spec.id] ...')` と JUnit XML から `Realization` が自動算出される）
- **AI レビューでの扱い**: **品質ゲートと受入基準の判定基準**。テスト戦略違反・品質ゲート未達・保証シナリオ（`<Test>`）の抜けは要修正。意図的 Out of Scope への過剰テスト要求はしない。

## 7. `guide` の定義と書き方ルール（確定）

Diátaxis の 4 象限のうち、Reference は `contract` / `domain` / `spec`、Explanation は `goal` / `design` / `decision` が担うため、`guide` は **Tutorials（最初の一歩）と How-to guides（目的別の手順書・運用プレイブック）** に専念する（Informative：参考情報）。

- **書くこと**: セットアップ手順（Getting Started）、日常ワークフロー、ショートカット、執筆ガイド、開発・検証ランブック、トラブルシューティング（**1 ページ 1 目的**）。
- **書かないこと**: **必須仕様（`<Spec>`）・不変制約（`<Constraint>`）・検証の合格基準そのもの**。`guide` は AI 常時投入対象外かつ `Realization` 対象外のため、仕様をここに混ぜると必ず見落とされる。
- **AI レビューでの扱い**: 判定基準（正）ではないが、CLI・UI・運用手順を変更した際に `guide` が陳腐化していれば同期更新を提案する対象。

## 8. 全体知識マップ：マクロ（`docs/`）〜 ミクロ（コード・テスト・Git）

コード・テスト・コミット・コメントの責務分離（コード＝How / テスト＝What / コミット＝Why / コメント＝Why not）と Documi の 7 Type を一本の軸でつなぐと、プロジェクト内のあらゆる知識の置き場所が一意に決まる。

| 層 | 置き場所 | 担う問い | 主な役割と境界 |
|---|---|---|---|
| **入口（最小）** | **`AGENTS.md`** | **Entry / Uninferable Commands** | リポジトリを見ても推測できない最小限の不変コマンド・禁止事項・`documi` 入口のみ（肥大化させない） |
| **マクロ (`docs/`)** | `goal` | **Purpose / Non-Goal** | なぜ作るか、誰のどんな課題か、やらないこと、不変制約 |
| **マクロ (`docs/`)** | `domain` | **Vocabulary / Invariants** | 共通言語・禁止語（`antiTerms`）・概念モデル・状態遷移・ドメイン不変条件 |
| **マクロ (`docs/`)** | `spec` / `contract` | **What / Interface / Test** | 外部から観測できる振る舞い・異常系・厳密な I/F 契約 ＋ 同居 `<Test>` 保証シナリオ |
| **マクロ (`docs/`)** | `design` | **Overview / Structure / Local Why** | 全体地図・テスト戦略（`scope: system`）、機能単位の構成と `<SourceRef>`、局所判断のインライン `<Decision>` |
| **マクロ (`docs/`)** | `decision` (ADR) | **Big Why & Why not** | 全体に関わる後戻りコストの高い構造選択の理由と棄却案（`<Decision>`） |
| **マクロ (`docs/`)** | `guide` | **How to Use / Operate** | 人間向けチュートリアル・日常運用手順・プレイブック（Informative） |
| **ミクロ (Git/Code)** | **コミットログ / PR** | **Change Why** | 個別の変更・バグ修正を行った今回の動機 |
| **ミクロ (Git/Code)** | **コードコメント** | **Local Why not** | 一見遠回りな数行について「あえて別解を取らない局所的防衛理由」（`<Decision>` ID 参照） |
| **ミクロ (Git/Code)** | **テストコード** | **Executable What** | 実行可能な仕様・リグレッションの証明（`test('[spec.id] ...')`・具体的アサーション） |
| **ミクロ (Git/Code)** | **プロダクションコード** | **Concrete How** | 実際に動く関数・型・アルゴリズム |

### 8.1 書く／書かないの境界判定（2 つのテストと公開シンボルの扱い）

「擬似コードは書かない」だけでは、本来 docs に書くべき重要な条件分岐（エラー処理・フォールバック・セキュリティ拒否）まで抜け落ちたり、逆にコード内の細かな手順まで書きすぎて陳腐化したりする。迷ったときは以下の **2 つのテスト** で判断する。

1. **リファクタリングテスト**: そのロジックの書き方（データ構造・ループ・内部ヘルパー分割）を変えても、外部の振る舞い・契約・テスト結果・不変条件が一切変わらないなら **書かない**。変わるなら **宣言的に（EARS・表・状態図で）書く**。
2. **AI 差し戻しテスト**: 別の AI に `docs/` だけ渡して再実装させたとき、そこが違っていたら「仕様違反だ」とレビューで差し戻すものは **書く**。差し戻さない実装細部は **書かない**。

| 対象 | docs に書く？ | 置き場所と正しいやり方 |
|---|---|---|
| **ドメインルール・状態遷移・不変条件** | **書く** | `domain` / `spec`（状態図・表・EARS） |
| **エラー・拒否条件・フォールバック・優先順位** | **書く** | `spec` / `contract`（決定表・EARS） |
| **過去の地雷・障害回避の防御理由（Chesterton's Fence）** | **必ず書く（3 点セット）** | ① `design`/`spec` 内インライン `<Decision>`（なぜこの防御が必要か）＋ ② 同居 `<Test>` ＋自動テスト（消すと落ちる）＋ ③ コード近傍の 1 行理由コメント |
| **後戻りコストが低い未確定の仮置き** | **仮置きとして明記** | `<Note intent="idea">` に仮定と確認事項を明記して仮実装し、Overview に自動集約して後から確定する（後戻りコストが高い仕様は先に人間へ確認する） |
| **公開境界のシンボル（export された `class` / `interface` / `type` / 主要関数）** | **把握できるようにする** | **手書きコピペせず**、`<SourceRef file="..." mode="exports" />`・`<SourceRef symbol="..." />`・`<TermDef symbols="file#Symbol" />` で実コードへ AST 紐づけする（リネーム時は `documi check` で即検知） |
| **モジュール境界・データフロー・副作用の分離** | **書く** | `design`（Mermaid 図＋責務表＋`<SourceRef>`） |
| **非公開ヘルパー・関数内の `if`/`for` 手順・一時変数の型** | **書かない** | コードとテストに任せる |
| **`AGENTS.md` / `.agents/skills/` だけへの方針メモ** | **単独では書かない** | プロダクト方針・不変制約・判断基準は必ず `docs/` に書き、`AGENTS.md` は極小（推測不能なコマンドと `documi` 入口のみ）に保つ |

### 8.2 ドキュメント更新トリガー表（PR 完了前セルフチェック）

`spec` と `contract` だけ更新して `design` / `decision` / `guide` が置き去りになるのを防ぐため、以下の変更を行ったら同じ PR 内で同期する。

| 今回の変更内容 | 必ず同期するドキュメント |
|---|---|
| 新しいサブシステム・主要モジュールの追加・境界変更 | 全体設計（`design` / `scope: system`）＋機能別 `design`（`satisfies`＋`<SourceRef>` / `mode="exports"`） |
| 後戻りコストが高い全体技術選定・トレードオフ判断 | 独立 `decision`（ADR 1 ファイル＋`<Decision summary="...">`＋棄却案）。機能固有の局所判断・過去の地雷回避は `design`/`spec` 内インライン `<Decision>`（マイクロ ADR） |
| 新しい振る舞い・制約・エラー・フォールバック・リグレッション防御の追加変更 | `spec`（`<Spec>` ＋ `<Test verifies="..." level="...">`）＋ 外部 I/F 変更なら `contract` |
| 1 つの `spec` に別 Capability が相乗りした／`spec` の `<Spec>` や `design` の `satisfies` 辺が 10 件を超えた | 機能領域（Capability）単位で `documi scaffold` により分割（`documi check` の `bloated-spec-doc` / `overloaded-hub-doc` で確認） |
