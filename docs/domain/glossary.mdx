# ドメイン用語集 (Living Glossary)

Documi の仕様・設計・ソースコードで共有される共通語彙を定義する。

<TermDef id="Artifact" aliases="ドキュメント, 文書" antiTerms="requirement" symbols="src/core/types.ts#Document, src/core/types.ts#ArtifactType">
  Documi が管理する Markdown / MDX ファイル単位。拡張子を除いた POSIX 相対パスが ID となり、`goal` / `decision` / `domain` / `spec` / `contract` / `design`（全体設計は `scope: system`） / `guide` の 7 種類の Type を持つ。
</TermDef>

<TermDef id="SemanticBlock" aliases="セマンティックブロック, ブロック" symbols="src/core/types.ts#SemanticBlock, src/core/types.ts#BlockKind">
  MDX 内の `<Spec>` / `<Constraint>` / `<Decision>` / `<Test>` / `<Note>` / `<TermDef>` で囲まれた意味単位。プロジェクト全体で一意なドット区切り ID と正規化 SHA-256 の `contentHash` を持つ。
</TermDef>

<TermDef id="GraphEdge" aliases="グラフエッジ, エッジ" symbols="src/core/types.ts#GraphEdge, src/core/types.ts#EdgeKind">
  ドキュメントまたはブロック間の有向辺。トレーサビリティの背骨 (`derives` / `satisfies` / `verifies` / `supersedes`) と、本文リンク・用語参照から自動抽出される `mentions` の 5 種で構成される。
</TermDef>

<TermDef id="SourceRef" aliases="ソース参照" symbols="src/core/source.ts#resolveSourceSymbol, src/core/types.ts#SourceRefDecl">
  ドキュメント内に実ソースコードの公開シンボル一覧（`mode="exports"`）や主要シンボル定義を埋め込む仕組み。<Term name="ProjectRoot" /> からの相対パスを指定し、`@ast-grep/napi` (tree-sitter) で動的に解決するため、コードを複製せず常に最新を反映する。仕様・契約と実装の疎結合を保つため、原則 `design` 文書内に閉じて使用する。
</TermDef>

<TermDef id="ProjectRoot" aliases="プロジェクトルート" symbols="src/server/store.ts#DocsStore, src/core/config.ts#resolveProjectPaths">
  ソースコード参照（`<SourceRef>`・`<TermDef symbols>`）および `@implements` / `@verifies` 走査の基準ディレクトリ。既定は `docs/` の親ディレクトリで、`.documi.json`・`--project`・`DOCUMI_PROJECT_ROOT` で上書きできる。ルート外参照やシンボリックリンク脱出は拒否される。
</TermDef>

<TermDef id="DocsIndex" aliases="インデックス" symbols="src/core/types.ts#DocsIndex, src/core/loader.ts#loadDocuments">
  `docs/` ディレクトリ全体を再帰走査して構築される共通データモデル。文書・ブロック・用語・グラフエッジ・鮮度メタデータ・問題一覧を一元管理する。
</TermDef>

<TermDef id="ReviewRecord" aliases="承認記録, レビュー記録" symbols="src/core/types.ts#BlockReviewRecord, src/core/reviews.ts#approveBlock">
  `docs/guard/reviews.json` に保存されるブロック単位の人間承認レコード。承認時の SHA-256 ハッシュ・Git コミット SHA・上流ハッシュ・任意の確認メモ（`note`）を保持し、MDX 本文とは物理分離される。
</TermDef>

<TermDef id="ReviewStatus" aliases="レビュー状態, 承認状態" symbols="src/core/types.ts#ReviewStatus">
  ブロック単位の人間承認状態（`unreviewed` / `approved` / `stale`）。`stale` は承認後に自身の本文 `contentHash` が変化した状態を指す。実装・検証状態である <Term name="Realization" /> とは完全に独立した 2 軸として扱う。
</TermDef>

<TermDef id="Suspect" aliases="suspect, 上流変更通知" symbols="src/core/reviews.ts#applyReviewsAndSuspects">
  承認済みブロック自身は未変更だが、参照先の上流ブロック（`derives` 等）が承認時点から更新されたことを示す軽量な波及通知フラグ。`stale`（自身の本文変更）とは異なり、`realization: drifted` や `documi check --strict` のエラーには昇格させず参考通知に留める。
</TermDef>

<TermDef id="Stability" aliases="安定度, stability" symbols="src/core/types.ts#Stability">
  <Term name="SemanticBlock" /> の成熟度（`evolving` / `stable` / `deprecated`）。`--review-gate stable` 指定時は `stability="stable"` な `normative` ブロックのみが承認ゲートのエラー対象になる。
</TermDef>

<TermDef id="Intent" aliases="意図区分, intent" symbols="src/core/types.ts#SpecIntent, src/core/types.ts#NoteIntent">
  ブロックの拘束力区分。`normative` は必須仕様（Goal 到達性・<Term name="Realization" />・承認ゲート対象）、`informative` は参考補足、`idea` は未確定の仮案・仮置き（Overview に自動集約）を表す。
</TermDef>

<TermDef id="DocsMount" aliases="マウント, マルチドキュメント" symbols="src/core/types.ts#DocsMount">
  モノレポ等で複数パッケージの `docs/` ディレクトリを単一グラフへ統合する設定単位（`.documi.json` の `docs` 配列）。名前付きマウントは `<id>/...` の文書 ID 名前空間を持ち、`guard/reviews.json` はマウント単位で分散保存される。
</TermDef>

<TermDef id="Realization" aliases="実装状態" antiTerms="draft, progress" symbols="src/core/types.ts#RealizationSummary, src/core/trace.ts#enrichWithRealization">
  コードアンカー (`@implements` / `<SourceRef>`)・テスト (`@verifies` / `test("[id]")`)・JUnit 実行結果・PR 情報から完全自動で算出される仕様の実現状態 (`unimplemented` / `in-progress` / `implemented` / `verified` / `drifted`)。
</TermDef>

<TermDef id="Bundle" aliases="まとめ出力, バンドル" symbols="src/core/bundle.ts#resolveBundleDocuments, src/server/pdf.ts#renderPdfFromUrl">
  複数ドキュメント（全文書・ディレクトリ配下・Goal 関連一式・任意選択）を表紙・自動目次・ページ内アンカー・全タブ展開付きの 1 冊の HTML / PDF として出力する仕組み。
</TermDef>

<TermDef id="HybridRAG" aliases="ローカル Hybrid RAG, セマンティック検索, グラフ検索" symbols="src/core/retrieval.ts#retrieveContext, src/core/hybrid-retrieval.ts#retrieveContextHybrid, src/core/vector-store.ts#syncVectorIndex">
  日本語・英語・コード識別子トークナイザによる BM25 検索と `<TermDef aliases>` 自動同義語展開に、任意のローカル Embedding（Ollama / OpenAI 互換 HTTP）と `bun:sqlite` `contentHash` 差分キャッシュを RRF で統合し、さらに明示グラフに沿って上流 Goal・`<Decision>` 結論（マイクロ ADR 含む）・`<SourceRef>` まで 1 発で収集する検索基盤。
</TermDef>

<TermDef id="AgentSkills" aliases="エージェントスキル, スキル" symbols="src/core/init.ts#initDocumiProject">
  `documi init` で `<projectRoot>/.agents/skills/` に生成される AI エージェント向け標準手順書 5 種（日常運用 `documi`・上流設計 `documi-design`・既存コード導入 `documi-bootstrap`・対話レビュークイズ `documi-review`・再現性監査 `documi-audit`）。`AGENTS.md` と競合せず、CLI ベースで自己完結したワークフローを提供する。
</TermDef>

<TermDef id="StaticSite" aliases="静的サイト, 静的書き出し" symbols="src/server/site.ts#buildStaticSite">
  `documi build-site` によって生成される、サーバー不要・読み取り専用の Web UI 配布物。事前計算した JSON・ハッシュ索引化コード・`HashRouter` 対応 SPA を含み、任意の静的ホスティングでそのまま配信できる。
</TermDef>

<TermDef id="Provisional" aliases="仮置き">
  <Term name="ReviewCard" /> で人間が選んだ選択肢を暫定適用して先に進める仕上げ状態。確定ではないため覆せる。見直しは義務ではなく、必要になったとき（その上に大きく建てるとき・問題が起きたとき）に行う。仮置きできないと判定されたカードでは仮置きボタン自体が表示されない。
</TermDef>

<TermDef id="Committed" aliases="確定">
  <Term name="ReviewCard" /> で人間が選んだ選択肢を確定する仕上げ状態。その方向の判断を人間が確定したことを示し、後続の「記録に残す」操作で `<Decision>` として docs に蒸留できる。「やらない」選択肢の確定も通常の確定として扱い、やらないと決めた記録が再検討の蒸発を防ぐ。
</TermDef>

<TermDef id="Incomprehensible" aliases="理解不能, 破損状態">
  <Term name="ReviewCard" /> で「意味がわからない」が押された状態。カードは破損し、決定も仮置きもできなくなる。問いや選択肢の説明が人間に通じなかった信号であり、カードの修理が必要なことを示す。
</TermDef>

<TermDef id="CardObjection" aliases="異議あり, 納得いかない">
  <Term name="ReviewCard" /> で「納得いかない」が押された状態の異議フラグ。進行は妨げない。前提や枠組みへの違和感の信号で、チャットでの修理経路につながる。人間が選択肢にないやり方を持っている場合は「他のやり方がある」書き込み選択肢を使う。
</TermDef>

## 混同しやすい言葉・使わない表現（Anti-Terms）

AI や人間が語彙を混同して仕様・実装・レビューがブレるのを防ぐため、以下の使い分けを徹底する。

| 避ける表現・混同 | 正しい用語・使い分け | 理由 |
|---|---|---|
| 単一の `status`（`draft` / `accepted` / `done` 等） | 人間承認は `ReviewStatus`（`unreviewed` / `approved` / `stale` + `suspect`）、実装進捗は <Term name="Realization" />（`unimplemented` 〜 `verified` / `drifted`） | 「承認されたこと」と「実装・テスト済みであること」を 1 軸に混ぜると未実装事故が起きるため |
| `requirement`（Type 名として） | **`spec`** | Artifact Type は 7 種に固定し、別名や後方互換エイリアスを持たない |
| `v1` / `v2` / `Phase X`（現行仕様内のラベル） | 現行の振る舞いとして直接記述（経緯は `decision` へ） | 未リリース期間中に世代ラベルを残すと、AI が古い挙動と現行挙動を取り違えるため |
| `.mdx` からの相対パス（`<SourceRef>` 内） | <Term name="ProjectRoot" /> からの POSIX 相対パス | 文書ディレクトリを移動しても参照が壊れないようにするため |
| コード全文のベクトル DB 化（RAG 対象として） | `docs/` のみを検索対象とし、コードは `<SourceRef>` と `@implements` で辿る | ソースコードを別ベクトル化すると二重管理と陳腐化を招くため |

概念同士の関係・状態遷移・ドメイン不変条件は [ドメインモデル](./domain-model.mdx) を参照。

<TermDef id="ReviewCard" aliases="判断カード, レビューカード, カード" antiTerms="Decision Card" symbols="src/core/cards.ts#StoredCard, src/web/components/ReviewCardsLayout.tsx#ReviewCardsLayout">
  AI が作業中の判断点で書き出し、人間が選択肢の比較と4つのボタン（意味がわからない・納得いかない・<Term name="Provisional" />・<Term name="Committed" />）だけで判断する入力界面。問い・状況となぜ今か・何もしないとどうなるか・具体例・選択肢（得るもの/失うもの付き）を持ち、選択肢には固有の「やらない」選択肢1つと人間が一行で書き込める「他のやり方がある」を含む。`<Decision>` は確定した判断の記録であり、Review Card は判断を求めるための入力界面である。操作状態は `.documi/cards/` に永続化され、確定内容は「記録に残す」操作で `<Decision>` として docs に蒸留される。蒸留済みカードは操作対象として一覧から消える。
</TermDef>
