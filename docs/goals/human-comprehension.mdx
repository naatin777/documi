# 人間が読んでシステムとコードまで深く理解できる

## 誰の課題か（Target Actors）

- AI と協働してプロダクトを育てる開発者・テックリード
- プロジェクトに途中参加し、仕様とソースコードの対応を短時間で把握したいメンバー
- 仕様書を 1 冊の資料としてオフライン・外部レビューで読みたい関係者

## いま何が困っているのか（Problem Statement）

1. **AI がコードや文書を大量生成するほど、人間の理解とレビューが追いつかない（理解負債・レビュー負債）**: 長大な Markdown や巨大な PR 差分を渡されても、「何が確定仕様で何が未確定の仮置きか、Before/After で何が変わったのか、どのコードが実体なのか」を追いきれない。
2. **ドキュメントとソースコードが別世界に分断されている**: 用語の意味を文章で読んでも、実際のソースコード上のどの型・関数がそれに対応し、どの仕様書で使われているのかを毎回 grep で探す手間がかかる。
3. **複数文書をまたいだ全体像や関係が見えにくい**: 仕様書と設計書や ADR を見比べたいときにタブを行き来して見失い、プロジェクトが大きくなると文書同士の依存関係も頭に入らなくなる。
4. **外部共有や通読のためにまとめる手段がない**: 個別の Markdown ファイルは Git 上にあっても、Goal や機能単位で 1 冊の仕様書として通読・印刷・PDF 共有するのが面倒。

## どうなってほしいか（Desired Outcome）

- 人間が Web UI を開いて上から下へ（`Goals → Domain → Specs → Contracts → Designs → Decisions → Guides`）読むだけで、**プロジェクトの目的から用語・仕様（＋同居する `<Test>` 保証シナリオ）・設計・意思決定までが物語として頭に入る**。
- 本文中の用語や `<SourceRef>` から **実ソースコードの最新の型・関数定義、禁止語（`avoid`）、および参照元文書（Where Used）をその場で確認** でき、ドキュメントがそのまま「ソースコード理解の地図」として機能する。
- 未確定の仮案・仮置き（`intent="idea"`）は Overview に自動集約され、関連する仕様書・設計書・ADR は **並べて読み比べ（Side-by-Side プレビュー）** や **ネットワークグラフ探索** でサクッと俯瞰できる。
- PR も Before / After の表・Mermaid 図・レビュー順 Walkthrough で構造化され、必要な仕様範囲は **表紙・目次付きの 1 冊の HTML / PDF として即座に書き出せる**。

## 成功のサイン（Success Signals）

- 初めてリポジトリに触れる人間でも、コードを隅々まで grep する前に `docs/` の閲覧と用語ホバー・グラフ探索だけで主要コンポーネントと設計意図を説明できる。
- レビュー時に「この仕様に対応する設計書と ADR はどれか」を 1 クリックで並べて確認できる。
