# 人間が読んでシステムとコードまで深く理解できる

## 誰の課題か（Target Actors）

- AI と協働してプロダクトを育てる開発者・テックリード
- プロジェクトに途中参加し、仕様とソースコードの対応を短時間で把握したいメンバー
- 仕様書を 1 冊の資料としてオフライン・外部レビューで読みたい関係者

## いま何が困っているのか（Problem Statement）

1. **AI がコードや文書を大量生成するほど、人間の理解とレビューが追いつかない（理解負債・レビュー負債）**: 「動くしテストも通るが、なぜこうなっているか誰も説明できない」状態に陥り、肥大化した PR 差分の前でレビュアーが燃え尽きてゴム印 LGTM になってしまう。長大な文書を渡されても「何が確定仕様で何が未確定の仮置きか、前後で何が変わったのか、どのコードが実体なのか」を追いきれない。
2. **ドキュメントとソースコードが別世界に分断されている**: 用語の意味を文章で読んでも、実際のソースコード上のどの型・関数がそれに対応し、どの仕様書で使われているのかを辿る手間がかかる。
3. **複数文書をまたいだ全体像や関係が見えにくい**: 仕様書と設計書や判断記録を見比べたいときに画面を行き来して見失い、プロジェクトが大きくなると文書同士の依存関係も頭に入らなくなる。
4. **外部共有や通読のためにまとめる手段がない**: 個別の仕様ファイルはリポジトリにあっても、Goal や機能単位で 1 冊の仕様書として通読・印刷・共有するのが面倒。

## どうなってほしいか（Desired Outcome）

- 上流から下流（目的 → 用語 → 仕様・保証シナリオ → 契約 → 設計 → 判断理由 → ガイド）へ順に読むだけで、**システム全体像が物語として頭に入る**。
- 本文中の用語やコード参照から、**最新の型・関数定義、使ってはいけない表現、参照元文書をその場で確認** でき、仕様書がそのまま「ソースコード理解の地図」として機能する。
- 未確定の仮案・仮置きは一覧に自動集約され、関連する仕様書・設計書・判断記録は **並べて読み比べ** や **関係グラフ** で素早く俯瞰できる。
- 変更差分は視覚的な Before / After で把握でき、必要な仕様範囲は **表紙・目次付きの 1 冊の資料として即座に書き出せる**。

## 成功のサイン（Success Signals）

- 初めてリポジトリに触れる人間でも、ソースコードを隅々まで追う前に、仕様書の閲覧と用語・関係グラフの探索だけで主要コンポーネントと設計意図を説明できる。
- レビュー時に「この仕様に対応する設計書と判断理由はどれか」を 1 クリックで並べて確認できる。
