# AI がドキュメントだけで同じ挙動を再現できる

## 誰の課題か（Target Actors）

- 仕様書を読み込んで実装・リファクタ・テスト生成を行うコーディング AI エージェント
- 複数の AI セッションや異なるモデルを跨いで一貫した品質の実装を得たい開発者

## いま何が困っているのか（Problem Statement）

1. **曖昧さのまま「間違ったもの」を爆速で作ってしまう**: 人間にとって当たり前すぎて言わなかった暗黙の前提や境界条件・異常系が抜けていると、AI は立ち止まって質問せずにもっともらしい仮定で隙間を埋め、セッションごとに違う挙動を量産する。
2. **語彙ドリフトと車輪の再発明・古い API 誤用が起きる**: 共通語彙や禁止語（Anti-Terms）・既存ユーティリティの地図がないと、AI は勝手に類義語を発明し、既存の内部関数を見落として作り直し、さらに新しいライブラリや GitHub Actions を古い記憶で推測書きしてしまう。
3. **背景議論（ADR 等）が長くなるとコンテキストを圧迫する**: トレードオフや棄却案は人間には重要だが、そのまま全文を AI に渡すとコンテキストウィンドウを消費し、肝心の結論を見落としやすくなる。
4. **ファイル連番やフラット構成が並列 AI 作業と衝突し、文脈収集コストも高い**: 複数エージェントでの編集時に連番が衝突し、1 つの仕様を実装するたびに Goal・制約・ADR・用語・契約・設計を手動で集めて貼る手間がかかる。

## どうなってほしいか（Desired Outcome）

- **`docs/` だけを読めば、ほとんどの AI エージェントが同じ振る舞いのソフトウェアを再現できる** 粒度の仕様（`<Spec>` ＋同居する入出力保証 `<Test>`）・制約（`<Constraint>`）・契約（`contract`）・用語（`<TermDef>` ＋ `antiTerms`）が構造化されている。
- **段階的開示（Progressive Disclosure）** により、AI はまず `get_project_map` で Goal・`goalConstraints`（未リリース方針等）・全体設計（`design` / `scope: system`）・ドメイン不変条件・独立 ADR の `<Decision>` 結論・用語集だけを受け取り、実装対象ごとに `get_spec_context` / `search_documents (includeContext: true)` で必要な設計・マイクロ ADR・同居 `<Test>`・`<SourceRef>`（公開シンボル一覧）をピンポイントに取得できる。
- **上流の調査・暗黙前提潰し（`documi-design`）** により、既存資産・実バージョン（`package.json` / `.d.ts` / GitHub Actions）・外部パターンを裏取りし、未確定の仮置きは黙って埋めず `intent="idea"` として明示できる。
- 連番なしの自由な階層パス ID により、並列ブランチや複数 AI での編集でも衝突せず、パス自体が意味を持つ。

## 成功のサイン（Success Signals）

- 新しい会話の AI エージェントが `get_project_map` と `get_spec_context` の 2 ステップだけで対象機能の目的・制約・関連設計・実コード位置を正確に把握できる。
- 人間がプロンプトに前提知識を毎回長文でコピペしなくても、仕様・契約に沿った実装が一貫して生成される。
