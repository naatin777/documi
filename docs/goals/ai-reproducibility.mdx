# AI がドキュメントだけで同じ挙動を再現できる

## 誰の課題か（Target Actors）

- 仕様書を読み込んで実装・リファクタ・テスト生成を行うコーディング AI エージェント
- 複数の AI セッションや異なるモデルを跨いで一貫した品質の実装を得たい開発者

## いま何が困っているのか（Problem Statement）

1. **曖昧さのまま「間違ったもの」を爆速で作ってしまう（Upstream Ambiguity / Demo Trap）**: 人間にとって当たり前すぎて言わなかった暗黙の前提・境界条件・本番制約が抜けていると、AI は立ち止まって質問せずにもっともらしい仮定で隙間を埋めて大量実装し、手戻り地獄やセッションごとの挙動ブレを生む。
2. **車輪の再発明 & アーキテクチャ崩壊（Reinventing the Wheel / Architecture Drift）**: 共通語彙・禁止語（Anti-Terms）・既存ユーティリティ地図・全体レイヤー境界がないと、AI は既存の内部関数を見落として似たヘルパーを量産し、エラー処理やデータ取得パターンが発散、局所最適でレイヤー境界も破る。さらに新しいライブラリや GitHub Actions を古い記憶で推測書きしてしまう。
3. **Context Rot（会話内劣化）& Context Drift（セッション断絶）**: 長いチャットを続けると AI が当初の目的や制約を見失い（Rot）、逆に新セッションへ切り替えると前回の合意や暗黙ルールがすべて消える（Drift）。かといって `AGENTS.md` に何でも追記したり ADR 全文を常時投入するとコンテキストがノイズ化し、かえって精度とコストが悪化する。
4. **ファイル連番やフラット構成が並列 AI 作業と衝突し、文脈収集コストも高い**: 複数エージェントでの編集時に連番が衝突し、1 つの仕様を実装するたびに Goal・制約・ADR・用語・契約・設計を手動で集めて貼る手間がかかる。

## どうなってほしいか（Desired Outcome）

- **`docs/` だけを読めば、ほとんどの AI エージェントが同じ振る舞いのソフトウェアを再現できる** 粒度の仕様（`<Spec>` ＋同居する入出力保証 `<Test>`）・制約（`<Constraint>`）・契約（`contract`）・全体設計（`design` / `scope: system`）・用語（`<TermDef>` ＋ `antiTerms`）が構造化されている。
- **常時ロードを最小化し、確定事項を即 `docs/` へ永続化してセッションを短く切れる（Progressive Disclosure）**: AI はまず `get_project_map` で Goal・`goalConstraints`（未リリース方針等）・全体設計（レイヤー境界・共通パターン）・ドメイン不変条件・独立 ADR の `<Decision>` 結論・用語集だけを受け取り、実装対象ごとに `get_spec_context` / `search_documents (includeContext: true)` で必要な設計・マイクロ ADR・同居 `<Test>`・`<SourceRef mode="exports">`（既存公開シンボル地図）をピンポイントに取得できる。
- **後戻りコストに応じた曖昧さ処理と上流裏取りができる**: 既存資産・実バージョン（`package.json` / `.d.ts` / GitHub Actions）・外部パターンを先に裏取りし、**後戻りコストが高い曖昧さ（公開契約・データモデル・認証・不可逆設計）は実装前に必ず人間へ確認** する一方、**後戻りコストが低い曖昧さ（UI 文言・レイアウト細部・暫定デフォルト値）は `<Note intent="idea">` に仮定を明記した上で仮実装してよく**、Overview で人間が後からまとめて確定・修正できる。
- 連番なしの自由な階層パス ID により、並列ブランチや複数 AI での編集でも衝突せず、パス自体が意味を持つ。

## 成功のサイン（Success Signals）

- 新しい会話の AI エージェントが `get_project_map` と `get_spec_context` の 2 ステップだけで対象機能の目的・制約・関連設計・実コード位置を正確に把握できる。
- 人間がプロンプトに前提知識を毎回長文でコピペしなくても、仕様・契約に沿った実装が一貫して生成される。
