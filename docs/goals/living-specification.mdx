# 人間にも AI にもやさしい Living Specification

## ビジョン（存在意義）

Documi は、単なる Markdown ビューアでも、AI に使い捨ての作業メモを書かせるだけのツールでもない。
**「AI がコードを書く時代において、人間が要件定義〜設計〜テスト〜コードまでを深く理解・判断でき、同時に AI エージェントがドキュメントを正として同じ挙動を再現し、コードレビューも有限回で収束させられる」** ための Living Specification プラットフォームを目指す。

## 誰のためのものか（Target Actors）

- **プロダクトオーナー / テックリード / 開発者（人間）**: AI に実装を任せながらも、システム全体像・仕様の確定度・変更差分・実装実態を自分の頭で把握し、最終判断と承認を行う人。
- **コーディング AI エージェント（AI）**: 仕様・制約・契約・ADR の結論・用語とコードシンボルの対応を読み取り、ブレなく実装・テスト・検証を行う実行者。

## 解決したい 4 つの柱（Sub-Goals）

この Root Goal は、解決すべき課題ごとに以下の 4 つの Sub-Goal へ分解する（分割・粒度の基準は [ドキュメント執筆ガイド](../guides/authoring-guide.mdx) を参照）。

1. **[人間が読んでシステムとコードまで深く理解できる](./human-comprehension.mdx)** — AI の生成速度に人間の理解が追いつかない課題を解消し、読む・並べて比較する・俯瞰する体験を最優先にする。
2. **[AI がドキュメントだけで同じ挙動を再現できる](./ai-reproducibility.mdx)** — 曖昧な文書や長大な議論によるコンテキスト圧迫・実装ブレを防ぎ、構造化された仕様と段階的開示で再現性を高める。
3. **[docs を正とした AI レビューが有限回で収束する](./convergent-ai-review.mdx)** — 判定基準のない AI レビューが無限に修正案を出し続ける問題を解消し、`docs/` の曖昧さを潰すことでどの AI でも「問題なし」へ収束する状態を作る。
4. **[人間の手作業を最小化しつつ、脱線と乖離を構造で防ぐ](./low-friction-governance.mdx)** — 承認・進捗管理の形骸化や「仕様に書いてあるから実装済みだと思っていた」事故を、サイドカー分離と自動算出で防ぐ。

## プロダクト哲学・コンセプト

### 1. SpecKit 等の既存 SDD ツールとの違い
既存の Spec-Driven Development (SDD) ツールは `plan.md` や `tasks.md` のような AI 向けの一時的な作業手順書を大量生成しがちで、人間が継続的に読んでシステムを理解する体験が弱い。
AI がコードを書く時代、人間が向き合う時間は「ソースコードの編集」よりも「**要件定義からアーキテクチャ・意思決定・詳細設計・テストまでを通して読み、確認・承認する時間**」が中心になる。
そのため Documi は IDE の文法ではなく **人間が読む・レビューする体験** を最優先に設計する。

### 2. 人間の手作業を極小化する（AI ファースト運用）
人間の責務は次の 3 つに絞る：
1. **方向性（Goal / Non-Goal）を決める**
2. **Web UI で読んで、ワンクリック承認・安定度変更・一言フィードバックを残す**（承認時点からの diff で差分を確認する）
3. **PR をマージする**

それ以外（文書執筆、セマンティックタグでの細切れ構造化、リンク整備、コード＆テストへの紐づけ、整合性チェック、リファクタ追従）は、ほぼすべて AI エージェントと Documi の自動検証に任せる。

### 3. ドキュメントを「AI レビューの停止条件（正）」にし、曖昧さを潰す
AI にコードレビューを依頼したとき、参照すべき正（仕様・契約・Non-Goals・制約・ADR の結論）が曖昧なままだと、修正案や設計の蒸し返しが無限に出続けて収束しない。
Documi は `docs/` を **「満たすべきこと」だけでなく「やらないこと・すでに決めたこと」まで含めた明確な判定基準** として維持し、レビューが収束しない原因である「ドキュメント側の曖昧さ」を継続的に潰していくことを重視する。

## やらないこと（Non-Goals）

- **Web ブラウザ上の高機能 MDX エディタは作らない**: 執筆・リファクタはローカルエディタや AI エージェントが行う方が圧倒的に効率が良く、Git 差分も綺麗に保てるため。
- **一時的なタスク管理ツール（Jira / `tasks.md` 代替）にはしない**: 実装の進行管理や変更の原子単位は Git / PR と自動算出の `realization` に委ねる。
- **独自のクラウド DB に仕様を閉じ込めない**: 常にリポジトリ内のテキストファイル（Markdown / MDX + JSON サイドカー）を正とする。

## 不変制約（Constraints）

<Constraint id="goal.no-arbitrary-js" scope="mdx" stability="stable">
  MDX 内の任意 JavaScript (ESM import/export、JSX 式、未許可コンポーネント) は一切実行しない。許可リストのセマンティックタグのみを AST ベースで安全に処理する。
</Constraint>

<Constraint id="goal.fs-sot" scope="architecture" stability="stable">
  ファイルシステム上の Markdown / MDX を Single Source of Truth とし、Web UI・REST API・MCP Server・CLI はすべて同じ Document Core を参照する。
</Constraint>

<Constraint id="goal.no-tasks-md" scope="workflow" stability="stable">
  一時的な作業チェックリスト (`tasks.md` 等) は仕様リポジトリに蓄積せず、変更の実行単位と履歴は Git / PR に委ねる。
</Constraint>

<Constraint id="goal.web-readonly-mdx" scope="ui" stability="stable">
  Web UI に高機能な MDX 本文エディタは作らない。Web UI からの書き込みは承認サイドカー (`docs/.documi/reviews.json`) に限定し、MDX 本文の編集は AI エージェントまたはローカルエディタが担う。
</Constraint>
