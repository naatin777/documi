# 人間にも AI にもやさしい Living Specification

## ビジョン（存在意義）

Documi は、単なる Markdown ビューアでも、AI に使い捨ての作業メモを書かせるだけのツールでもない。
**「AI がコードを書く時代において、人間が要件定義〜設計〜テスト〜コードまでを深く理解・判断でき、同時に AI エージェントがドキュメントを正として同じ挙動を再現し、コードレビューも有限回で収束させられる」** ための Living Specification プラットフォームを目指す。

## 誰のためのものか（Target Actors）

- **プロダクトオーナー / テックリード / 開発者（人間）**: AI に実装を任せながらも、システム全体像・仕様の確定度・変更差分・実装実態を自分の頭で把握し、最終判断と承認を行う人。
- **コーディング AI エージェント（AI）**: 仕様・制約・契約・ADR の結論・用語とコードシンボルの対応を読み取り、ブレなく実装・テスト・検証を行う実行者。

## AI 開発時代に解決する 5 つの構造的課題

AI がコードを書く時代には、従来の開発とは質が異なる 5 つの構造的な詰まりが発生する。Documi はこれらを個別の場当たり対処ではなく、**構造化された Living Specification（`docs/`）** と 4 つの Sub-Goal で一貫して解消する。

| # | AI 開発の構造的課題 | 何が起きるか | 主に担う Sub-Goal |
|---|---|---|---|
| **1** | **理解負債 & レビュー負債** *(Comprehension / Review Debt)* | 「動くしテストも通るが、なぜこうなっているか誰も説明できない」。PR 差分が肥大化してレビュアーが燃え尽き、ゴム印 LGTM で仕様バグやセキュリティ穴が通過する | [人間が読んで深く理解できる](./human-comprehension.mdx) |
| **2** | **曖昧さのまま「間違ったもの」を爆速で作る** *(Upstream Ambiguity / Demo Trap)* | AI は質問せずもっともらしい仮定で隙間を埋めて大量実装してしまう。人間が暗黙に前提としていた境界条件・本番制約を無視して手戻り地獄になる | [AI がドキュメントだけで再現できる](./ai-reproducibility.mdx) |
| **3** | **車輪の再発明 & アーキテクチャ崩壊** *(Reinventing the Wheel / Architecture Drift)* | AI が既存の内部ユーティリティや共通 API を見落として似たヘルパーを量産し、エラー処理やデータ取得パターンが発散、局所最適でレイヤー境界も壊す | [AI がドキュメントだけで再現できる](./ai-reproducibility.mdx) |
| **4** | **Context Rot（会話内劣化）& Context Drift（セッション断絶）** | 長い会話では AI が当初の目的を見失い、逆に新セッションでは前回の合意や暗黙ルールが全部消える。`AGENTS.md` へ全部詰め込んでもノイズ化で精度が落ちる | [AI がドキュメントだけで再現できる](./ai-reproducibility.mdx) / [AI レビューが有限回で収束する](./convergent-ai-review.mdx) |
| **5** | **「過去の地雷・障害履歴」を良かれと思って消す** *(Chesterton's Fence)* | AI は過去の障害や外部 API のクセを知らないため、一見遠回りな防御コードやエッジケース処理を「綺麗なリファクタ」として削除し、過去のバグを再発させる | [脱線と乖離を構造で防ぐ](./low-friction-governance.mdx) / [AI レビューが有限回で収束する](./convergent-ai-review.mdx) |

## 解決したい 4 つの柱（Sub-Goals）

この Root Goal は、解決すべき課題ごとに以下の 4 つの Sub-Goal へ分解する（分割・粒度の基準は [ドキュメント執筆ガイド](../guides/authoring-guide.mdx) を参照）。

1. **[人間が読んでシステムとコードまで深く理解できる](./human-comprehension.mdx)** — AI の生成速度に人間の理解が追いつかない課題を解消し、読む・並べて比較する・俯瞰する体験を最優先にする。
2. **[AI がドキュメントだけで同じ挙動を再現できる](./ai-reproducibility.mdx)** — 曖昧な文書や長大な議論によるコンテキスト圧迫・実装ブレを防ぎ、構造化された仕様と段階的開示で再現性を高める。
3. **[docs を正とした AI レビューが有限回で収束する](./convergent-ai-review.mdx)** — 判定基準のない AI レビューが無限に修正案を出し続ける問題を解消し、`docs/` の曖昧さを潰すことでどの AI でも「問題なし」へ収束する状態を作る。
4. **[人間の手作業を最小化しつつ、脱線と乖離を構造で防ぐ](./low-friction-governance.mdx)** — 承認・進捗管理の形骸化や「仕様に書いてあるから実装済みだと思っていた」事故を、サイドカー分離と自動算出で防ぐ。

## プロダクト哲学・コンセプト

### 1. SpecKit 等の既存 SDD ツールとの違い
既存の Spec-Driven Development (SDD) ツールは `plan.md` や `tasks.md` のような AI 向けの一時的な作業手順書を大量生成しがちで、人間が継続的に読んでシステムを理解する体験が弱い。
AI がコードを書く時代、人間が向き合う時間は「ソースコードの編集」よりも「**要件定義からアーキテクチャ・意思決定・詳細設計・テストまでを通して読み、確認・承認する時間**」が中心になる。
そのため Documi は IDE の文法ではなく **人間が読む・レビューする体験** を最優先に設計する。

### 2. 人間の手作業を極小化する（AI ファースト運用）
人間の責務は次の 3 つに絞る：
1. **方向性（Goal / Non-Goal）を決める**
2. **AI チャットの対話クイズや Web UI で仕様と差分を確認し、最終確認 URL または Web UI / CLI から承認する**（修正したい点は AI チャットへ直接伝える）
3. **PR をマージする**

それ以外（文書執筆、セマンティックタグでの細切れ構造化、リンク整備、コード＆テストへの紐づけ、整合性チェック、リファクタ追従）は、ほぼすべて AI エージェントと Documi の自動検証に任せる。

### 3. ドキュメントを「AI レビューの停止条件（正）」にし、曖昧さを潰す
AI にコードレビューを依頼したとき、参照すべき正（仕様・契約・Non-Goals・制約・ADR の結論）が曖昧なままだと、修正案や設計の蒸し返しが無限に出続けて収束しない。
Documi は `docs/` を **「満たすべきこと」だけでなく「やらないこと・すでに決めたこと・消してはいけない過去の地雷」まで含めた明確な判定基準** として維持し、レビューが収束しない原因である「ドキュメント側の曖昧さ」を継続的に潰していくことを重視する。

### 4. `AGENTS.md` を太らせず、構造化 `docs/` のオンデマンド取得を正とする
リポジトリルートの `AGENTS.md` 等にルール・構成・歴史的経緯を詰め込むと、毎セッション全量ロードされてコンテキストを圧迫し、過剰探索や精度低下を招く（Context Bloat）。
Documi では常時ロードの指示ファイルは **リポジトリから推測不能な最小限の入口・不変コマンドだけ** に絞り、仕様・制約・用語・ADR・過去の地雷はすべて **`docs/` を唯一の正（SSOT）** として構造化し、`get_project_map` / `get_spec_context` で必要な分だけ段階的開示（Progressive Disclosure）する。また、プロダクトの判断やルールを AI スキル（`.agents/skills/` 等）だけに閉じて書かず、必ず `docs/` へ反映する。

## やらないこと（Non-Goals：あえて設けないもの）

- **Web ブラウザ上の高機能 MDX エディタは作らない**: 執筆・リファクタはローカルエディタや AI エージェントが行う方が圧倒的に効率が良く、Git 差分も綺麗に保てるため。
- **タスク管理・チケット管理（Jira / GitHub Issues / `tasks.md` 代替）はあえて設けない**: タスク・期限・作業担当（Assignee）は終われば消える一時情報であり、永続する Living Specification に混ぜると必ず陳腐化する。作業の実行単位は Git / PR に委ね、仕様の実装状況はコード・テスト・PR からの自動算出（`realization`）で捉える。
- **frontmatter の手書き `owner:` 管理や内蔵コメント板は作らない**: 責任範囲は `.github/CODEOWNERS`、議論・修正依頼は AI チャットおよび GitHub PR に委ね、二重管理を作らない。
- **Web UI に LLM クライアントを内蔵しない**: API キー管理や普段のコーディングエージェントとの文脈分断を避け、AI 機能は CLI / MCP / Agent Skills 側に統一する。
- **独自のクラウド DB に仕様を閉じ込めない**: 常にリポジトリ内のテキストファイル（Markdown / MDX + `docs/guard/reviews.json`）を正とする。

<Note id="note.future-progress-visibility" intent="idea">
  **今後の未実装課題（Non-Goal ではなく将来拡張したい領域）**: タスク管理はあえて設けない一方、「仕様ベースでどこまで完成しているか」の視認性をさらに高めるため、以下を今後の課題として想定している。
  1. Overview の各 Goal カードに配下 Spec の進捗内訳（`verified` / `in-progress` / `unimplemented` / `approved`）を表示する Goal 単位の進捗バー
  2. `documi serve` 起動時にオープン PR を軽量・非同期に反映し、Web UI 上でも `in-progress` 状態が自然に見えるようにする連携
  3. チーム運用向けに `.github/CODEOWNERS` を自動読み取りして担当オーナーを表示する仕組み（frontmatter 手書きなし）
</Note>

## 不変制約（Constraints）

<Constraint id="goal.no-arbitrary-js" scope="mdx" stability="stable">
  MDX 内の任意 JavaScript (ESM import/export、JSX 式、未許可コンポーネント) は一切実行しない。許可リストのセマンティックタグのみを AST ベースで安全に処理する。
</Constraint>

<Constraint id="goal.fs-sot" scope="architecture" stability="stable">
  ファイルシステム上の Markdown / MDX を Single Source of Truth とし、Web UI・REST API・MCP Server・CLI はすべて同じ Document Core を参照する。
</Constraint>

<Constraint id="goal.no-tasks-md" scope="workflow" stability="stable">
  一時的な作業チェックリスト (`tasks.md` 等) は仕様リポジトリに蓄積せず、変更の実行単位と履歴は Git / PR に委ねる。
</Constraint>

<Constraint id="goal.web-readonly-mdx" scope="ui" stability="stable">
  Web UI に高機能な MDX 本文エディタは作らない。Web UI からの書き込みは承認ガードファイル (`docs/guard/reviews.json`) に限定し、MDX 本文の編集は AI エージェントまたはローカルエディタが担う。
</Constraint>

<Constraint id="goal.pre-release-policy" scope="workflow" stability="evolving">
  未リリース開発期間中は後方互換レイヤ（v1/v2 分岐・非推奨エイリアス・DB マイグレーション）を溜めず現行実装を直接書き換える。パッケージ公開・タグ打ち・リリースノート作成等のリリース準備は、人間の明示的な指示なしに開始しない。
</Constraint>
