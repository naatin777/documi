# AI 時代の開発で、人間が仕様と実装を把握し続けられる

## 誰の課題か（Target Actors）

- **AI コーディングエージェントを常用する個人開発者（主対象）**: 実装の大部分を AI に任せながらも、システム全体像・仕様の確定度・変更差分・実装実態を自分の頭で把握し、最終判断と承認を行う人。
- **小規模チームのテックリード（副対象）**: 数人規模のチームで、AI 生成コードの品質と方向性に責任を持つ人。
- **コーディング AI エージェント（AI）**: 仕様・制約・契約・判断理由・共通語彙を読み取り、ブレなく実装・テスト・検証を行う実行者。

## 課題の本質（Root Problem）：人間と AI の「認識のズレ」

AI がコードの大部分を書く開発で人間が疲弊する根本原因は、作業量ではなく **人間と AI の認識のズレが手戻りの形でしか発覚しない** ことにある。ズレは 3 類型に分解できる。

| 類型 | 現れるイライラ | ズレの内容 |
|---|---|---|
| **知らない** | 「その機能、もうあるんだけど…」 | AI がプロジェクトの inventory（既存機能・内部ユーティリティ）を把握していない |
| **流儀が違う** | 「こういう実装にしてほしくないんだけど…」 | AI がこのプロジェクトの設計判断・制約・やり方を知らない |
| **ドメインが違う** | 「全然違うものを作ってる…」 | AI が人間と概念モデル・用語の意味を共有していない |

この構造が厄介なのは 2 点ある。

1. **人間は AI が何を知らないかを事前には把握できない**: 人間は「当然分かっている」と仮定し、AI は分かっていなくても自信満々に隙間を埋めて実装を進めるため、ズレは実装後の手戻りとしてしか表面化しない。
2. **チャットで直してもズレは復活する**: 修正が会話履歴に留まる限り、セッションやモデルが変われば同じズレが繰り返し発生する。

## 5 つの構造的課題（ズレが生む症状）

認識のズレは、従来の開発とは質が異なる 5 つの構造的な詰まりとなって現れる。

| # | AI 開発の構造的課題 | 何が起きるか | 主に担う Sub-Goal |
|---|---|---|---|
| **1** | **理解負債 & レビュー負債** *(Comprehension / Review Debt)* | 「動くしテストも通るが、なぜこうなっているか誰も説明できない」。PR 差分が肥大化してレビュアーが燃え尽き、AI レビューも判定基準がなく無限に発散する | [人間が読んで深く理解できる](./human-comprehension.mdx) / [AI レビューが有限回で収束する](./convergent-ai-review.mdx) |
| **2** | **曖昧さのまま「間違ったもの」を爆速で作る** *(Upstream Ambiguity / Demo Trap)* | AI は質問せずもっともらしい仮定で隙間を埋めて大量実装してしまう。人間が暗黙に前提としていた境界条件・本番制約を無視して手戻り地獄になる | [AI がドキュメントだけで再現できる](./ai-reproducibility.mdx) |
| **3** | **車輪の再発明 & アーキテクチャ崩壊** *(Reinventing the Wheel / Architecture Drift)* | AI が既存の内部ユーティリティや共通 API を見落として似たヘルパーを量産し、エラー処理やデータ取得パターンが発散、局所最適でレイヤー境界も壊す | [AI がドキュメントだけで再現できる](./ai-reproducibility.mdx) |
| **4** | **Context Rot（会話内劣化）& Context Drift（セッション断絶）** | 長い会話では AI が当初の目的を見失い、逆に新セッションでは前回の合意や暗黙ルールが全部消える。指示ファイルへ全部詰め込んでもノイズ化で精度が落ちる | [AI がドキュメントだけで再現できる](./ai-reproducibility.mdx) / [AI レビューが有限回で収束する](./convergent-ai-review.mdx) |
| **5** | **「過去の地雷・障害履歴」を良かれと思って消す** *(Chesterton's Fence)* | AI は過去の障害や外部 API のクセを知らないため、一見遠回りな防御コードやエッジケース処理を「綺麗なリファクタ」として削除し、過去のバグを再発させる | [脱線と乖離を構造で防ぐ](./low-friction-governance.mdx) / [AI レビューが有限回で収束する](./convergent-ai-review.mdx) |

## どうなってほしいか（Desired Outcome）

人間と AI が **同じ仕様グラフを介して理解・実装・検証・承認を往復** できる状態を実現する。認識のズレは修正されるたびに構造化された仕様・判断・用語として永続化され、同じズレは二度と起きない。この双方向ループは 5 段階で構成される（詳細な採用理由は [プロダクト方針の決定](../decisions/2026-11-27-misalignment-as-living-asset.mdx)）。

1. **書く**: 人間の暗黙知（方向性・流儀・ドメイン語彙・判断理由）を仕様として外化する
2. **引く**: AI は必要なタイミングで必要な分だけ仕様を検索・取得する（構造化コンテキスト検索による段階的開示）
3. **確かめる**: 実装前は対話クイズで、実装後はコード・テストとの機械検証で、ズレを手戻り前に炙り出す
4. **直す**: 発覚したズレの修正はチャットで終わらせず、その場で仕様・決定・用語へ記録する
5. **守る**: 人間が承認した知識は AI の編集から保護し、変更は差分通知で人間へ戻す

あわせて、以下の運用状態を目指す。

- **人間の責務を 3 つに絞る**: ① 方向性（Goal / Non-Goal）を決める、② 対話確認や画面上で仕様と差分を確認して承認する、③ PR をマージする。それ以外の執筆・構造化・リンク整備・整合性検証は AI と自動検査に任せる。
- **常時読み込みの指示ファイルを太らせず、仕様の段階的開示を正とする**: ルールや仕様をチャット履歴や運用メモに閉じ込めず、すべて仕様リポジトリへ構造化して必要な文脈だけを都度取り出す。
- この Root Goal は、以下の 4 つの Sub-Goal へ分解して達成する：
  1. **[人間の手作業を最小化しつつ、脱線と乖離を構造で防ぐ](./low-friction-governance.mdx)** — 主軸。承認記録の保護・<Term name="Realization" /> の自動算出・自動検証により、「確かめる」「守る」を担い、未実装事故と乖離を防ぐ。
  2. **[人間が読んでシステムとコードまで深く理解できる](./human-comprehension.mdx)** — 承認・修正判断を速く正確にする手段として、読む・並べて比較する・俯瞰する体験を提供し、理解負債とレビュー負債を解消する。
  3. **[AI がドキュメントだけで同じ挙動を再現できる](./ai-reproducibility.mdx)** — 長期目標。構造化された仕様と段階的開示により、曖昧さ・車輪の再発明・Context Rot / Drift を防ぐ。
  4. **[docs を正とした AI レビューが有限回で収束する](./convergent-ai-review.mdx)** — 実験テーマ。「満たすべきこと・やらないこと・既決事項・過去の地雷」を明記し、どの AI でも有限回で収束する判定基準を探る。

## 成功のサイン（Success Signals）

- **ズレの再発防止**: 人間が同じ指摘・説明・修正を繰り返すことが減り、既決事項を AI が再提案・再実装しなくなる。
- **手戻り前の検出**: 認識のズレが実装後の手戻りではなく、実装前の対話確認や `documi check` の機械検証で発覚する。
- **修正の蓄積**: チャットで発覚したズレの修正が仕様・決定・用語として永続化され、別セッション・別モデルの AI にも引き継がれる。
- **人間の理解**: ソースコードを隅々まで追わなくても、仕様書を読むだけでプロジェクトの目的・制約・主要設計・未確定の仮置きを把握して承認判断できる。
- **構造による乖離防止**: 仕様変更やコードリファクタに伴う乖離・参照切れ・仕様同期漏れが、人間の手動点検なしで機械的に検知される。

## やらないこと（Non-Goals：あえて設けないもの）

- **Web ブラウザ上の高機能な仕様エディタは作らない**: 執筆やリファクタはローカルエディタや AI エージェントが行う方が効率が良く、Git 差分も綺麗に保てるため。
- **タスク管理・チケット管理（Jira / GitHub Issues / 一時チェックリストの代替）はあえて設けない**: タスクや担当は終われば消える一時情報であり、永続する仕様書に混ぜると必ず陳腐化する。作業単位は Git / PR に委ね、仕様の進捗は <Term name="Realization" /> としてコード・テスト・PR から自動算出する。
- **手書きの担当者管理や内蔵コメント板は作らない**: 責任範囲はリポジトリのオーナー設定、議論や修正依頼は AI チャットおよび GitHub PR に委ね、二重管理を作らない。
- **Web UI に LLM クライアントを内蔵しない**: API キー管理や普段のコーディングエージェントとの文脈分断を避け、AI 連携はエージェント側へ統一する。
- **独自のクラウド DB に仕様を閉じ込めない**: 常にリポジトリ内のテキストファイルを正とする。
- **複数人のリアルタイム共同編集・組織的な権限管理は作らない**: 主対象は AI 常用の個人開発者であり、大企業向けガバナンス基盤への拡張は小規模チームでの運用実績が出てから再検討する。

<Note id="note.future-progress-visibility" intent="idea">
  **今後の未実装課題（Non-Goal ではなく将来拡張したい領域）**: タスク管理はあえて設けない一方、「仕様ベースでどこまで完成しているか」の視認性をさらに高めるため、以下を今後の課題として想定している。
  1. Overview の各 Goal カードに配下仕様の進捗内訳を表示する Goal 単位の進捗バー
  2. ローカルサーバー起動時にオープン PR を軽量・非同期に反映し、画面上でも進行中状態が自然に見える連携
  3. チーム運用向けにリポジトリの CODEOWNERS を自動読み取りして担当オーナーを表示する仕組み
</Note>
