# 人間の手作業を最小化しつつ、脱線と乖離を構造で防ぐ

## 誰の課題か（Target Actors）

- AI に大部分の執筆・実装を任せつつ、品質と方向性の責任を持つ開発者・レビューア
- 継続的インテグレーション（CI）上で仕様とコードの整合性を担保したいチーム

## いま何が困っているのか（Problem Statement）

1. **「仕様に書いてあるから実装済みだと思っていた」事故が起きる**: 単一のステータスだけでは「人間が承認したか」と「実際に実装されテストが通っているか」が混線し、手動の進捗チェックリストもすぐ陳腐化する。
2. **AI が良かれと思って勝手に仕様を生やし、目的から脱線する**: 上流の Goal と無関係な機能仕様がいつの間にか増え、人間が気づきにくい。
3. **AI のファイル直書きと人間承認の信頼性が両立しない**: 仕様本文に承認フラグを埋め込むと、AI が編集時に誤って承認を書き換えるリスクがあり差分も汚れる。一方で画面からの本文編集を強制すると執筆効率が落ちる。
4. **仕様変更・コード変更に伴う波及やリンク切れを見落とす**: 上流仕様が変わったのに下流設計が古いままだったり、リファクタでコード側が変わって参照が壊れても気づけない。またコードやスキルだけ変えて仕様の更新を置き去りにしてしまう。
5. **「過去の地雷・障害履歴」を AI が良かれと思って消してしまう（Chesterton's Fence）**: AI は過去の障害・外部 API のクセ・環境固有のワークアラウンドを知らないため、一見遠回りな防御コードやエッジケース処理を「綺麗なリファクタ」として削除し、過去のバグを再発させてしまう。

## どうなってほしいか（Desired Outcome）

- **人間の作業は「方向性の決定・対話確認や画面での承認・PR マージ」だけ** に最小化され、執筆・タグ付け・検証・進捗更新の雑務から解放される。
- <Term name="ReviewRecord" /> は仕様本文から物理分離されて保護され、**承認後に本文が変われば自動で再確認対象（差分表示付き）になり、上流が変われば下流へ <Term name="Suspect" /> が自動波及** する。
- 仕様の <Term name="Realization" /> は手書きを禁止し、**ソースコード・テスト実行結果・PR から完全自動で算出** される。
- **過去の地雷・防御コードは理由・リグレッションテスト・コード近傍メモの 3 点で構造保護** され、リファクタ時に理由確認なしで消されない。
- 必須仕様の Goal 到達性・コード参照の実在性・承認改ざん防止・語彙ドリフト・未確定仮置き・仕様同期漏れが自動で可視化・検証され、脱線や壊れた参照がマージ前に止まる。

## 成功のサイン（Success Signals）

- 人間がレビュー画面を開くだけで、AI が新規追加・変更した仕様と承認時点からの行差分を即座に把握して承認・フィードバックできる。
- テストが 1 件でも落ちたり参照先シンボルが消えたりすれば、手動点検なしで乖離やエラーとして自動検知される。
- 過去の障害回避ロジックを別セッションの AI がリファクタしようとしたとき、記録された判断理由とリグレッションテストによって「なぜ存在するか」を即座に確認でき、無断削除によるバグ再発が起きない。
