# レビュー・Realization・AST 検証・健全性の検証

## 1. 保証シナリオ（Given / When / Then）

### 人間専用レビュー承認と `stale` / `suspect` 波及

- **Given**: 承認済み（`approved`）の `<Spec>` ブロックとその下流 `design` / `spec` が存在する
- **When**: 上流ブロックの本文が編集され `contentHash` が変化する、または `reviews.json` が未許可に編集された状態で `documi check --no-review-edit` を実行する
- **Then**: 変更されたブロックは `stale`、下流ブロックは `suspect` へ遷移し、`reviews.json` の未許可変更は `review-file-modified` エラーで即座に遮断される

### Realization 5 状態の優先順位と JUnit XML 連携

- **Given**: ソースの `@implements`・テストの `test("[<spec.id>] ...")`・`<SourceRef>`・JUnit XML（`passed` / `failed`）が混在するプロジェクトがある
- **When**: `enrichWithRealization` を実行する
- **Then**: `failed` テスト・破損 `<SourceRef>`・`stale`＋実装ありは `drifted`、テスト全通は `verified`、未紐づけは `unimplemented` と優先順位どおりに一意に決まる

### AST 参照検証とセキュリティ境界防御

- **Given**: 9 言語のソースコードを参照する `<SourceRef>` / `<TermDef symbols>` と、絶対パス・`..`・symlink・`.env`・バイナリ・1 MiB 超ファイルを指す不正参照がある
- **When**: `validateSourceLinks`・公開シンボル抽出（`mode="exports"`）・Code Explorer API を実行する
- **Then**: 実在する公開シンボルは最新シグネチャと行範囲が抽出され、壊れた参照や境界外パス・`.env` アクセスはすべて拒否・エラー報告される

### ドキュメント健全性ヒント（非ブロッキング Advisory）

- **Given**: Design/Verification 未カバーの `<Spec>`、`<Spec>` が 10 件超の `spec` 文書、`satisfies` / `verifies` が 10 件超の `design` / `verification` 文書、更新遅れの `architecture` 文書が存在する
- **When**: `computeDocumentHealth` および `documi check` を実行する
- **Then**: `missing-design`・`missing-verification`・`bloated-spec-doc`・`overloaded-hub-doc`・`stale-architecture` が Advisory ヒントとして報告されつつ、CI 終了コード自体は失敗させない

### プロジェクト設定・Monorepo 複数マウントと双方向パス解決

- **Given**: 単一または複数マウント配列の `docs`・複数配列の `testReport` を定義した `.documi.json`、マウント跨ぎ参照（`derives` / クロス相対パス / `doc:<docId>`）、各マウント配下の `guard/reviews.json`、または未定義キー・重複マウント ID を含む不正設定がある
- **When**: `resolveProjectPaths`・`loadDocuments`・`approveBlock`・`documi check --scope <id>`・`documi scaffold --scope <id>` を実行する
- **Then**: 正常構成は名前空間付き統合グラフとして解決され、承認は所属マウントの `guard/reviews.json` へ保存、`--scope` は他マウント参照を壊さず絞り込み、不正設定や重複マウント ID は `ConfigDomainError` で即座に拒否される
