# テスト戦略・品質ゲート・検証方針

## 1. 証拠主義（Prove It Works）と 2 層検証モデル

Documi の検証は **ドキュメント側（受入基準・保証シナリオ）** と **テストコード側（実行証拠）** の 2 層で責務を分担し、二重管理とドリフトを防ぐ。

| 層 | 置き場所 | 役割 |
|---|---|---|
| **保証シナリオ層** | `docs/verification/<domain>.mdx` | 機能領域ごとに、絶対に壊れてはいけない振る舞い・境界値・セキュリティ／異常系を **宣言的な Given / When / Then** で明記する（1 ファイルあたり `verifies` 10 件以下） |
| **実行証拠層** | `tests/*.test.ts(x)` + `.documi/test-results.xml` | `test('[<spec.id>] ...', ...)` と JUnit XML で実挙動を自動検証し、各 `<Spec>` の `realization`（`verified` / `drifted`）を自動算出する |

- **ビルド通過や自己申告を完了とみなさない**: 仕様・契約・修正の完了は、自動テスト実行結果（JUnit XML）および静的・構造チェックの通過という客観的証拠で証明する。
- **形骸テストと過剰モックの禁止**: 定数を写しただけの落ちないテストや、内部実装を過剰モックしたテストは避け、実際のファイルシステム（一時ディレクトリ）・Hono アプリ・`bun:sqlite`・mdast / `@ast-grep/napi`・MCP ツールを通して振る舞いを検証する。
- **バグ修正は Red → Green で確認**: 不具合修正時は、修正前の状態で失敗する再現テストを先に確認してから修正を通す。

## 3. 品質ゲート（マージ前必須コマンド）

PR および変更完了時は、以下をすべてエラー・警告 0 件で通過させる。

```bash
mkdir -p .documi && bun test --reporter=junit --reporter-outfile=.documi/test-results.xml
bun run check
bun run lint
bun run format:check
bun run knip
bun run build
bun run documi:check
```

## 4. 意図的な対象外（Out of Scope）

以下は CI 自動テストの既定対象外とし、過剰なテスト維持コストや環境依存フレーキーを避ける：

- ヘッドレスブラウザによるピクセル単位のビジュアル回帰テスト（WebGL グラフ描画・PDF レイアウト・静的サイト配信の目視確認はローカルスモーク検証で行う）
- 外部 GitHub API (`gh pr list`) や外部 Embedding API（実 Ollama / OpenAI / Gemini サーバー）への実ネットワーク通信を伴う CI 結合テスト（CI では決定論的モックプロバイダおよびモック `fetch` で検証する）
