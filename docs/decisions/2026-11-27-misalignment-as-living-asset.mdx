# プロダクトの芯を「人間と AI の認識のズレの資産化」と定義する決定

<Decision id="dec.misalignment-as-asset" summary="Documi の主対象は AI 常用の個人開発者。中核価値は人間と AI の認識のズレを仕様・決定・用語として永続化し、書く→引く→確かめる→直す→守るの双方向ループで再発を防ぐこと" stability="evolving">
  Documi の主対象は **AI コーディングエージェントを常用する個人開発者**（副対象は小規模チームのテックリード。ただしチーム向けの分業・権限管理機能はスコープ外）とする。中核価値は、人間と AI の **認識のズレ**（知らない・流儀が違う・ドメインが違う）を、修正のたびに構造化された仕様・決定・用語として永続化し、**書く → 引く → 確かめる → 直す → 守る** の双方向ループでズレの再発と手戻りを防ぐことと定義する。構造化コンテキスト検索はオプションの高度機能ではなく、このループの「引く」を担う中核部品と位置づける。**Embedding ありきが本領（推奨）**であり、BM25＋用語展開＋グラフ展開は Embedding 未導入でも成立する依存ゼロの baseline とする。
</Decision>

## 背景と課題

プロダクトレビューと対話を通じて、AI 開発で人間が疲弊する根本原因は作業量ではなく **認識のズレが手戻りの形でしか発覚しない** ことだと特定した。ズレは 3 類型に分解できる。

| 類型 | 現れるイライラ | ズレの内容 |
| --- | --- | --- |
| **知らない** | 「その機能、もうあるんだけど…」 | AI がプロジェクトの inventory（既存機能・内部ユーティリティ）を把握していない |
| **流儀が違う** | 「こういう実装にしてほしくないんだけど…」 | AI がこのプロジェクトの設計判断・制約・やり方を知らない |
| **ドメインが違う** | 「全然違うものを作ってる…」 | AI が人間と概念モデル・用語の意味を共有していない |

さらに構造的な問題として、**人間は AI が何を知らないかを事前には把握できない**。人間は「当然分かっている」と仮定し、AI は分かっていなくても自信満々に実装を進めるため、ズレは実装後の手戻りとしてしか表面化しない。そしてチャットで修正してもセッションが変われば同じズレが復活する。

従来の Root Goal は「人間が仕様と実装を把握し続けられる」と広く掲げ、5 大課題・4 Sub-Goal を同時に背負っていたため、**何が最初の価値かが滲み、機能の取捨選択基準を失っていた**。

## 検討した代替案と棄却理由

### 1. 乖離防止・承認ガードのツールに絞る案

- **検討理由**: `stale` / `suspect` / `reviews.json` / Realization 算出は実装資産と最も一致し、機械検証しやすい。
- **棄却理由**: 受動的すぎる。ズレを「検出して直す」だけでは、AI が正しい知識を持って実装に入る **往路（引く）** が抜け落ち、ズレの発生自体を減らせない。構造化コンテキスト検索は中核でありオプションではないと判明した。

### 2. 汎用 AI メモリ基盤 / RAG プラットフォームと名乗る案

- **検討理由**: 「AI が必要時に正しい知識を引ける」体験は確かに中核であり、RAG はその実現手段である。
- **棄却理由**: ベクトル DB＋全文検索はコモディティであり差別化できない。Documi の固有価値は、検索対象が **承認状態・Stability・Realization・`derives` / `satisfies` グラフ構造を持つ検証済み知識** である点にあり、汎用メモリ基盤の看板はこの強みをかえって隠す。

### 3. 人間向けドキュメント viewer / 通読体験に絞る案

- **検討理由**: Side-by-Side 閲覧・用語ホバー・グラフ・Export は人間の理解体験として強い。
- **棄却理由**: 人間の理解は目的ではなく **承認・修正判断を速く正確にするための手段** である。viewer 中心にするとドキュメントツールとの競合になり、AI との双方向ループという固有価値が消える。

## 採用した方向

認識のズレは最初から全部予測して書き切ることは不可能である。だからこそ、ズレが発覚するたびにそれを資産に変える **双方向ループ** をプロダクトの芯とする。

1. **書く**: 人間の暗黙知（方向性・流儀・ドメイン語彙・判断理由）を仕様として外化する
2. **引く**: AI は必要なタイミングで必要な分だけ仕様を検索・取得する（構造化コンテキスト検索による段階的開示）
3. **確かめる**: 実装前は対話クイズ（`documi-review`）で、実装後はコード・テストとの機械検証（`documi check` / Realization）で、ズレを手戻り前に炙り出す
4. **直す**: 発覚したズレの修正はチャットで終わらせず、その場で `<Spec>`・`<Decision>`・`<TermDef>` へ記録する
5. **守る**: 人間が承認した知識は AI の編集から保護し、変更は `stale` / `suspect` の差分通知で人間へ戻す

このループが回るほど仕様は育ち、同じズレは二度と起きない。**イライラが起きるたびに仕様が育つ** ことが「Living Specification」の名づけの根拠である。

## Sub-Goal の位置づけ

この決定に伴い、4 つの Sub-Goal の優先順位を以下の通り整理する。

| Sub-Goal | 位置づけ |
| --- | --- |
| [脱線と乖離を構造で防ぐ](../goals/low-friction-governance.mdx) | **主軸**: 「確かめる」「守る」を担う |
| [人間が読んで深く理解できる](../goals/human-comprehension.mdx) | **手段**: 承認・修正判断を速く正確にするための補助価値 |
| [AI がドキュメントだけで再現できる](../goals/ai-reproducibility.mdx) | **長期目標**: ループが熟した先の到達点。「完全再現」の直接保証は約束しない |
| [AI レビューが有限回で収束する](../goals/convergent-ai-review.mdx) | **実験テーマ**: 既決事項の再指摘が減るかの観測から始める |

## 影響・将来の見直し条件

- **機能の取捨選択基準**: 各機能は「ズレのどの類型を、ループのどの段階で減らすか」で説明可能でなければならない。説明できない機能追加は優先度を下げる。
- **Embedding の位置づけ**: Embedding ありきを「引く」の本領とし、導入を強く推奨する。BM25＋用語展開＋グラフ展開は Embedding 未導入環境でもループが成立する依存ゼロの baseline として維持する（縮退ではなく正式な動作形態）。
- **未承認知識の検索での扱い**: AI が「直す」で記録した修正は unreviewed のまま検索コーパスに入り、承認前に次の AI が参照しうる。これは意図通りとし、除外・降格はせず **unreviewed / suspect / stale / Stability / Realization / `supersedes` 失効のラベルを付けて返し、AI 側が信頼度を判断できる** ようにする方向を目指す。
- **チーム境界**: 副対象のテックリードは「個人として Documi を使う」利用形態を指す。「A が書いて B が承認」のような分業・権限管理の要望はスコープ外と明言し、個人利用の体験を優先する。
- **受け入れるトレードオフ**: 「認識のズレ」は感情ベースで直接測定できない。計測機能の実装にはコミットせず、**まず自分たちの dogfooding で再発・手戻りの実例を観察してから**、代理指標や計測の要否を判断する。
- **見直し条件**: 主対象を個人開発者に絞った判断は、小規模チームでの導入実績が出た段階で再検討する。また「AI レビュー収束」の観測手段が確立された場合は Sub-Goal の優先順位を見直す。
