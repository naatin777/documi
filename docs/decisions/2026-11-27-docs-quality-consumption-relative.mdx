# docs の品質は消費結果で定義し、検証はピラミッド構造で育てる

<Decision id="dec.docs-quality-consumption-relative" summary="docs の正しさは文書に内在せず消費結果にのみ存在する。品質検証は再現実験を頂点とするピラミッドで構造化し、品質基準は誤読の実測から育つ資産とする" date="2026-11-27">

<Context>
`<Signal>` ブロック導入に続き「docs 自体が正しく書けているかをどう保証するか」が課題となった。外部調査（spec-kit の checklist「unit tests for requirements」、BDD Living Documentation、vale 等の prose linting、freshness 管理）では、業界でも正しさは層ごとに別仕組みで扱われていることが分かったが、各層を統べる原理は明示されていない。原理なしに個別機構を輸入すると、消費者の誤読予測に寄与しない形骸化した検査が増える危険がある。
</Context>

<Chosen>
**docs の品質は消費結果で定義する**: 「この docs を読んだ AI・人間は、人間の意図と一致した行動を取れるか」が唯一の究極基準であり、文書内在の正しさは追わない。以下の 3 つを tenet とする。

1. **品質は消費相対**: すべての品質機構は「消費失敗（誤読・ズレ）をどれだけ予測できるか」で評価する。INCOSE 等の汎用ルールはそのまま輸入せず、AI が実際に誤読したパターンから逆向きに規則を導く。
2. **検証はピラミッド構造**: 頂点は再現実験（別 AI に docs だけ渡して挙動を再現できるか、高コスト・低頻度）、中段はクイズ・checklist（消費者との認識検証）、下段は Signal の機械判定と check（構造整合、高速・高頻度）。下位の代理指標の価値は上位の失敗との相関で測る。
3. **品質基準もまた資産**: checklist や品質規則は使い捨てず、誤読が観測されるたびに育つ蓄積物として docs に保持する（spec-kit が checklist を毎回生成して捨てるのとの差別化点）。犬食いで実際に起きた誤読を最重要データとして収集する。
</Chosen>

<Rejected option="INCOSE / EARS 等の要求品質ルールを一式輸入して機械検査する">
汎用ルールは人間向け要件工学の基準であり、AI エージェントの誤読パターンと一致するとは限らない。消費失敗との相関が実測されない検査は形骸化し、誤った安心感を生む。規則は犬食いの誤読データから必要なものだけ育てる。
</Rejected>

<Rejected option="再現実験だけを品質保証の中心に据える">
再現実験は高コストで頻繁に回せず、日常の編集のたびには使えない。だからこそ高速な代理指標（check・Signal）の層が必要であり、ピラミッドの各層は代替ではなく補完関係にある。
</Rejected>

<Rejected option="散文品質（vale 等の prose linting）を最優先で導入する">
読み味の改善は消費失敗の主因ではないことが多く、優先度は低い。曖昧語の警告は AI の解釈分岐に寄与する場合のみ意味を持つため、誤読データで裏付けてから導入する。
</Rejected>

<Tradeoff>
消費相対の品質定義は、客観的で静的な「仕上がり検査」を持たないことを意味し、品質の判断が常に消費文脈に依存する。再現実験は頻繁に回せないため、日常では代理指標への依存が避けられず、代理指標と実際の誤読の相関を犬食いで観測し続ける運用負荷が残る。
</Tradeoff>

</Decision>

## 影響

- 品質機構の設計判断はすべてこの 3 tenet に照らす: 「消費失敗を予測するか」「ピラミッドのどの層か」「基準は資産として蓄積されるか」
- 犬食いで誤読（AI が docs を読んで意図と違う行動を取った事例）が起きたとき、`<Decision>` や品質規則として記録する運用を始める
- checklist 的な要件品質検証・prose linting の導入可否は、誤読データが集まってから本 ADRに照らして判断する
