# 同一リポジトリ原則・読み取り専用 Code Explorer・MCP 精密編集ハイブリッドの採用

<Outcome id="dec.repo-code-and-mcp-edit" stability="stable">
  `docs/` とプロジェクトコードは **同一リポジトリ・同一ブランチ（Docs-as-Code）** を標準既定とし、1 つの PR 内で仕様・実装・テスト・`documi check` を原子的に検証する（同一 repo 内の別ブランチ運用は非推奨、マルチリポは将来の設定拡張で扱う）。Web UI には **読み取り専用の Code Explorer** を搭載し、ドキュメント⇄ソースコードの双方向参照と仕様カバレッジ可視化を提供する（コード編集可能な Web IDE にはしない）。AI のドキュメント編集は **探索・検証・ブロック単位の精密編集＆ID リネームを MCP、大規模な自由記述をファイル直書き** とする 3 層ハイブリッドを採用し、AI が 1 ブロック修正するためにファイル全体の不要な文脈を読み込む汚染を防ぐ。なお **`docs/.documi/reviews.json` の更新（承認）は引き続き人間専用** とし、MCP 書き込みツールからは一切変更不可とする。
</Outcome>

## 背景と判断軸（Context / Drivers）

1. **人間が仕様からコードまで一貫して理解したい**: `<SourceRef>` や用語ホバーによる抜粋表示だけでは、ファイル全体の文脈や「どのソースファイルがどの仕様を実装していて、どこが仕様未紐づけか」を追いにくい。
2. **仕様とコードの乖離を構造的に防ぎたい**: `docs/` とソースの配置関係が曖昧だと、PR レビュー・CI 検証・`approvedCommit` ベースの Git diff が破綻しやすい。
3. **AI 編集時のコンテキスト汚染を防ぎたい**: 大規模な仕様書や用語集から 1 つの `<Spec>` / `<TermDef>` だけを修正したい場合、ファイル直書き（`read_file` → `edit_file`）では置換位置を合わせるために無関係なブロックや背景文章まで丸ごと AI コンテキストに読み込みがちになる。一方で、長文ガイドの全面執筆を MCP の JSON 引数に押し込むとエスケープ崩れやトークン浪費を招く。

## 検討した選択肢と棄却理由（Options Considered）

### 1. Web UI からのソースコード閲覧

- **採用: 読み取り専用の Code Explorer（仕様⇄コード双方向ビューア）**
  - `<SourceRef>`・Context Inspector・Realization から該当ファイルの全文＋行ハイライトへ即座に遷移でき、コード側からも紐づく `<Spec>` / `<TermDef>` へ逆ジャンプできる。
  - `src/core/source.ts` の `projectRoot` 境界防御・バイナリ拒否・サイズ制限をそのまま流用して安全性を担保する。
- **棄却: 抜粋表示（`<SourceRef>`）のみに留める**
  - 前後の文脈や仕様未紐づけのファイル分布が見えず、「ドキュメントをコード理解の地図にする」目標を片方向しか満たせない。
- **棄却: Web UI 上でソースコードを直接編集できる Web IDE 化**
  - 既存のコードエディタ / AI エディタと競合し、複雑なエディタ状態管理・LSP・競合解決の保守コストに見合わない。

### 2. `docs/` とプロジェクトコードのリポジトリ・ブランチ構成

- **採用: 同一リポジトリ・同一ブランチを標準既定（`--project` / 将来のマルチリポ設定を拡張口として維持）**
  - 1 つの PR で「仕様変更＋実装＋テスト＋`documi check`」を原子的に検証・レビュー・`git revert` でき、`reviews.json` の `approvedCommit` とコードの履歴も一致する。
- **棄却: 同一リポジトリ内の別ブランチ（例: `docs` 専用ブランチ）**
  - コードブランチと仕様ブランチが必ず時間差でズレ、`@implements` や `<SourceRef>` の AST 検証・JUnit 連携が破綻しやすい。
- **保留（将来拡張）: 複数リポジトリ横断の仕様リポジトリ**
  - マイクロサービス横断の上位設計では需要があるため、既存の `--docs` / `--project` 分離を維持しつつ、将来的に複数 `projectRoot` マッピング設定へ拡張できる余地を残す。

### 3. AI によるドキュメント編集経路

- **採用: 3 層ハイブリッド（探索・検証・局所ブロック編集＆ID リネーム＝MCP / 大規模な自由記述＝ファイル直書き）**
  - `get_spec_context` / `query_specs` が正確な `docPath`・`startLine`・`endLine` を返すことで、ピンポイント参照を可能にする。
  - 1 ブロック更新（`update_block`）・ブロック追記（`add_block`）・用語登録（`upsert_term`）・新規雛形作成（`scaffold_document`）・参照一括リネーム（`rename_block_id`）を MCP ツール化することで、**AI がファイル全体や全参照ファイルを読み込まずに安全に編集でき、同時に即時バリデーションまで完結**する。
  - 長文ガイドや大規模構成変更は従来通りファイル直書き＋`validate_docs` を許容する。
- **棄却: MCP を完全読み取り専用に固定する**
  - 1 ブロックや 1 用語を直すたびに AI が文書全体を読み込む必要が生じ、コンテキスト圧迫と無関係箇所の誤改変リスクが残る。またブロック ID 変更時の全ファイル横断置換で取りこぼしが起きやすい。
- **棄却: すべてのドキュメント編集を MCP 経由のみに強制する**
  - 長大な MDX 全文の JSON エスケープによる劣化・トークン増を招き、コーディングエージェント標準のファイル diff 承認 UX の利点を失う。

## 影響とガードレール（Consequences）

- **不変の権限境界**: MCP 書き込みツールは `docs/` 配下の `.mdx` / `.md`（および `rename_block_id` に限り `projectRoot` 配下の対象ソース・テストファイル）のみを更新でき、**`docs/.documi/reviews.json` および `.documi/` 配下は絶対に書き換えない**。
- **書き込み時の即時検証**: MCP 書き込みツールは書き換え前にパストラバーサル・MDX 危険構文・ID 形式・重複 ID を検証し、違反時はファイルを変更せずエラーを返す。書き込み後は `DocsStore` を再読込して最新の検証結果を返す。
- **見直し条件**: 複数リポジトリ横断の仕様管理ニーズが高まった段階で、複数 `projectRoot` 設定ファイル形式を別 ADR で検討する。
