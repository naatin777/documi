# docs 構造を capability 同居＋横断グローバル層へ転換する決定

<Decision id="dec.capability-colocated-structure" summary="solution 空間（spec/test/micro-ADR/設計メモ）は capability 単位のファイルに同居させ、goals・domain・横断 ADR・system 設計のみグローバル層に残す。type は配置ではなく意味論。全体俯瞰はツリーではなくツールが担う" stability="evolving">
  docs の solution 空間（`<Spec>`・`<Test>`・インライン `<Decision>`・設計メモ）は **capability（機能領域）単位のファイルに同居** させ、`goals/`・`domain/`・プロジェクト横断 ADR（`decisions/`）・システム全体設計のみ **グローバル層** として type 別配置を残す。Artifact Type は配置ルールではなく frontmatter / ブロックの意味論とし、type 別ディレクトリへの収納は強制しない。**type 全体の俯瞰はファイルツリーではなくツール（`documi map` / グラフ / Overview）の責務** とし、ファイルツリーは人間の認知モデルに合わせて機能中心に寄せる。
</Decision>

## 背景と課題

type 別ディレクトリ配置（`goals/` / `specs/` / `designs/` / `decisions/` …）を dogfooding した結果、以下の構造的な摩擦が見えた。

1. **人間の認知モデルとの不一致**: 人間は type ではなく機能で考える。「auth のことを知りたい」とき `specs/`・`designs/`・`decisions/`・`contracts/` を跨ぐ必要があり、1 機能の知識が物理的に散在する。認識のズレを減らすツールが、配置構造自体で「なんで分かれているの？」というズレを生んでいる。
2. **明示エッジへの過度な依存**: 散在した知識を繋ぐ `derives` / `satisfies` はすべて手書きの負債であり、書き忘れるとグラフが繋がらず腐る。一方、**同居している知識はリンクを書かなくても構造的に繋がっている**。近接性は保守不要で腐らない暗黙のトレーサビリティである。
3. **初見のわかりにくさ**: 新規ユーザーが `docs/` を開いたとき、type 分類はプロダクトの機能マップとして見えず、導入障壁になる。

外部調査では、GitHub spec-kit（`specs/NNN-feature/` に spec・plan・contracts を同居）や Kiro（`.kiro/specs/<feature>/`）など、AI 仕様駆動ツールは **機能同居へ収斂** しつつある。ただしこれらは feature 開発ワークフローの使い捨て成果物（`tasks.md` 等）を含む設計であり、永続する Living Memory を目指す Documi とは性質が異なる。直貼りはせず、原則のみを取り込む。

## 検討した代替案と棄却・先送り理由

### 1. type 正規化の維持（現状）

- **擁護できる点**: 寿命・読み手が type ごとに揃う。「ファイルは正規化されたストレージ、読むときはツールが join する」哲学として一貫している。ファイルがほとんど移動しないため **Doc ID（＝パス）が安定** する隠れた美徳がある。
- **棄却理由**: 認知負荷・明示エッジ依存・初見の問題は構造に由来するため、ツールの join 体験を磨いても根本解決にならない。「正しく届く知識」が正義なら、近接性という最強の配送手段を捨てる理由がない。

### 2. 完全機能同居（spec-kit 型）

- **棄却理由**: 知識は本来グラフ状であり、機能軸もまた単一の木でしかない。共有語彙（`domain`）・システム横断の制約・複数機能に跨る ADR など **機能に帰属しない知識の置き場が死ぬ**。8 割は機能ローカルでも、残り 2 割は正しくグローバルであるべき。

### 3. Doc ID とパスの分離まで一気に踏み込む案

- **検討内容**: `id:` frontmatter を正規 ID とし、ファイルツリーを「居所」に格下げする。これができれば配置の自由が完全になり、capability 再編の移動コストも消える。
- **先送り理由**: ID 解決・`supersedes`・レビュー記録・マルチマウント・静的出力の全レイヤに影響する大規模再設計であり、配置転換と同時に行うと変更が読めなくなる。**段階的に進める**: まず配置転換と rename ツールの強化で運用し、capability 再編による移動の痛みが実測された段階で ID 分離を別途 ADR として再検討する。

## 採用した構造

```text
docs/
├── goals/            ← 少数・安定。グローバル層
├── domain/           ← 共有語彙は横断知識。グローバル層
├── decisions/        ← プロジェクト横断の ADR のみ（時系列ジャーナル）。グローバル層
├── system/           ← システム全体設計・システム制約（現行の scope: system に相当）。グローバル層
└── capabilities/     ← solution 空間。機能中心の名前付けはプロジェクト自由
    └── auth/
        └── lockout.mdx   ← <Spec> + <Test> + インライン <Decision> + 設計メモが同居
```

配置ルール:

- **capability ファイルへの同居をデフォルトとする**: 1 capability = 1 ファイルの原則は維持しつつ、`<Test>` とインライン `<Decision>` に加えて設計メモ・境界条件も同じファイルに置く。ファイルが大きくなってもレビューはブロック単位のため承認粒度は低下しない。
- **capability の粒度**: ドメイン領域（例: `auth`）をディレクトリ、capability（例: `lockout`）をファイルとする 2 段構成を標準とする。領域ディレクトリの命名はプロジェクトのドメイン語彙に従う。
- **横断的な振る舞い知識は `domain/` に置く**: 複数 capability が依存する共有のドメインモデル・状態機械・不変条件（例: アカウント状態機械）は、capability でも `system/` でもなく `domain/` 層に置く。`system/` はアーキテクチャ構造・技術制約に限定する。
- **micro-ADR の昇格**: capability ファイル内のインライン `<Decision>` が後から複数 capability に影響すると判明した場合、`decisions/` の独立 ADR へ昇格し、元のインライン記述は superseded またはリンクに置き換える。
- **肥大時の分離ルール**: capability ファイルの設計記述が複数モジュール・画面に跨る構造になり単体で読む価値が出た場合、またはファイルが通読に耐えない規模（目安: 数百行級。閾値は dogfooding で調整）になった場合、`design` 等を別ファイルへ分離する。分離後も同じ領域ディレクトリに置き近接性を保つ。
- **`contract` が独立ファイルになるのは例外的な場合のみ**: 外部インターフェースとして単体で読む価値がある場合に限る。
- **「どちらに置くか」の判断基準**: その知識を必要とするのが 1 つの capability のみなら同居、2 つ以上ならグローバル層（振る舞いは `domain/`、横断 ADR は `decisions/`、アーキテクチャは `system/`）。迷ったら同居を選び、横断利用が実測されてからグローバルへ昇格する（早すぎる抽象化を避ける）。
- **type は frontmatter / ブロックの意味論**: ディレクトリ名からの type 推論は残しつつ、配置による type の強制はしない。

## 全体俯瞰はツールの責務

ファイルツリーが機能中心になると、「全 spec 一覧」「全 decision の時系列」のような type 横断の俯瞰はツリーからは読めなくなる。これは退行ではなく責務の移動であり、以下が代替となる。

- **`documi map` / Overview**: type 別サマリと健全性の俯瞰
- **グラフビュー**: 機能を跨ぐ依存関係の可視化
- **`documi query --kind` / `--type`**: type 単位の一覧抽出

つまり **ツリーは機能の物語を、ツールは type の俯瞰を** 担う。犬食いとして、capability 構造でも全体を見渡せることが確認できなければならない。

## 影響・移行

- **段階移行とし、本 ADR だけでは既存 docs を移動しない**: 移行は別途計画し、① rename / 移動ツールの確認、② init テンプレートと scaffold の更新、③ 自リポジトリ docs の移行（最大の犬食い）、の順で進める。
- **type 推論・マルチマウント・静的出力への影響を検証する**: frontmatter 優先の type 推論は既に対応しているが、`bloated-spec-doc` 等の健全性ヒント・ scaffold のテンプレート・静的サイトのナビゲーションは type 別配置を前提にしている可能性があり、移行時に監査する。
- **マルチマウントとの親和性**: capability 同居はコード近傍に docs を置くモノレポ運用と自然に整合する。
- **見直し条件**: ① capability 再編によるファイル移動が頻発し ID 不安定が実測されたら ID 分離を再検討、②「どちらに置くか」の判断が運用上の摩擦になったら判断基準を改訂、③ ツールによる俯瞰が不足していれば構造側ではなくツール側を強化する。
